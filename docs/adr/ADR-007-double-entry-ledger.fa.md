# ADR-007: حسابداری دوطرفه از V1

وضعیت: طراحی پذیرفته‌شده در ۲۰۲۶-۱۰-۲۲ با انتخاب گزینهٔ E توسط مالک پروژه. پیاده‌سازی و شواهد SQL Server هنوز وجود ندارند و کارایی اندازه‌گیری نشده است. [English](ADR-007-double-entry-ledger.en.md)

## مسئله: موجودی فعلی، تاریخچه را توضیح نمی‌دهد

اگر فقط موجودی فعلی را نگه داریم، نمی‌توانیم آن را از سابقهٔ حسابداری بازسازی کنیم. مثلاً credit مشتری باید هم حساب مشتری و هم حساب مقابل را در یک journal متوازن ثبت کند. نمونه‌ها و قواعد علامت در سند دفترکل آمده‌اند.

## تصمیم

در همین سرویس SQL Server از `accounts`، `operations`، `journals` و `postings` استفاده می‌کنیم. posting‌ها شواهد مالی immutable هستند و موجودی ماندگار حساب، projection هم‌زمان آن‌هاست. journal کامل و متوازن، projection‌ها و موفقیت عملیات باید با هم commit شوند.

| حالت | رفتار |
| --- | --- |
| rejection | بدون journal و posting |
| retry مطابق | پاسخ ذخیره‌شده، بدون posting تازه |
| افتتاحیهٔ غیرصفر | عملیات داخلی با opening journal |
| credit/debit | حساب مقابل تأمین یا تسویه |

این تصمیم، اختیاری یا آینده‌بودن double-entry در ADR-003 و شروع دوجدولی را جایگزین می‌کند. معماری پذیرفته شده، اما constraint، هویت، قفل و امنیت ADR-001–005 هنوز به مرور نیاز دارند.

[طراحی دفترکل](../fa/Ledger.md) قواعد علامت، مثال‌ها، reconciliation و تحویل مرحله‌ای را توضیح می‌دهد. این گسترش دامنه انتخاب کاربر است و الزام شرکت معرفی نمی‌شود.

## گزینه‌ها و هزینه

| گزینه | دلیل انتخاب یا رد |
| --- | --- |
| فقط balance | تاریخچهٔ حسابداری قابل‌بازسازی نیست |
| رکورد ثابت دوحسابی | ساده‌تر است، اما journal چندسطری آینده را محدود می‌کند |
| لایه‌های اضافی transfer و ledger transaction مثل BankingLedger | lifecycle اضافه برای این دامنه |
| سرویس مستقل ledger | مرز distributed غیرضروری |
| مدل منتخب | چند posting در یک تراکنش محلی |

SQL schema جدا تضمین حسابداری تازه اضافه نمی‌کند.

هزینه‌ها، فضای journal و posting، index، log write، reconciliation و contention حساب تأمین مشترک‌اند. در CBS21–22 اندازه‌گیری می‌شوند؛ invariant را برای ادعای سرعت تضعیف نمی‌کنیم. FX آینده review مستقل ارز، clearing و reservation می‌خواهد.

## پیاده‌سازی و پذیرش

ابتدا [ماتریس قیدها](../fa/Database-review.md) و CBS02–04 را پیش از اولین migration مالی مرور کنید. قواعد دامنه، migration چهارجدولی، mapping و operation slice‌ها در همان کارهای هدایت‌شده اضافه می‌شوند. مراحل آینده را یک‌جا پیاده نکنید و learning gate را بدون شاهد نبندید.

### شواهد لازم

SQL Server test باید concurrency، duplicate race، افتتاحیه، immutability، rollback در تمام write boundary‌ها، restart و بازسازی مستقل را پوشش دهد.

### اصلاح و migration آینده

اصلاح مالی با reversing journal تازه انجام می‌شود؛ endpoint عمومی reversal خارج V1 است. فعلاً schema rollback یا data migration نداریم. تغییر آیندهٔ تاریخچهٔ ثبت‌شده، forward migration بررسی‌شده و حفظ هویت‌ها می‌خواهد.
