# قرارداد HTTP API نسخهٔ اول

[English](../en/API-v1.md) · [نقشهٔ راه](Roadmap.md)

دامنهٔ انتخاب‌شده توسط کاربر در ۲۰۲۶-۱۰-۲۲: اولین نسخهٔ کاربردی هر چهار عملیات موجودی را از طریق HTTP API با JSON و SQL Server ارائه می‌کند. شکل endpointها تا مرور CBS01/CBS23 پیشنهادی است. هنوز endpoint مالی پیاده نشده است. V1 یعنی اولین نسخهٔ کاربردی API و با migration موسوم به `V1` در Flyway یا tag گیت متفاوت است.

## مسیرهای پیشنهادی

| روش | مسیر | درخواست |
| --- | --- | --- |
| POST | `/api/v1/accounts/{accountId}/credits` | `transactionId`, `amountMinor`, `currency` |
| POST | `/api/v1/accounts/{accountId}/debits` | `transactionId`, `amountMinor`, `currency` |
| POST | `/api/v1/transfers` | `transactionId`, `sourceAccountId`, `destinationAccountId`, `amountMinor`, `currency` |
| GET | `/api/v1/accounts/{accountId}/balance` | شناسهٔ حساب در path |

مبلغ صحیح در واحد کوچک پول و محدودهٔ `long` است. یک ارز پشتیبانی‌شده در CBS01 انتخاب شود؛ کد ارز دلخواه پذیرفته نشود. عملیات تغییردهنده از فضای یکتای مشترک transaction ID با تشخیص تعارض نوع عملیات و payload استفاده می‌کنند. خطای نحوی شناسهٔ عملیات را رزرو نمی‌کند. مقداردهی اولیهٔ حساب‌ها بخشی مستند از توسعه/تست و جدا از این چهار مسیر است.

عملیات موفق HTTP 200 و نتیجهٔ صریح شامل transaction ID، نوع عملیات، ارز و دادهٔ نتیجهٔ commitشده برمی‌گرداند. replay همان نتیجهٔ ذخیره‌شده را حتی پس از تغییر بعدی موجودی برمی‌گرداند. استعلام، موجودی commitشده و ارز را برمی‌گرداند. فیلدهای دقیق DTO، content type و مثال‌ها در CBS23 پیش از پیاده‌سازی مسیرها مشخص شوند.

خطاهای پیشنهادی پاسخ ProblemDetail یکسان با `code` پایدار دارند: HTTP 400 برای ورودی نامعتبر، شناسه/مبلغ نادرست، ارز پشتیبانی‌نشده یا انتقال به خود؛ 404 برای حساب ناموجود؛ 409 برای تعارض payload شناسهٔ عملیات، کسری موجودی یا overflow؛ 503 برای عدم دسترسی موقت زیرساخت یا پایان retryهای موقت. کدهای نهایی و بازیابی commit نامطمئن در CBS01/CBS03/CBS23 مرور می‌شوند. پاسخ 503 یا گم‌شدن پاسخ اثبات نمی‌کند commit رخ نداده است؛ retry با همان transaction ID نتیجهٔ ماندگار را بازیابی می‌کند. stack trace، رمز و SQL داخلی وارد پاسخ نشوند.

## تحویل و پذیرش

interface جاوای موجود اسکلت اولیه است و خروجی V1 یا API عمومی ثابت نیست. منطق تراکنش پشت controllerهای نازک در packageهای مبتنی بر feature و با constructor injection بماند. نوع‌ها و امضاهای سرویس داخلی می‌توانند برای بیان نتیجه و خطای کسب‌وکار تغییر کنند؛ معنای چهار عملیات حفظ و تفاوت عمدی با امضاهای جاوای چالش مستند شود. interface صرفاً برای انتقال منطق تراکنش به controller حذف نشود.

قرارداد HTTP، اعتبارسنجی DTO، نگاشت خطا و تست متمرکز adapter در CBS23 بلافاصله پس از CBS05 اضافه شوند. هر عملیات ماندگار در CBS10–15 یک مسیر کامل HTTP تا SQL Server باشد. پاسخ موفق ساختگی مالی پیاده‌سازی پذیرفته‌شده نیست. تست هم‌زمانی سرویس و SQL مستقیم حفظ و integration واقعی HTTP برای موجودی، تغییرات، replay، conflict، اعتبارسنجی و rollback اضافه شود. معیار هسته در CBS20 شامل چهار مسیر واقعی و راهنمای بازتولید API با Docker و مثال درخواست/پاسخ است.

V1 ابتدا API توسعهٔ محلی با اتصال loopback فعلی و فرض صریح اپراتور مورداعتماد است. JWT، مالکیت و نقش در CBS24–25/P3 و پیش از دسترسی اشتراکی یا خارجی اضافه می‌شوند. V1 سرویس امن مشتریان نامیده نشود. خطای احراز هویت بعداً 401 و خطای مجوز 403 است و مجوز فعلی پیش از replay بررسی می‌شود. OTP در P4 باقی می‌ماند و پس از اضافه‌شدن تأیید، مسیر مستقیم انتقال نباید آن را دور بزند. Redis، Kafka و CDC همچنان مراحل بعدی‌اند.
