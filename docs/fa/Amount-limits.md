# سقف مبلغ و replay در V1

به‌روزرسانی پیاده‌سازی، ۲۰۲۶-۱۰-۲۴: [snapshot سیاست اجرا](Execution-policy.md) اکنون predicate سقف شامل مقدار مساوی و انتخاب funding تغییرناپذیر را مستقل از زیرساخت دارد. بارگذاری typed و اختیاری هنگام startup هم موجود است؛ ارزیابی و رد ماندگار و اتصال HTTP هنوز باقی‌اند.

## سیاست پذیرفته‌شده، ۲۰۲۶-۱۰-۲۳

کاربر برای سقف عملیات و موجودی مشتری مقدار `10000000000000` را مشخص کرد و نگه‌داشتن رد اولیهٔ سقف را انتخاب کرد. سقف مشترک اولیهٔ V1 برای هر credit، debit و transfer و برای موجودی هر مشتری **۱۰٬۰۰۰٬۰۰۰٬۰۰۰٬۰۰۰ ریال** است. رسیدن دقیق به سقف مجاز است. این سند تصمیم کسب‌وکار را ثبت می‌کند؛ بارگذاری سیاست، ارزیابی سقف، رد ماندگار و اعمال قید در schema هنوز پیاده نشده‌اند.

| مقدار | قاعدهٔ اولیهٔ V1 |
| --- | --- |
| مبلغ credit/debit/transfer | عدد صحیح مثبت ریالی، حداکثر 10000000000000 |
| موجودی مشتری پس از عملیات موفق | از صفر تا 10000000000000، با احتساب دو مرز |
| موجودی حساب مصنوعی funding/clearing | سیاست قبلی signed-long بر اساس دستهٔ حساب؛ سقف مشتری شامل آن نیست |
| موجودی افتتاحیهٔ مشتری | رعایت سقف موجودی مشتری و پروتکل پذیرفته‌شدهٔ journal افتتاحیه |

سقف transfer روی مبلغی اعمال می‌شود که یک بار جابه‌جا می‌شود. انتقال ۱۰۰ ریالی یک posting بدهکار ۱۰۰ و یک posting بستانکار ۱۰۰ دارد؛ جمع دو خط، مبلغ انتقال را ۲۰۰ نمی‌کند. این سقف مجوز FX نمی‌دهد و سیاست اولیهٔ استقرار با IRR را تغییر نمی‌دهد.

## نمایش عدد و سیاست کسب‌وکار

نوع‌های `long` در Java و `BIGINT` در SQL Server اعداد مثبت بزرگ‌تر از این سقف را هم نمایش می‌دهند. `Money` برای حسابداری عمداً مقدار علامت‌دار می‌پذیرد، اما command مالی مبلغ مثبت می‌خواهد. parser در HTTP جداگانه عدد اعشاری و عدد بیرون از بازهٔ signed-long را رد می‌کند. سقف انتخابی را داخل parser ساختار یا سازندهٔ عمومی Money قرار ندهیم؛ درخواست مثبت و قابل‌نمایش بالاتر از سقف باید برای رد ماندگار قابل‌ثبت باشد.

بنابراین جدول آیندهٔ operations باید مبلغ درخواستی بالاتر از 10000000000000 را ذخیره کند. قید عمومی `operations.amount <= cap` ثبت آن رد را غیرممکن می‌کند. نامنفی‌بودن موجودی مشتری و بازهٔ نمایش عدد، invariant ساختاری‌اند؛ اعمال سقف قابل‌تنظیم کسب‌وکار به snapshot صریح سیاست و مسیر کنترل‌شدهٔ نوشتن هم نیاز دارد. قیدهای دقیق SQL همچنان بخشی از مرور پیش از migration هستند.

## مثال گام‌به‌گام

دسترسی محلی معتبر، IRR مجاز، حساب‌های فعال موجود و نبود خطای دیگر را فرض می‌کنیم. این‌ها مثال طراحی‌اند و اجرای عملیات مالی نیستند.

1. درخواست `credit-limit-1` مبلغ 10000000000001 ریال دارد. اعتبارسنجی عدد صحیح مثبت را می‌گذراند. coordinator پیش از ارزیابی سیاست فعلی، نتیجهٔ قبلی را جست‌وجو می‌کند. برای شناسهٔ تازه، پروتکل پذیرفته‌شده باید هویت را رزرو کند و رد نهایی سقف را همراه درخواست و پاسخ اصلی commit کند؛ journal و تغییر موجودی ندارد.
2. retry یکسان پس از افزایش فرضی سقف به 20000000000000 می‌رسد. همان رد اولیه replay می‌شود و credit موفق نمی‌سازد. سقف بزرگ‌تر فقط مثال است و تغییر تنظیمات پذیرفته‌شده نیست.
3. استفادهٔ دوباره از `credit-limit-1` با مبلغ ۱۰۰، canonical request را عوض می‌کند و تعارض هویت می‌دهد. تلاش کسب‌وکار تازه شناسهٔ تراکنش تازه می‌خواهد.
4. مشتری A موجودی 9999999999950 ریال دارد. credit تازهٔ ۱۰۰ زیر سقف عملیات است، اما موجودی را به 10000000000050 می‌رساند. زیر قفل حساب، عملیات را به‌دلیل عبور از سقف موجودی رد کنیم؛ journal و تغییر projection ندارد. credit برابر ۵۰ دقیقاً به سقف می‌رسد و این دو محدودیت را رعایت می‌کند.
5. debit برابر ۱۰۰ از مشتری با موجودی ۵۰ همچنان به‌دلیل کسری موجودی رد می‌شود، هرچند زیر سقف عملیات است. عبور از یک بررسی، بررسی‌های دیگر را حذف نمی‌کند.

مبلغ بیرون از signed-long اصلاً command نوع‌دار نمی‌شود و هویت رزرو نمی‌کند. خرابی اتصال دیتابیس خطای فنی است و تصمیم نهایی سقف نیست. status و reasonهای HTTP برای نتیجه‌های سقف هنوز پیاده‌سازی و تست قرارداد می‌خواهند؛ fallback فعلی همچنان 503 است.

## مرز تراکنش و سیاست

برای شناسهٔ موجود، canonical intent و دسترسی فعلی را بررسی کنیم و پیش از ارزیابی دوبارهٔ سقف قابل‌تغییر، نتیجهٔ نهایی ذخیره‌شده را replay کنیم. برای شناسهٔ تازه یک snapshot سازگار سیاست به کار ببریم. مبلغ و موجودی نهایی مشتری را در پروتکل مرورشدهٔ رزرو و تراکنش بررسی کنیم. بررسی موجودی نهایی به موجودی فعلی زیر قفل نیاز دارد. پیش از هر نوشتن پولی، همهٔ projectionها را آماده کنیم؛ موفقیت با journal متوازن و رد بدون journal commit شود.

canonical request فراخواننده شامل مبلغ و ارز است. سقف فعلی سیاست سرور است؛ تغییر آن نباید canonical request را عوض کند یا replay را باطل کند. شواهد سیاست را کنار تصمیم اولیه نگه داریم؛ قالب ذخیره‌سازی و نسخه‌بندی هنوز بخشی از مرور schema است. خرابی loader نباید به سقف صفر یا رد مشتری تبدیل شود.

کاهش سقف آینده به زیر موجودی حساب‌های موجود، سیاست گذار صریح می‌خواهد. این تصمیم معافیت حساب قدیمی، مسدودی حساب یا کاهش خودکار موجودی را انتخاب نمی‌کند. endpoint مدیریت سیاست یا سازوکار hot reload پیاده نشده است. معیارهای باقی‌ماندهٔ migration در [یافته‌های مرور SQL](Persistence-review.md) آمده‌اند.
