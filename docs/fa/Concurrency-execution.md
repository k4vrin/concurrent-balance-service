# شواهد هم‌زمانی عملیات با IDهای متفاوت در CBS16

[English](../en/Concurrency-execution.md) · [نیازمندی‌ها](Requirements.md) · [بازیابی retry](Retry-execution.md) · [وضعیت پیاده‌سازی](Implementation-status.md)

## مسئله را از برداشت‌های رقیب شروع کنیم

حسابی با موجودی ۱۰۰ ریال، هشت درخواست هم‌زمان برداشت ۳۰ ریالی با transaction IDهای متفاوت دریافت می‌کند. فقط سه درخواست می‌توانند موفق شوند. پنج درخواست بازنده باید تصمیم کسری وجه را نگه دارند، journal نسازند و حتی بعد از شارژ حساب همان تصمیم را replay کنند. موجودی نهایی به‌تنهایی کافی نیست؛ outcome ماندگار، history و projection باید با هم سازگار باشند.

کلاس `SqlServerDistinctConcurrencyIT` این سناریو و چهار حالت مرتبط را از HTTP واقعی تا adapterهای SQL Server بررسی می‌کند. کد مالی تولیدی، schema و تنظیمات تغییر نکرده‌اند.

## هماهنگ‌کردن attemptهای واقعی

`ConcurrentHttpBatch` به تعداد درخواست‌ها worker می‌سازد و پیش از ارسال از barrier ده‌ثانیه‌ای سمت client استفاده می‌کند. هر درخواست HTTP مهلت ۳۰ ثانیه‌ای و کل batch انتظار ۳۵ ثانیه‌ای دارد. نتیجهٔ همهٔ workerها با ترتیب ورودی جمع می‌شود و exception یا cancellation هرکدام باعث شکست تست می‌شود.

یک spy مخصوص تست روی `AccountStore`، barrier دوم را پیش از اولین فراخوانی قفل حساب در هر درخواست قرار می‌دهد. مهلت این barrier چهار ثانیه و در محدودهٔ timeout پنج‌ثانیه‌ای تراکنش است؛ همهٔ attemptهای اولیه باید به آن برسند. سپس spy خود adapter واقعی را صدا می‌زند؛ گرفتن قفل، ترتیب حساب‌ها، بررسی وجه و نوشتن دیتابیس همان مسیر تولیدی‌اند. retryهای بعدی وارد barrier نمی‌شوند. batchهای بررسی‌شده هشت یا نه درخواست دارند و در pool ده‌اتصالی فعلی جا می‌شوند. بعد از هر batch، spy reset می‌شود.

fixtureها حساب صفر را با identity محدود initializer می‌سازند. وجه اولیه با credit handler واقعی و journal متوازن ایجاد می‌شود. هر کلاس funding مستقل و هر سناریو پیشوند transaction ID یکتا دارد؛ history ماندگار تست‌های قبلی روی شمارش مورد انتظار اثر ندارد.

## سناریوها و نتیجهٔ دقیق

| سناریو | دستورهای هم‌زمان | نتیجهٔ ماندگار مورد انتظار |
| --- | --- | --- |
| credit به یک مشتری | هشت credit متفاوت ۲۵ ریالی | هشت موفقیت، مشتری ۲۰۰ ریال بیشتر، funding هم ۲۰۰ بیشتر، هشت journal و شانزده posting. |
| funding مشترک و مشتری‌های جدا | هشت credit متفاوت ۲۵ ریالی | هر مشتری ۲۵ ریال بیشتر، funding جمعاً ۲۰۰ بیشتر، هشت موفقیت/journal و شانزده posting. |
| برداشت‌های رقیب | هشت debit سی‌ریالی از مشتری با موجودی ۱۰۰ | سه موفقیت، پنج رد ماندگار، موجودی ۱۰، funding نود ریال کمتر، سه journal و شش posting. |
| انتقال‌های رقیب | هشت transfer سی‌ریالی از مبدأ با موجودی ۱۰۰ به مقصدهای صفر جداگانه | سه موفقیت و پنج رد؛ مبدأ ۱۰، مجموع مقصدها ۹۰، funding بدون تغییر، سه journal و شش posting. |
| عملیات ترکیبی | سه credit بیست‌وپنج‌ریالی، سه debit ده‌ریالی و سه transfer پانزده‌ریالی از مبدأ مشترک با موجودی ۱۰۰۰ | نه موفقیت؛ مبدأ ۱۰۰۰ می‌ماند، مقصد از ۱۰۰۰ به ۱۰۴۵ می‌رسد، funding چهل‌وپنج ریال بیشتر؛ نه journal و هجده posting. |

بررسی SQL تعداد دقیق کل عملیات، موفقیت‌ها و ردها و نبودن PENDING ماندگار را الزام می‌کند. هر عملیات موفق باید یک journal، دقیقاً دو posting و مجموع DEBIT/CREDIT برابر با محاسبات `decimal(38,0)` داشته باشد. عملیات ردشده journal یا posting ندارد.

بعد از پایان همهٔ workerها، SQL مستقل projection هر حساب را با رعایت سمت عادی حساب مشتری/funding از postingهای immutable بازسازی می‌کند. حساب بدون history باید صفر بازسازی شود. سپس همهٔ درخواست‌های اصلی هم‌زمان replay می‌شوند و باید همان status و بایت‌های پاسخ را با شمارش history بدون تغییر بدهند. بازنده‌های debit و transfer پس از شارژ ۳۰۰ ریالی replay می‌شوند؛ موجودی تازه نباید رد ماندگار را عوض کند. بعد از replay، reconciliation دوباره اجرا می‌شود.

## بررسی، ۲۰۲۶-۱۰-۲۹

اجرای کامل Java 21 با `./mvnw -o -B -ntp -Psqlserver-it verify`، تعداد **۴۲۱ تست قابل‌حمل و ۱۶۲ تست واقعی SQL Server** را با **صفر failure، error و skip** در **45.449 ثانیه** گذراند. مجموع XMLهای تازهٔ Surefire/Failsafe بررسی شد.

اجرای متمرکز اولیه، هر پنج تست تازهٔ integration را در کنار ۴۲۱ تست قابل‌حمل، در 17.931 ثانیه گذراند. regression نهایی شامل بررسی‌های اضافهٔ reconciliation بعد از replay هم‌زمان است. هر دو type تازه از Javadoc/doclint گذشتند. اسکن syntax tree با compiler، همهٔ ۱۴۷ فایل Java را بررسی کرد و هیچ type تودرتو، local یا anonymous پیدا نکرد. لینک‌های اسناد، whitespace و اسکن مقادیر دقیق credential در logها/reportها هم موفق بودند.

## محدودیت‌ها و کار بعدی

این تست‌ها یک instance برنامه با تراکنش‌های هم‌زمان جداگانه و دیتابیس اختصاصی موجود `cbs_test` را بررسی می‌کنند. barrierها ورود هم‌پوشان به مرحلهٔ قفل را برقرار می‌کنند، اما همهٔ interleavingهای scheduler/دیتابیس یا throughput را ثابت نمی‌کنند. reconciliation بعد از پایان نویسنده‌هاست، نه هنگام تغییر دلخواه history به‌صورت هم‌زمان.

رقابت transaction ID یکسان/متعارض بین instanceها، انتقال‌های معکوس، پیشرفت حساب مستقل هنگام قفل‌بودن حساب دیگر و faultهای بیشتر پاسخ/commit در CBS17–19 می‌مانند. شبیه‌سازی ARM64 محلی SQL Server خارج از پشتیبانی Microsoft است. این نتیجه پذیرش مستقل یادگیری یا آمادگی production نیست. این checkpoint شامل تست‌های هم‌زمانی عملیات با ID متفاوت در CBS16 و راهنماهای هر دو زبان است؛ CBS15 جداگانه با `6f6cc61` commit و push شده است.
