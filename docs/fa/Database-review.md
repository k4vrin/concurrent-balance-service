> به‌روزرسانی bootstrap در ۲۰ اکتبر ۲۰۲۶: SQL Server جای هدف پیشنهادی قبلی Oracle را گرفته است. P0 شروع شده و کامل نیست. وجود وابستگی‌ها و موفقیت تست سلامت، صحت مالی را ثابت نمی‌کنند.

# مرور صحت دیتابیس و هزینهٔ آن

وضعیت: پیشنهاد برای مرور پیش از schema. DDL اجرا نشده و اندازه‌گیری انجام نشده است. [English](../en/Database-review.md) · [تصمیم‌ها](Decisions.md)

## مسئله: چه چیزی را به دیتابیس می‌سپاریم؟

برای مثال، `CHECK` می‌تواند مبلغ یک ردیف را مثبت نگه دارد، اما جمع posting‌های چند ردیف را متوازن نمی‌کند. پیش از migration باید مشخص کنیم کدام invariant را constraint حفظ می‌کند و کدام به پروتکل تراکنش نیاز دارد. درصد overhead را هم باید اندازه بگیریم.

گزینهٔ E با `accounts`، `operations`، `journals` و `postings` شروع می‌شود؛ [طراحی دفترکل](Ledger.md) و [ADR-007](../adr/ADR-007-double-entry-ledger.fa.md) مرجع‌اند. بعداً `transfer_intents`، `outbox_events`، `processed_events` و `transaction_history` اضافه می‌شوند و نام‌ها فعلاً پیشنهادی‌اند.

هر operation یک credit، debit یا transfer کامل و نتیجهٔ ماندگارش است. ID داخلی ردیف با transaction ID کلاینت فرق دارد.

### تصمیم‌های لازم پیش از V1

- نسخه و image مربوط به SQL Server و مرز portability؛
- نوع شناسه، واحد و ارز و مرجع initialization حساب؛
- دامنهٔ یکتایی شناسه، سقف مبلغ و ثبت rejection؛
- retention، بستن یا حذف حساب؛
- نوع حساب و جزئیات posting.

double-entry از V1 پذیرفته شده، اما schema هنوز مرور می‌خواهد. سیاست retention در ۲۰۲۶-۱۰-۲۳ پذیرفته شده است؛ جزئیات storage و اجرای آن همچنان باید مرور شوند. تصمیم‌ها را قبل از migration ثبت کنید.

### null و مقایسهٔ شناسه

`CHECK` با نتیجهٔ `UNKNOWN` ممکن است `null` را بپذیرد. فیلد اجباری باید `NOT NULL` داشته باشد و شرط شکل عملیات روشن باشد.

collation و trailing space در SQL Server می‌توانند هویت رشته‌ای را تغییر دهند. قواعد مقایسهٔ transaction ID باید صریح و تست‌شده باشند. شناسهٔ خالی را در برنامه رد کنید.

### مبلغ و مرز اعتبارسنجی

در V1 هر واحد یک ریال است. مبلغ و موجودی با `BIGINT` متناظر `long` ذخیره می‌شوند و شرط مبلغ مثبت و موجودی متناسب با نوع حساب لازم است. ورودی را پیش از conversion بررسی کنید؛ coercion دیتابیس جای API validation نیست.

### invariant‌های چندردیفی

`CHECK` معمولی یک ردیف را می‌بیند. انتقال دوحسابی، مالکیت در جدول دیگر یا جمع posting‌ها را «تضمین‌شده با CHECK» معرفی نکنید.

ADR-007 double-entry را الزامی کرده است. journal متوازن، persistence تراکنشی، writer محدود و reconciliation مستقل با projection لازم‌اند.

## مرور index

برای هر index این اطلاعات را ثبت کنید:

| موضوع | اطلاعات لازم |
| --- | --- |
| مصرف | query دقیق و مرحله |
| دسترسی | equality و range predicate، sort، توزیع داده و ترتیب ستون‌ها |
| ساختار موجود | index‌های PK و UNIQUE |
| هزینه | نرخ نوشتن و فضای ذخیره‌سازی |
| شاهد | لینک actual plan یا benchmark |

کنار unique index شناسهٔ تراکنش، index هم‌معنی نسازید. نیاز FK به index را با update و delete واقعی parent و concurrency بررسی کنید. ساخت خودکار index برای تمام FK‌ها را فرض نکنید.

### نامزدهای بررسی

- lookup و lock حساب با PK؛
- lookup یکتای transaction ID؛
- تاریخچهٔ owner یا account با keyset pagination؛
- outbox منتظر بر اساس status و next-attempt؛
- هویت event در consumer؛
- یکتایی intent اجراشده.

همهٔ این‌ها نیاز V1 نیستند. status-only index ممکن است selectivity کمی داشته باشد. history index در هر insert هزینه دارد و outbox status index هنگام تغییر status هم update می‌شود.

## اندازه‌گیری هزینه

### محیط آزمایش

از schema قابل‌حذف و دادهٔ مصنوعی استفاده کنید. constraint‌های صحت در schema قابل‌تحویل باقی می‌مانند. برای مقایسهٔ variant‌ها، تغییر index و plan و fixture بازتولیدپذیر را ثبت کنید.

مثلاً حذف `UNIQUE` هم کنترل صحت و هم index پشتیبان را عوض می‌کند. تمام تفاوت را به هزینهٔ `CHECK` نسبت ندهید.

### مقایسهٔ منصفانه

سخت‌افزار، نسخه، حجم و توزیع داده، request mix، durability، connection pool، concurrency و statistics باید قابل‌مقایسه باشند. warmup و چند تکرار انجام دهید و پراکندگی را گزارش کنید.

حساب‌های مستقل و hot account را جدا بسنجید. درخواست‌های یکتا و duplicate-heavy هم آزمایش جدا می‌خواهند. lock wait را با هزینهٔ ارزیابی هر ردیف مخلوط نکنید.

### معیارها

- تعداد عملیات مالی commit‌شده در ثانیه؛
- latency انتهابه‌انتها در p50 و p95 و p99؛
- نرخ rejection و خرابی؛
- CPU دیتابیس، logical reads و log bytes هر عملیات؛
- lock wait، pool wait و اندازهٔ index.

حجم کار موفق برابر را مقایسه کنید؛ رد بیشتر درخواست‌ها نباید سرعت بیشتر گزارش شود. فرمول `overhead_pct = (variant_latency - baseline_latency) / baseline_latency * 100` فقط برای latency قابل‌مقایسه و همراه تعداد نمونه و پراکندگی معتبر است. تغییر throughput معیار جداست.

### قالب گزارش

1. شناسهٔ آزمایش، تاریخ و commit، invariant و variant‌ها؛
2. تفاوت SQL و DDL، workload ثابت، سخت‌افزار و نسخه؛
3. warmup، تعداد تکرار، نتایج خام و درصد همراه پراکندگی؛
4. نتیجهٔ صحت، عوامل مخدوش‌کننده، تصمیم و مسیر شواهد.

وضعیت فعلی همهٔ معیارها «اندازه‌گیری نشده» است. هدف عددی بعد از baseline و مشخص‌شدن محیط کاربر تعیین می‌شود.

منابع: [SQL Server constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints) و [optimizer statistics](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics). با نسخهٔ ثابت پروژه دوباره تطبیق داده شوند.

## چک‌لیست چهارجدولی گزینهٔ E

- `journals.operation_id` اجباری و یکتا باشد. موفقیت commit‌شده دقیقاً یک سند کامل و رد درخواست هیچ سندی ندارد. عملیات افتتاحیه نیز این پروتکل چندردیفی را رعایت کند.
- هر posting باید foreign key حساب و سند، مبلغ مثبت از نوع `BIGINT`، سمت `DEBIT` یا `CREDIT` و ارجاع سازگار با ارز داشته باشد. کلید مرکب یا حفاظت معادل برای ارز مرور شود. حذف آبشاری تاریخچه ممنوع است.
- هر سند باید دست‌کم دو سطر، هر دو سمت بدهکار و بستانکار و جمع برابر به‌ازای ارز داشته باشد. این قواعد با `CHECK` ردیفی تضمین نمی‌شوند. نویسندگان جایگزین داده محدود شوند و مسیر ثبت و تلاش برای تغییر یا حذف تاریخچه تست شوند.
- projection بدهی مشتری باید غیرمنفی باشد. حساب تأمین مصنوعی از سیاست علامت‌دار خودش پیروی می‌کند. overflow تمام موجودی‌های حاصل باید پیش از اعمال تغییر مبلغ کنترل شود.
- افتتاحیه با عملیات، سند و posting داخلی ثبت شود. تمام projection‌ها از تاریخچهٔ کامل، با دید سازگار از دادهٔ commit‌شده و accumulator دقیق بزرگ‌تر بازسازی شوند. خرابی عمدی فقط در تست ایزوله تزریق و به‌طور مستقل کشف شود.
- مسیر دسترسی به ثبت‌ها بر اساس حساب و هویت پایدار سند و سطر، جست‌وجوی یکتای سند با شناسهٔ عملیات، index foreign key، اتصال‌های تطبیق و مجوز صرفاً افزودن یا append-only مرور شوند. پیش از افزودن index بیشتر، هزینهٔ فضا، لاگ، مدت قفل و حساب تأمین مشترک اندازه‌گیری شود.

ارجاع درخواست با posting متفاوت است: شناسهٔ حساب درخواستی در operations باید برای رد نهایی حساب ناموجود هم قابل‌ثبت باشد؛ بنابراین foreign key اجباری حساب ندارد. posting با foreign key اجباری به حساب واقعی ارجاع می‌دهد و حذف آبشاری تاریخچهٔ حسابداری مجاز نیست.
