# مرور صحت دیتابیس و هزینهٔ آن

وضعیت: پیشنهاد پیش از schema؛ DDL اجرا نشده و اندازه‌گیری نداریم. [English](../en/Database-review.md) · [تصمیم‌ها](Decisions.md)

## مرور قبل از migration اول

گزینهٔ E از چهار جدول مفهومی `accounts`، `operations`، `journals` و `postings` شروع می‌کند؛ [Ledger.md](Ledger.md) و [ADR-007](../adr/ADR-007-double-entry-ledger.fa.md) مرجع‌اند. مراحل بعد `transfer_intents`، `outbox_events`، `processed_events` و `transaction_history` را اضافه می‌کنند. نام‌ها پیشنهادی‌اند. یک operation، credit یا debit یا انتقال کامل و نتیجهٔ ماندگار آن را نشان می‌دهد. شناسهٔ داخلی ردیف با transaction ID کاربر متفاوت است.

پیش از V1 تعیین شود: نسخه/image SQL Server و مرز portability، نوع شناسه، واحد و ارز، مرجع مقداردهی حساب، دامنهٔ یکتایی شناسه، حداکثر مقدار، ثبت رد درخواست، retention، بستن/حذف حساب و جزئیات posting و نوع حساب. دفترکل دوطرفه از V1 پذیرفته شده ولی schema هنوز مرور لازم دارد. تصمیم‌ها قبل از migration ثبت شوند.

CHECK با نتیجهٔ unknown ممکن است null را بپذیرد؛ فیلد اجباری NOT NULL و شرط شکل عملیات روشن داشته باشد. collation و مقایسهٔ فاصلهٔ انتهایی SQL Server می‌توانند بر هویت رشته‌ای اثر بگذارند. قواعد مقایسهٔ transaction ID صریح و آزموده و شناسهٔ خالی در برنامه رد شود. برای واحد پول صحیح از `BIGINT` متناظر long و CHECK مبلغ مثبت و سیاست موجودی وابسته به نوع حساب استفاده شود. ورودی قبل از تبدیل کنترل شود؛ coercion دیتابیس قرارداد اعتبارسنجی API نیست.

CHECK معمولی یک ردیف، انتقال دوحسابی، مالکیت در جدول دیگر یا جمع postingها را کنترل نمی‌کند. چنین قواعدی نباید «تضمین‌شده با CHECK» معرفی شوند. double-entry طبق ADR-007 الزامی است؛ ساخت متوازن، ثبت تراکنشی، محدودیت writer و reconciliation با موجودی cached لازم است.

## مرور index

برای هر index ثبت شود: query و مرحله، predicate مساوی/بازه/مرتب‌سازی، توزیع داده، ترتیب ستون، indexهای PK/UNIQUE موجود، نرخ نوشتن، فضا و لینک پلن/benchmark. index اضافی هم‌معنی با unique transaction ID نسازیم. نیاز index برای FK با رفتار واقعی حذف/تغییر parent و هم‌زمانی بررسی شود؛ ساخت خودکار index برای همهٔ FKها فرض نشود.

نامزدها: PK حساب و قفل آن، lookup یکتای transaction ID، تاریخچهٔ مالک/حساب با keyset، outbox منتظر بر اساس وضعیت و زمان تلاش، هویت event مصرف‌کننده و یکتایی intent اجراشده. همهٔ این‌ها نیاز V1 نیستند. index تنها روی status ممکن است selectivity ضعیف داشته باشد. index تاریخچه برای هر insert هزینه دارد و index وضعیت outbox هنگام تغییر status هم نگهداری می‌شود.

## اندازه‌گیری هزینه

از schema آزمایشی قابل‌حذف و دادهٔ مصنوعی استفاده شود؛ constraintهای صحت در schema قابل‌تحویل باقی بمانند. مقایسهٔ variantها در محیط آزمایش، تغییر index و پلن همراه و fixture بازتولیدپذیر ثبت شود. حذف UNIQUE هم کنترل صحت و هم index پشتیبان را تغییر می‌دهد؛ همهٔ اختلاف را به CHECK نسبت ندهیم.

سخت‌افزار، نسخه، حجم و توزیع داده، ترکیب درخواست، durability، connection pool، concurrency و statistics قابل‌مقایسه باشند. warmup و چند تکرار با گزارش پراکندگی انجام شود. حساب‌های مستقل و hot account جدا، و درخواست یکتا و duplicate-heavy نیز جدا سنجیده شوند. اختلاف انتظار قفل با هزینهٔ ارزیابی ردیف مخلوط نشود.

عملیات مالی commitشده در ثانیه، p50/p95/p99 انتهابه‌انتها، نرخ رد و خرابی، CPU دیتابیس، logical reads، log bytes هر عملیات، lock wait، pool wait و اندازهٔ index ثبت شوند. حجم کار موفق برابر مقایسه شود؛ رد بیشتر درخواست‌ها نباید به‌عنوان سرعت بیشتر گزارش شود. فرمول `overhead_pct = (variant_latency - baseline_latency) / baseline_latency * 100` فقط روی latency قابل‌مقایسه با تعداد نمونه و پراکندگی استفاده شود. تغییر throughput معیار جداست.

قالب گزارش: شناسهٔ آزمایش، تاریخ/commit، invariant، variantها، تفاوت SQL/DDL، workload ثابت، سخت‌افزار/نسخه، warmup/تکرار، نتیجهٔ خام، درصد همراه پراکندگی، نتیجهٔ صحت، عوامل مخدوش‌کننده، تصمیم و مسیر شواهد. نتیجهٔ فعلی همهٔ موارد: **اندازه‌گیری نشده**. هدف عددی بعد از baseline و تعیین محیط کاربر مشخص شود.

منابع: [SQL Server constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints) و [optimizer statistics](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics). با نسخهٔ ثابت پروژه دوباره تطبیق داده شوند.

## چک‌لیست چهارجدولی گزینهٔ E

- `journals.operation_id` اجباری و یکتا باشد. موفقیت commitشده دقیقاً یک سند کامل و رد درخواست هیچ سندی ندارد. عملیات افتتاحیه نیز این پروتکل چندردیفی را رعایت کند.
- posting دارای FK حساب و سند، مبلغ مثبت BIGINT، سمت DEBIT/CREDIT و ارجاع سازگار با ارز باشد. کلید مرکب یا حفاظت معادل برای ارز مرور شود. حذف آبشاری تاریخچه ممنوع است.
- هر سند دست‌کم دو سطر، هر دو سمت و جمع برابر به‌ازای ارز دارد. این قواعد CHECK ردیفی نیستند. writer جایگزین محدود و مسیر ثبت و تلاش برای تغییر/حذف تاریخچه آزموده شوند.
- projection بدهی مشتری غیرمنفی و حساب تأمین مصنوعی مطابق سیاست علامت‌دار خود باشد. overflow تمام موجودی‌های حاصل پیش از اعمال delta کنترل شود.
- افتتاحیه با operation و journal و posting داخلی ثبت شود. تمام projectionها از تاریخچهٔ کامل با دید commitشدهٔ سازگار و accumulator دقیق بزرگ‌تر بازسازی شوند. فساد عمدی فقط در تست ایزوله تزریق و مستقل کشف شود.
- دسترسی posting بر اساس حساب و هویت پایدار سند/سطر، lookup یکتای عملیات به سند، index FK، join تطبیق و مجوز append-only مرور شوند. هزینهٔ فضا، log، مدت قفل و حساب تأمین مشترک پیش از index بیشتر اندازه‌گیری شود.
