# دفتر تصمیم‌های معماری

وضعیت تمام موارد: Proposed. پذیرش یا پیاده‌سازی ادعا نمی‌شود. تاریخ: ۲۰ اکتبر ۲۰۲۶. [English](../en/Decisions.md)

تصمیم تنظیمات جداست: [ADR-006](../adr/ADR-006-default-sqlserver.fa.md) حذف پذیرفته‌شدهٔ profileهای Maven/Spring مربوط به SQL Server در ۲۰۲۶-۱۰-۲۲ را ثبت می‌کند. تصمیم‌های مالی زیر همچنان پیشنهادی‌اند.

## ADR-001: مرز ماندگار صحت

اصلاح دامنه در ۲۰۲۶-۱۰-۲۲: V1 یک HTTP API برای هر چهار عملیات با مسیرهای کامل تا SQL Server است. [API-v1.md](API-v1.md) جای ترتیب تحویل صرفاً سرویس را می‌گیرد. امضاهای جاوای داخلی قابل تغییرند. HTTP مرز تراکنش محلی دیتابیس را تغییر نمی‌دهد. دسترسی اولیه محلی و مورداعتماد است؛ P3 پیش از استفادهٔ اشتراکی/خارجی معیار احراز هویت و مجوز باقی می‌ماند. این انتخاب دامنه به معنی پذیرش ADRهای مالی یا پیاده‌سازی نیست.

زمینه: حرکت پول، retry و سامانه‌های خارجی آینده باید در خرابی سازگار بمانند. پیشنهاد: سرویس ماژولار Spring Boot با SQL Server به‌عنوان مرجع مالی، Java 21، Maven wrapper، Flyway و تست روی SQL Server واقعی. SQL Server پس از گفت‌وگو هدف persistence این اسکلت انتخاب شده است. نسخه و edition سرور و سازگاری JDBC/Flyway قبل از پذیرش schema بررسی شوند.

تغییر حساب، هویت و نتیجهٔ ماندگار عملیات و در آینده outbox در یک تراکنش دیتابیس commit شوند. حساب‌های درگیر با ترتیب ثابت قفل شوند. لحظهٔ قابل‌مشاهده‌شدن نتیجهٔ commitشده مشخص باشد. قفل سراسری سرویس نداشته باشیم. انتظار قفل محدود و خطای کسب‌وکار از خطای موقت زیرساخت جدا باشد. خواندن یک حساب دادهٔ commitشده می‌دهد؛ چند خواندن جدا، snapshot مشترک تضمین نمی‌کند.

گزینه‌ها: حافظهٔ محلی ماندگاری restart ندارد؛ optimistic locking به retry محدود کل تراکنش نیاز دارد؛ SQL شرطی نیازمند پروتکل دوحسابی است. قفل Redis مرز خرابی و lease اضافه می‌کند و جای صحت دیتابیس را نمی‌گیرد. هزینه‌ها: رقابت حساب، انتظار قفل، اتصال، transaction log/version store و رشد جدول عملیات. شواهد پذیرش: تست SQL مستقیم، درخواست هم‌زمان، انتقال دوطرفه و rollback پیش از commit.

## ADR-002: Idempotency، کاربر و Redis

زمینه: کاربر شناسهٔ درخواست را تعیین می‌کند؛ شناسهٔ جدید می‌تواند یک فرمان مجاز جدید باشد. Idempotency نیت کاربر را تشخیص نمی‌دهد و جای مجوز، محدودیت یا تأیید انتقال را نمی‌گیرد.

پیشنهاد: transaction ID در نسخهٔ تک‌مستأجر میان credit/debit/transfer یکتا باشد. fingerprint استاندارد، actor و نتیجهٔ نهایی همراه حرکت پول ثبت شوند. در P4 یکتایی مستقل روی intent اجراشده مانع اجرای دوبارهٔ همان intent با شناسه‌های متفاوت می‌شود. درخواست یکسان نتیجهٔ قبلی را می‌گیرد و محتوای متفاوت conflict است. پیش از replay احراز هویت و دسترسی فعلی بررسی شود و نتیجهٔ کاربر دیگر افشا نشود.

سیاست پیشنهادی رد درخواست: درخواست معتبر و مجاز که به دلیل کسب‌وکار رد می‌شود، نتیجهٔ نهایی بدون تغییر موجودی ثبت کند. retry همان شناسه حتی بعد از تغییر موجودی همان رد را برگرداند. خطای ساختار، احراز هویت و دسترسی رکورد مالی نمی‌سازد. خطای فنی قبل از commit موفقیت نهایی نمی‌سازد و retry از هویت دیتابیس بازیابی می‌شود. خطای موقت نباید بی‌صدا به رد دائمی تبدیل شود.

Redis فقط کپی پاسخ نهایی تغییرناپذیر را با کلید محیط و transaction ID، fingerprint و نسخهٔ schema ذخیره کند. miss، انقضا، خرابی محتوا، mismatch یا قطعی به دیتابیس مراجعه کند؛ نبود کلید مجوز debit نیست. cache فقط از نتیجهٔ commitشده پر شود. مسیر hit نیز کنترل دسترسی فعلی دارد. قبل از مجازشدن اصلاح نتایج نهایی، نسخه‌بندی و invalidation لازم است. هویت یا tombstone ماندگار از TTL Redis طولانی‌تر بماند؛ حذف آن ضمانت retry را تغییر می‌دهد و ADR لازم دارد. بهبود کارایی تا اندازه‌گیری ادعا نمی‌شود.

Redis-only شکاف commit میان دو سامانه دارد. lease می‌تواند به کاهش رقابت کمک کند ولی مرجع ایمنی نیست. هزینه‌ها: حافظه، serialization، شبکه، نسخهٔ محتوا و وابستگی جدید. معیار پذیرش: پاک‌کردن Redis بعد از commit، crash پیش از cache، درخواست تکراری روی دو instance و حمله به مالکیت نباید حرکت مالی دوم بسازند.

## ADR-003: constraint پیش از schema

پیشنهاد: [Database-review.md](Database-review.md) پیش از V1 مرور شود. برای هر invariant قاعدهٔ تراکنش، حفاظت دیتابیس، تست رقابت/حمله و آزمایش هزینه مشخص شود. مثبت‌بودن مبلغ، منفی‌نشدن موجودی، ارجاع اجباری و یکتایی هویت حفظ شوند؛ قبل از تضعیف invariant مالی، گلوگاه بررسی شود.

CHECK معمولی یک ردیف، صحت کامل انتقال دو حساب یا جمع postingها را تضمین نمی‌کند. قواعد چندردیفی با مسیر تراکنشی، مجوز و reconciliation حفظ می‌شوند. تاریخچهٔ double-entry توسعهٔ پیشنهادی schema است و نباید هستهٔ چهارعملیاتی را عقب بیندازد. در صورت اضافه‌شدن، حساب تأمین/تسویه برای credit/debit و ممنوعیت تغییر موجودی خارج از مسیر حسابرسی تعریف شود. درصد هزینه هنوز معلوم نیست.

## ADR-004: تأیید وابسته به تراکنش

زمینه: جلوگیری از retry ثابت نمی‌کند مالک حساب همین گیرنده و مبلغ را تأیید کرده است. بعد از P3، intent تغییرناپذیر با actor، مبدأ، مقصد، مبلغ، ارز، انقضا و شناسهٔ سرور ساخته شود. جزئیات مهم پیش از تأیید نمایش داده شوند. هر تغییر نیازمند intent و کد جدید است. ساخت intent پول رزرو نمی‌کند.

endpointهای پیشنهادی: `POST /transfer-intents`، `POST /transfer-intents/{id}/challenge`، `POST /transfer-intents/{id}/confirm` و `GET /transfer-intents/{id}`. صدور و ارسال مجدد محدود و در صورت نیاز idempotent باشند؛ ارسال مجدد نسل قبلی کد را باطل کند. تأیید، transaction ID و کد می‌گیرد و دادهٔ مالی را از intent می‌خواند. مسیر عمومی دیگری نباید تأیید را دور بزند. credit/debit همچنان نقش مجاز می‌خواهند.

کد تصادفی امن و کوتاه‌عمر با HMAC و راز خارج از دیتابیس نگهداری شود. hash سادهٔ کد عددی کوتاه در برابر حدس آفلاین کافی نیست. مقایسهٔ ثابت‌زمان، سقف تلاش و محدودیت ارسال لازم است؛ مقدار نهایی سیاست‌ها و کانال ارسال در مرور امنیتی تعیین شود. کد واقعی در production لاگ یا در پاسخ API نمایش داده نشود. ابتدا adapter ارسال fake فقط برای تست/محلی باشد؛ این اثبات عامل دوم واقعی یا مقاومت در برابر phishing نیست.

تمام مسیرهای تأیید ابتدا intent و بعد حساب‌ها را با ترتیب ثابت قفل کنند. actor، fingerprint، وضعیت، انقضا و کد بررسی شوند. مصرف کد معتبر، تکمیل intent، انتقال، ارجاع یکتای intent، نتیجهٔ عملیات و در آینده outbox با هم commit شوند. تأیید هم‌زمان با transaction ID متفاوت نیز intent را فقط یک‌بار اجرا کند. ارسال شبکه‌ای داخل قفل مالی نباشد. شمارندهٔ تلاش نامعتبر باید با وجود پاسخ خطا commit شود؛ پرتاب exception نباید افزایش شمارنده را rollback کند. resend، شمارش تلاش و تأیید روی intent هماهنگ باشند. رد کسب‌وکار بعد از کد معتبر در این پیشنهاد نهایی است و intent را مصرف می‌کند؛ تلاش مالی جدید intent جدید می‌خواهد.

برای intent تکمیل‌شده، بعد از احراز هویت و کنترل مالکیت، هویت و fingerprint عملیات اصلی تطبیق داده شود و نتیجهٔ قبلی بدون OTP تازه بازگردد. این مسیر فقط بازیابی است و فرمان جدید اجرا نمی‌کند. endpoint وضعیت، بازیابی در صورت گم‌شدن transaction ID را ممکن می‌کند.

هزینه‌ها: رفت‌وبرگشت بیشتر، state، قابلیت اتکای ارسال، کنترل سوءاستفاده و پیچیدگی خطا. تست‌ها: کد متعلق به دیگری، تغییر مقصد، انقضا، رقابت resend، ثبت تلاش، تأیید دوگانه، rollback، پاسخ گمشده، replay غیرمجاز و bypass. مبنا: [OWASP transaction authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html).

## ADR-005: رویداد پیش از CDC

پیشنهاد: رویداد دارای نسخه و event ID ثابت، همراه عملیات موفق در outbox ثبت شود. publisher مبتنی بر polling بعد از تأیید broker پیشرفت را ثبت کند. crash بین تأیید و ثبت می‌تواند پیام تکراری بسازد. consumer تاریخچه، شناسهٔ مصرف‌شده و اثر تاریخچه را در تراکنش دیتابیس خود ثبت کند و سپس offset commit شود. تراکنش Kafka به‌تنهایی دیتابیس خارجی را اتمیک نمی‌کند.

رویداد، واقعیت commitشده است و نباید موجودی را دوباره جابه‌جا کند. تاریخچهٔ اولیه بر پایهٔ operation ID باشد؛ ترتیب تمام عملیات یک حساب با این کلید تضمین نمی‌شود. projection موجودی آینده به نسخهٔ هر حساب، ترتیب و reconciliation نیاز دارد. retry، backoff، dead letter و بازیابی تعریف شوند؛ شواهد مالی بی‌صدا کنار گذاشته نشوند.

در P7، Debezium روی insertهای outbox بررسی شود. نسخه و edition واقعی SQL Server، connector و capture adapter، مجوز، CDC بومی، Agent/capture job و retention جدول تغییرات، بازیابی snapshot، نگهداری offset و schema history و در صورت کاربرد licensing ثبت شوند. سازگاری با image محلی فرض نشود. هنگام cutover، polling متوقف و مرز انتشار روشن باشد؛ dedup مصرف‌کننده برای هم‌پوشانی و بازیابی لازم می‌ماند. polling مسیر جایگزین است. شواهد: قطعی broker، duplicate، restart و replay. منابع: [Kafka](https://kafka.apache.org/41/design/design/#message-delivery-semantics) و [Debezium](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html).

## چرخه و قالب ADR

شناسه ثابت باشد. Proposed فقط پس از مرور گزینه‌ها و شواهد لازم مرحله به Accepted تبدیل شود. Accepted به معنی پیاده‌سازی نیست. commit پیاده‌سازی، نتیجهٔ اندازه‌گیری، تاریخ و محدودیت جدا ثبت شوند. تصمیم جدید با لینک، قدیمی را Superseded کند. هر دو زبان در همان PR اصلاح شوند.

قالب هر ADR: شناسه/عنوان، وضعیت/تاریخ/مسئول، زمینه و محدودیت، invariant یا تهدید، گزینه‌ها، مرز منتخب، تراکنش/قفل/خرابی، فرض هزینه، روش اندازه‌گیری و baseline، نتیجه یا «اندازه‌گیری نشده»، تست پذیرش، rollback/migration، لینک PR و schema و دو زبان. مجهول‌ها صریح بمانند.
