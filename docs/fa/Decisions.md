> به‌روزرسانی bootstrap در ۲۰ اکتبر ۲۰۲۶: SQL Server جای هدف پیشنهادی قبلی Oracle را گرفته است. P0 شروع شده و کامل نیست. وجود وابستگی‌ها و موفقیت تست سلامت، صحت مالی را ثابت نمی‌کنند.

# دفتر تصمیم‌های معماری

وضعیت: پروتکل‌های ADR-001–005 هنوز پیشنهادی‌اند، به‌جز سیاست رد نهایی که در ۲۰۲۶-۱۰-۲۲ پذیرفته شد. ADR-007 هم در همان تاریخ طراحی دفترکل V1 را پذیرفت. کد و شواهد مالی هنوز نداریم.

تاریخ اولیهٔ این دفتر ۲۰ اکتبر ۲۰۲۶ است. [English](../en/Decisions.md)

دو تصمیم جدا را هنگام خواندن متن در نظر بگیرید:

- [ADR-006](../adr/ADR-006-default-sqlserver.fa.md) در ۲۰۲۶-۱۰-۲۲ profile‌های Maven و Spring مربوط به SQL Server را حذف کرد.
- [ADR-007](../adr/ADR-007-double-entry-ledger.fa.md) گزینهٔ E را پذیرفت و اختیاری‌بودن دفترکل در ADR-003 را جایگزین کرد.

جزئیات پروتکل‌های مالی زیر همچنان به مرور نیاز دارند.

## ADR-001: مرز تضمین صحت و ماندگاری

### دامنهٔ تحویل

اصلاح ۲۰۲۶-۱۰-۲۲: V1 هر چهار عملیات را از HTTP تا SQL Server پیاده می‌کند. [قرارداد API](API-v1.md) جای ترتیب تحویل صرفاً مبتنی بر سرویس را می‌گیرد و امضاهای داخلی جاوا می‌توانند تغییر کنند.

HTTP مرز تراکنش محلی را عوض نمی‌کند. دسترسی اولیه محلی و مورداعتماد است؛ P3 پیش از دسترسی اشتراکی یا خارجی، احراز هویت و مجوز را اضافه می‌کند. این انتخاب دامنه، پذیرش پروتکل مالی یا پیاده‌سازی آن نیست.

### مسئله و پیشنهاد

اگر برنامه بین نوشتن موجودی و ثبت نتیجه متوقف شود، پول و پاسخ عملیات نباید دو وضعیت ناسازگار داشته باشند. پیشنهاد، سرویس ماژولار Spring Boot با SQL Server به‌عنوان مرجع مالی، Java 21، Maven wrapper، Flyway و تست SQL Server واقعی است. SQL Server هدف منتخب bootstrap است.

پیش از پذیرش رفتار schema، نسخه و edition سرور را pin و سازگاری JDBC و Flyway را بررسی کنید.

### مرز commit

این داده‌ها در یک تراکنش محلی commit می‌شوند:

- projection حساب‌ها، یعنی موجودی ذخیره‌شده؛
- هویت و نتیجهٔ عملیات؛
- یک journal متوازن و posting‌های تغییرناپذیر آن؛
- outbox در مرحلهٔ آینده.

تمام حساب‌های مشتری و سیستمی را با یک lock order ثابت قفل کنید. نقطه‌ای که نتیجهٔ commit‌شده قابل‌مشاهده می‌شود باید روشن باشد. global service lock نداریم و lock wait باید محدود باشد.

رد کسب‌وکار را از خرابی موقت زیرساخت جدا کنید. خواندن یک حساب دادهٔ commit‌شده می‌دهد؛ چند خواندن جدا، snapshot مشترک را تضمین نمی‌کنند.

### گزینه‌ها و هزینه‌ها

| گزینه | محدودیت |
| --- | --- |
| حافظهٔ محلی | بعد از restart ماندگار نیست |
| optimistic locking | به retry محدودِ کل تراکنش نیاز دارد |
| SQL شرطی | پروتکل صریح دوحسابی می‌خواهد |
| Redis lock | lease و مرز خرابی تازه اضافه می‌کند و جای صحت دیتابیس را نمی‌گیرد |

هزینه‌ها شامل contention حساب، lock wait، مصرف connection، transaction log، version store و رشد جدول عملیات‌اند. پذیرش به تست مستقیم SQL، درخواست هم‌زمان، انتقال‌های خلاف جهت و rollback پیش از commit نیاز دارد.

## ADR-002: Idempotency، کاربر و Redis

[پیش‌نویس CBS03](Idempotency-protocol.md) مسیر رزرو، canonical command، concurrency، replay و recovery را برای مرور مشترک توضیح می‌دهد. این پیش‌نویس وضعیت ADR را به پذیرفته‌شده تغییر نمی‌دهد.

### تهدید و مرز مسئولیت

کلاینت شناسه را انتخاب می‌کند؛ شناسهٔ تازه می‌تواند یک فرمان مجاز تازه باشد. برای مثال، دو شناسهٔ متفاوت برای مبلغ و گیرندهٔ یکسان لزوماً retry نیستند. Idempotency نیت کاربر را تشخیص نمی‌دهد و جای مجوز، سقف یا تأیید انتقال را نمی‌گیرد.

### هویت ماندگار

پیشنهاد، شناسهٔ یکتای سراسری میان `credit`، `debit` و `transfer` در سرویس تک‌مستأجر است. canonical fingerprint، ارتباط با actor احرازشده و نتیجهٔ نهایی همراه تغییر مالی ذخیره می‌شوند. در P4 یکتایی مستقل intent اجراشده جلوی اجرای دوبارهٔ همان intent با شناسه‌های متفاوت را می‌گیرد.

درخواست یکسان پاسخ اصلی می‌گیرد و payload متفاوت conflict. پیش از replay، احراز هویت و مجوز فعلی را بررسی کنید. اگر مالکیت روشن نیست، نتیجهٔ actor دیگر را افشا نکنید.

### رد نهایی، سیاست پذیرفته‌شدهٔ ۲۰۲۶-۱۰-۲۲

درخواست معتبر و مجازی که به دلیل کسب‌وکار رد می‌شود، نتیجهٔ نهایی ماندگار دارد. موجودی تغییر نمی‌کند و journal یا posting نداریم. retry همان شناسه، حتی بعد از تغییر موجودی، همان رد را برمی‌گرداند.

خطای ساختار، احراز هویت یا مجوز، رکورد عملیات مالی نمی‌سازد. خرابی فنی پیش از commit نتیجهٔ نهایی ثبت نمی‌کند و retry از مسیر هویت دیتابیس بازیابی می‌شود. خطای موقت را بی‌صدا به رد دائمی تبدیل نکنید.

### Redis فقط cache پاسخ است

نسخهٔ تغییرناپذیر پاسخ نهایی با کلید محیط و شناسهٔ تراکنش، fingerprint و نسخهٔ schema ذخیره می‌شود. miss، expiry، محتوای خراب، mismatch یا قطعی Redis به دیتابیس برمی‌گردند. نبود کلید اجازهٔ برداشت تازه نیست.

cache فقط از نتیجهٔ commit‌شده پر می‌شود و مسیر hit هم مجوز فعلی می‌خواهد. پیش از مجازکردن اصلاح نتیجهٔ نهایی، versioning و invalidation را طراحی کنید.

هویت ماندگار یا tombstone آن باید بیشتر از TTL در Redis بماند. حذف آن قرارداد retry را عوض می‌کند و ADR جدا می‌خواهد. بهبود کارایی تا اندازه‌گیری ادعا نمی‌شود.

### هزینه و شواهد پذیرش

Redis-only بین دو commit شکاف می‌گذارد. lease شاید contention را کم کند، اما مرجع ایمنی نیست. هزینه‌ها حافظه، serialization، شبکه، نسخهٔ محتوا و dependency تازه‌اند.

پاک‌شدن Redis پس از commit، crash پیش از پرکردن cache، duplicate روی دو instance و دورزدن مالکیت نباید اثر مالی دوم بسازند.

## ADR-003: مرور قیدها پیش از schema

[مرور دیتابیس](Database-review.md) باید پیش از migration موسوم به V1 انجام شود. برای هر invariant، یعنی قاعده‌ای که همیشه باید برقرار بماند، این موارد را مشخص کنید:

- پروتکل تراکنش و حفاظت دیتابیس؛
- تست concurrency یا bypass؛
- روش اندازه‌گیری هزینه.

مبلغ مثبت، سیاست موجودی متناسب با حساب، ارجاع اجباری و هویت یکتا حفظ می‌شوند. پیش از تضعیف قاعدهٔ مالی، گلوگاه را بررسی کنید.

`CHECK` ردیفی جمع posting‌ها یا انتقال دوحسابی را کامل تضمین نمی‌کند. این قواعد، مسیر تراکنشی کنترل‌شده، مجوز محدود و reconciliation می‌خواهند.

از ۲۰۲۶-۱۰-۲۲، [ADR-007](../adr/ADR-007-double-entry-ledger.fa.md) دفترکل دوطرفه را از V1 الزامی کرده است. مدل چهارجدولی، حساب مقابل تأمین یا تسویه، افتتاحیهٔ سنددار و reconciliation در [طراحی دفترکل](Ledger.md) آمده‌اند. تغییر موجودی بیرون مسیر حسابرسی مجاز نیست؛ overhead هنوز اندازه‌گیری نشده است.

## ADR-004: تأیید وابسته به تراکنش

### intent چه چیزی را تأیید می‌کند؟

جلوگیری از duplicate ثابت نمی‌کند که مالک حساب همین مبلغ و گیرنده را تأیید کرده است. پس از P3، یک intent تغییرناپذیر با actor، مبدأ، مقصد، مبلغ، ارز، انقضا و شناسهٔ سرور می‌سازیم. جزئیات مهم پیش از تأیید نمایش داده می‌شوند.

تغییر هرکدام از داده‌ها intent و کد تازه می‌خواهد. ساخت intent پول رزرو نمی‌کند.

### endpoint‌های پیشنهادی

- `POST /transfer-intents`
- `POST /transfer-intents/{id}/challenge`
- `POST /transfer-intents/{id}/confirm`
- `GET /transfer-intents/{id}`

صدور و resend باید محدود و در صورت نیاز idempotent باشند. resend نسل قبلی کد را باطل می‌کند. confirm شناسهٔ تراکنش و کد را می‌گیرد و دادهٔ مالی را از intent می‌خواند.

endpoint عمومی دیگری نباید تأیید را bypass کند. `credit` و `debit` هم نقش مجاز می‌خواهند.

### نگهداری و ارسال کد

کد باید امن، تصادفی و کوتاه‌عمر باشد و با HMAC و راز خارج از دیتابیس حفاظت شود. hash سادهٔ کد عددی کوتاه برای حدس آفلاین کافی نیست. constant-time comparison، سقف تلاش و محدودیت ارسال لازم‌اند.

مقادیر نهایی و کانال ارسال در security review مشخص می‌شوند. کد واقعی را در production log یا پاسخ API نمایش ندهید.

adapter اولیهٔ ارسال فقط برای تست و توسعهٔ محلی fake است. این کار عامل دوم واقعی یا مقاومت در برابر phishing را ثابت نمی‌کند.

### ترتیب قفل و commit

همهٔ مسیرهای confirm ابتدا intent و سپس حساب‌ها را با ترتیب ثابت قفل می‌کنند. actor، fingerprint، وضعیت، انقضا و کد بررسی می‌شوند. مصرف کد، تکمیل intent، journal و posting انتقال، projection‌ها، ارجاع یکتای intent، نتیجهٔ عملیات و بعداً outbox با هم commit می‌شوند.

حتی confirm‌های هم‌زمان با شناسهٔ تراکنش متفاوت فقط یک‌بار intent را اجرا می‌کنند. تماس شبکه داخل بازهٔ قفل مالی انجام نمی‌شود.

شمارندهٔ کد نامعتبر باید با وجود پاسخ خطا commit شود؛ exception نباید آن را rollback کند. resend، شمارش تلاش و confirm روی intent هماهنگ‌اند.

در پیشنهاد فعلی، رد کسب‌وکار پس از کد معتبر نهایی است و intent را مصرف می‌کند. تلاش مالی تازه intent تازه می‌خواهد.

### recovery و تست‌ها

برای intent تکمیل‌شده، پس از احراز هویت و کنترل مالکیت، هویت و fingerprint عملیات اصلی را تطبیق دهید. سپس پاسخ قبلی بدون OTP تازه برمی‌گردد. این مسیر فقط recovery است و فرمان تازه اجرا نمی‌کند. endpoint وضعیت، recovery هنگام گم‌شدن شناسهٔ تراکنش را ممکن می‌کند.

هزینه‌ها شامل round trip بیشتر، state، قابلیت اتکای ارسال، کنترل سوءاستفاده و پیچیدگی خطا هستند. تست‌ها باید کد متعلق به دیگری، تغییر مقصد، انقضا، رقابت resend، ثبت تلاش، confirm دوگانه، rollback، پاسخ گم‌شده، replay غیرمجاز و bypass را پوشش دهند. مبنا: [مجوزدهی تراکنش در OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html).

## ADR-005: رویداد پیش از CDC

### outbox و تحویل تکراری

رویداد نسخه‌دار با event ID ثابت همراه موفقیت، journal، posting‌ها و projection‌ها در outbox همان تراکنش ذخیره می‌شود. polling publisher پس از تأیید broker پیشرفت را ثبت می‌کند. crash بین تأیید و ثبت پیشرفت می‌تواند پیام تکراری بسازد.

consumer تاریخچه، هویت پیام مصرف‌شده و اثر تاریخچه را در یک تراکنش دیتابیس خودش ثبت می‌کند؛ سپس offset commit می‌شود. تراکنش Kafka به‌تنهایی دیتابیس خارجی را اتمیک نمی‌کند.

رویداد یک واقعیت commit‌شده است و نباید دوباره پول جابه‌جا کند. کلید تاریخچهٔ اولیه operation ID است و ترتیب تمام عملیات یک حساب را تضمین نمی‌کند. projection موجودی در آینده، نسخهٔ هر حساب، ordering و reconciliation می‌خواهد.

retry، backoff، dead letter و recovery را مشخص کنید. شواهد مالی را بی‌صدا کنار نگذارید.

### معیار امکان‌سنجی CDC در P7

Debezium برای insert‌های outbox بررسی می‌شود. پیش از انتخاب مسیر، این موارد ثبت می‌شوند:

- نسخه و edition واقعی SQL Server، connector و capture adapter؛
- مجوزها، CDC بومی، Agent و capture job؛
- retention جدول تغییرات و snapshot recovery؛
- نگهداری offset و schema history؛
- license در صورت کاربرد.

سازگاری با image محلی را فرض نکنید. در cutover، polling را متوقف و مرز انتشار را مشخص کنید. dedup در consumer برای هم‌پوشانی و recovery همچنان لازم است و polling مسیر fallback می‌ماند.

شواهد لازم، قطعی broker، duplicate، restart و پردازش دوباره‌اند. منابع: [Kafka](https://kafka.apache.org/41/design/design/#message-delivery-semantics) و [Debezium](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html).

## چرخه و قالب ADR

| وضعیت | شرط و معنا |
| --- | --- |
| پیشنهادی | هنوز به مرور گزینه‌ها و شواهد لازم مرحله نیاز دارد |
| پذیرفته‌شده | تصمیم طراحی پذیرفته شده؛ پیاده‌سازی را ثابت نمی‌کند |
| جایگزین‌شده | تصمیم تازه با لینک، تصمیم قبلی را جایگزین کرده است |

شناسهٔ ADR ثابت می‌ماند. commit پیاده‌سازی، اندازه‌گیری، تاریخ و محدودیت‌ها جدا ثبت می‌شوند. هر دو زبان در همان PR به‌روز می‌شوند.

قالب هر ADR این اطلاعات را می‌خواهد:

1. شناسه، عنوان، وضعیت، تاریخ و مسئول؛
2. زمینه، محدودیت، invariant یا تهدید، گزینه‌ها و مرز منتخب؛
3. پروتکل تراکنش، قفل و خرابی؛
4. فرض هزینه، روش اندازه‌گیری، baseline و نتیجه یا «اندازه‌گیری نشده»؛
5. تست پذیرش، rollback یا migration و لینک PR و schema و زبان دیگر.

مجهول‌ها را صریح نگه دارید.

## نمایش پول پذیرفته‌شده، ۲۰۲۶-۱۰-۲۲

### تصمیم پولی

کاربر `long` جاوا را برای مبلغ و موجودی IRR به ریال پذیرفت. هر واحد یک ریال است؛ SQL Server از `BIGINT` و API از نام‌هایی مثل `amountRial` و `balanceRial` استفاده می‌کند. مقدار کسری از ریال پیش از ساخت عملیات نامعتبر است.

سقف تجاری جدا برای مبلغ پذیرفته شده، اما عدد آن و هر سقف موجودی هنوز باز است. سقف نوع داده جای سقف تجاری را نمی‌گیرد.

### محاسبات و overflow

جمع و تفریق تمام حساب‌ها، از جمله projection حساب سیستمی، باید overflow را کنترل کنند. خطای بازه نباید اثر پولی جزئی بگذارد. جمع journal و reconciliation با accumulator دقیق و بزرگ‌تر انجام می‌شود و بعد بازهٔ projection کنترل می‌شود.

`BigDecimal` هم دقیق است و برای نرخ، کارمزد و محاسبهٔ میانی کسری مناسب می‌ماند. پیش از posting، rounding و باقیمانده باید مرور شوند.

### توضیح تصمیم در مصاحبه

واحد صحیح مستقیماً مقادیر مجاز ریال را در V1 مدل می‌کند. دقت ارز و نوع storage دو تصمیم جدا هستند. `long` ایمنی concurrency نمی‌دهد؛ تراکنش و قفل این مسئولیت را دارند.

اگر موجودی یا accrual کسری از واحد لازم داشت، یا مبلغ از `BIGINT` فراتر رفت، storage از نوع decimal دوباره بررسی می‌شود.

### مرز FX آینده

می‌توان مبلغ ثبت‌شدهٔ صحیح را با واحد صریح هر ارز، نرخ decimal و توازن posting‌ها به‌ازای ارز حفظ کرد. quote پذیرفته‌شده و مبلغ گرد‌شده برای replay می‌مانند.

حساب‌ها، موقعیت و تسویهٔ FX، نقدینگی و rounding کار CBS38 هستند. این یادداشت هیچ‌کدام را پیاده نمی‌کند؛ سیاست پولی طراحی پذیرفته‌شده است و شاهد اجرا یا اندازه‌گیری مالی نیست.

## سیاست نگهداری پذیرفته‌شده در ۲۰۲۶-۱۰-۲۳

در V1، شناسهٔ عملیات commit‌شده، دستور canonical و پاسخ نهایی اصلی بدون تاریخ حذف نگهداری می‌شوند. موفقیت و رد نهایی کسب‌وکار هر دو شناسه را دائماً رزرو می‌کنند. خطای validation یا rollback، رزرو commit‌شده باقی نمی‌گذارد.

اصلاح با شناسهٔ تازه و مرتبط انجام می‌شود و replay اصلی حفظ می‌شود. TTL در Redis شناسهٔ SQL Server را آزاد نمی‌کند. آرشیو آینده باید یکتایی و امکان بازیابی پاسخ اصلی را نگه دارد؛ [سیاست نگهداری CBS03](Idempotency-protocol.md) را ببینید.

فقط سیاست نگهداری پذیرفته شده است. جزئیات دیگر پروتکل همچنان پیش‌نویس‌اند و مرور می‌خواهند.

## مرز تراکنش پذیرفته‌شده، ۲۰۲۶-۱۰-۲۳

هر تلاش مالی با Spring `TransactionTemplate` و propagation از نوع REQUIRED در coordinator غیرتراکنشی اجرا شود؛ نبود تراکنش بیرونی در ورودی الزاماً کنترل شود. نتیجهٔ Success/Rejected مقدار عادی است؛ exception فنی rollback می‌کند. retry، بازیابی duplicate و نگاشت HTTP بیرون تلاش باشند. رزرو، رد یا نتیجهٔ مالی موفق با REQUIRES_NEW جداگانه commit نشوند. پایان template فقط با نبود تراکنش بیرونی تأیید commit است. guard صریح یا ورودی NEVER در bean پروکسی‌شده این شرط را اجرا کند؛ self-invocation نباید آن را دور بزند. این پذیرش مکانیزم است، نه رفتار SQL یا کل پروتکل. [پیش‌نویس CBS04](Transaction-protocol.md) گام مرور بعدی است.

## ADR-008: معماری برنامهٔ پذیرفته‌شده، ۲۰۲۶-۱۰-۲۳

[ADR-008](../adr/ADR-008-application-architecture.fa.md) مونولیت ماژولار، مرز feature و port/adapter انتخابی را می‌پذیرد. [معماری](Architecture.md) مثال‌ها و درخت هدف را دارد. CQRS تک‌دیتابیسی بعداً در ADR-009 پذیرفته شد؛ شکل‌های پیشرفته و سایر پیشنهادها وضعیت اعلام‌شدهٔ خود را دارند. این پذیرش persistence مالی را پیاده نمی‌کند.

## ADR-009: پذیرش CQRS تک‌دیتابیسی، ۲۰۲۶-۱۰-۲۳

[ADR-009](../adr/ADR-009-single-database-cqrs.fa.md) مدل command/نوشتن و projection خواندن جدا روی همان SQL Server و حفظ موجودی هم‌زمان اتمیک را می‌پذیرد. command bus، read store جدا یا event sourcing لازم نیست. پیاده‌سازی و شاهد دیتابیس هنوز باز هستند.

## هویت و ترتیب حساب پذیرفته‌شده، ۲۰۲۶-۱۰-۲۳

AccountId از UUID استفاده می‌کند و مستقل از transaction ID است. AccountLockOrder.DESCENDING نیمه‌های UUID را unsigned و نزولی برای همهٔ writerهای حساب مقایسه می‌کند. wrapper و comparator پیاده و unit-test شده‌اند؛ قفل دیتابیس پیاده نشده است. مجموعهٔ کامل و یکتای حساب‌ها مرتب و lookup قفل داخل تراکنش مالی پشت سر هم اجرا شود. ترتیب طبیعی UUID جاوا، GUID سرور یا نتیجهٔ query حجمی تضمین اخذ قفل نیست. نگاشت SQL، index، parsing و تست رقابت واقعی هنوز باز هستند.

## اصلاح سیاست ارزهای پشتیبانی‌شده، ۲۰۲۶-۱۰-۲۳

به درخواست کاربر، ارزهای مجاز دیگر داخل CommandValidation یا سازندهٔ commandها ثابت نیستند. `CommandValidation.requirePositiveAmount` فقط وجود و مثبت‌بودن مبلغ را بررسی می‌کند. CreditCommand، DebitCommand و TransferCommand ارز Money را برای سیاست جداگانهٔ `SupportedCurrencies(Set<Currency>)` حفظ می‌کنند. این تصمیم محدودیت قبلی IRR در سازنده‌ها را جایگزین می‌کند. سیاست استقرار اولیهٔ V1 همچنان IRR است؛ validator مبتنی بر مجموعه، تبدیل FX یا واحد ارزهای دیگر را تعریف نمی‌کند.

SupportedCurrencies از مجموعهٔ ورودی کپی تغییرناپذیر می‌سازد و متد `requireSupported(Currency)` دارد. ارز مجاز از ورودی می‌آید و داخل کد اعتبارسنجی production ثابت نیست. مجموعه، عضو یا ارز null رد می‌شود؛ مجموعهٔ صریحاً خالی همهٔ ارزها را غیرفعال می‌کند. تغییر مجموعهٔ اصلی، snapshot قبلی سیاست را عوض نمی‌کند. در آینده تنظیمات یا adapter دیتابیس می‌تواند snapshot تازه بدهد؛ سیاست وارد payload دستور نمی‌شود و سازندهٔ value object هم دیتابیس نمی‌خواند. loader، جدول یا bean زمان اجرا هنوز پیاده نشده است.

نمونهٔ اتصال با مجموعهٔ سیاست ورودی، پیش از اجرا:

```java
var policy = new SupportedCurrencies(currenciesFromConfiguration);
policy.requireSupported(command.amount().currency());
```

coordinator آینده باید پیش از ارزیابی دوبارهٔ این سیاست قابل‌تغییر، نتیجهٔ نهایی موجود را پیدا کند. retry منطبق باید حتی پس از غیرفعال‌شدن ارز، نتیجهٔ اصلی را replay کند. برای عملیات تازه، پشتیبانی ارز با یک snapshot سازگار و پیش از رزرو بررسی می‌شود. قالب معتبر ارز با مجازبودن در سیاست فعلی فرق دارد. خرابی بارگذاری دیتابیس خطای فنی است؛ نباید آن را مجموعهٔ خالی یا تصمیم نهایی رد ارز تعبیر کرد. پروتکل بارگذاری و تازه‌سازی سیاست هنوز به طراحی و تست اتصال نیاز دارد.

Maven verify با Java 21.0.11 در ۷٫۵۶۵ ثانیه، ۱۳۷ تست را بدون failure، error یا skip گذراند. نُه مورد سیاست، چند ارز مجاز، رد ارز بیرون از مجموعه، مجموعهٔ بدون IRR، مجموعهٔ خالی و null و snapshot تغییرناپذیر را می‌سنجند. سیزده تست command اکنون حفظ ارز را به‌جای رد ثابت ارز بررسی می‌کنند. HTTP، ترتیب replay و بارگذاری سیاست از دیتابیس هنوز پیاده نشده‌اند؛ این شواهد اعتبارسنجی مستقل از زیرساخت است.
