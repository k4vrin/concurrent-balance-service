# پروتکل idempotency عملیات در CBS03

[English](../en/Idempotency-protocol.md) · [ADR-002](Decisions.md) · [نیازمندی‌ها](Requirements.md)

وضعیت در ۲۰۲۶-۱۰-۲۲: پیش‌نویس برای مرور مشترک. سیاست‌های کسب‌وکارِ پذیرفته‌شده همچنان معتبرند؛ قالب شناسه، encoding، رزرو و recovery هنوز پیشنهادند. این سند کد، schema یا تست SQL Server اضافه نمی‌کند. SQL دقیق تراکنش و قفل‌ها در CBS04 و پیش از مایگریشن مالی مرور می‌شود.

## مسئله: پاسخ نرسیده، اما شاید پول جابه‌جا شده باشد

کلاینت درخواست انتقال می‌فرستد، اما پاسخ را دریافت نمی‌کند. ممکن است سرور پیش از commit متوقف شده باشد؛ ممکن است هم تراکنش commit شده باشد و فقط پاسخ در شبکه گم شده باشد. از دید کلاینت، هر دو حالت شبیه timeout هستند.

مثلاً کلاینت با شناسهٔ `transfer-001` درخواست انتقال ۱۰۰ ریال می‌دهد. اگر انتقال commit شده باشد، retry با همین شناسه باید پاسخ اصلی را برگرداند. اگر تراکنش rollback شده باشد، همین شناسه می‌تواند برای اجرای درخواست استفاده شود. در هیچ‌کدام از این دو حالت نباید دو انتقال commit شوند.

این مثال فقط مسئله را نشان می‌دهد. مسیر مالی هنوز پیاده نشده و تست SQL Server برای آن اجرا نشده است.

## قرارداد idempotency

هر شناسهٔ تراکنش، تا وقتی در دیتابیس نگهداری می‌شود، به یک دستور تغییرناپذیر و حداکثر یک نتیجهٔ نهاییِ commit‌شده اشاره می‌کند:

| درخواست | رفتار موردانتظار |
| --- | --- |
| همان شناسه و همان دستور | پاسخ نهایی اصلی را برگردان؛ این رفتار replay است |
| همان شناسه و دستور متفاوت | conflict برگردان؛ نتیجهٔ اصلی را تغییر نده |
| شناسهٔ تازه | درخواست را یک تلاش تازه در نظر بگیر |

شناسهٔ تازه ثابت نمی‌کند که کاربر قصد مالی تازه‌ای دارد. Idempotency جلوی اثر تکراری یک شناسه را می‌گیرد؛ تشخیص نیت کاربر، مجوز و محدودیت نرخ درخواست مسئولیت‌های دیگری هستند.

در V1، SQL Server مرجع نتیجه است. Redis در آینده فقط نسخهٔ معتبر پاسخ commit‌شده را cache می‌کند. پاک‌شدن cache نباید اجازهٔ اجرای دوبارهٔ عملیات را بدهد. این قرارداد حداکثر یک اثر commit‌شده برای هر شناسهٔ نگهداری‌شده را تضمین می‌کند؛ تحویل دقیقاً یک‌باره در شبکه را تضمین نمی‌کند.

دامنهٔ شناسه‌ها در این سرویس تک‌مستأجر سراسری است. `credit`، `debit`، `transfer` و افتتاحیهٔ داخلی از همین فضای مشترک استفاده می‌کنند. درخواست GET موجودی، شناسهٔ عملیات مالی رزرو نمی‌کند.

## چه چیزی هویت درخواست را مشخص می‌کند؟

### قالب شناسهٔ تراکنش

قالب پیشنهادی شناسه:

- طول ۱ تا ۱۲۸ نویسهٔ ASCII؛
- شامل حروف، رقم و نشانه‌های `.`، `_`، `:` و `-`؛
- حساس به بزرگی و کوچکی حروف؛
- بدون فاصله. فاصله را رد می‌کنیم و با trim حذف نمی‌کنیم.

مقدار `null`، شناسهٔ خالی، طول بیش‌ازحد و نویسهٔ نامجاز باید پیش از رزرو رد شوند. برنامه و کلید یکتای دیتابیس باید شناسه‌ها را با قواعد یکسان مقایسه کنند. رفتار collation و فاصلهٔ انتهایی در SQL Server به تست واقعی نیاز دارد.

قالب و مقایسهٔ شناسهٔ حساب، تصمیم جداگانهٔ CBS04 است. شناسهٔ افتتاحیه هم از همین سازوکار یکتایی استفاده می‌کند. برخورد شناسه به‌معنی یکسان‌بودن دستور نیست و مجوز replay دستور دیگری را نمی‌دهد.

### دستور canonical و fingerprint

برای مقایسهٔ درخواست‌ها، از دستور یک نمایش ثابت می‌سازیم؛ این نمایش را canonical command می‌نامیم. ترتیب کلیدها و فاصله‌های JSON نباید هویت درخواست را عوض کنند. شکل‌های عددی هم‌ارز هم، اگر قرارداد ورودی آن‌ها را می‌پذیرد، باید به همان نمایش برسند.

فیلدهای دستور canonical عبارت‌اند از:

| فیلد | قاعده |
| --- | --- |
| نسخهٔ encoding | روش ساخت نمایش ثابت را مشخص می‌کند |
| نوع عملیات | افزایش موجودی، برداشت، انتقال یا افتتاحیه |
| شناسه‌های درخواستی حساب | مبدأ، مقصد و هدف با نقش‌های جدا |
| مبلغ | عدد صحیح مثبت به ریال |
| ارز | ارز درخواست |
| شناسهٔ actor پس از افزودن احراز هویت | عامل احرازشده‌ای که درخواست به او متصل است |

در V1 فقط اپراتور محلی مورداعتماد داریم؛ هویت فرضی مشتری نمی‌سازیم. وقتی actor اضافه شد، سازگاری با رکوردهای قدیمی به قواعد نسخه‌دار نیاز دارد.

برای encoding، فیلدهای UTF-8 با طول صریح، نشانگر `null` و ترتیب ثابت پیشنهاد می‌شوند. مبلغ معتبر به نمایش ثابتِ عدد صحیح در مبنای ده تبدیل می‌شود. بایت‌های canonical، نسخهٔ encoding و fingerprint از نوع SHA-256 را نگه می‌داریم. تطابق هش به‌تنهایی کافی نیست؛ خود دستور هم باید مقایسه شود.

شناسهٔ تراکنش کلید lookup است. موارد زیر وارد fingerprint نمی‌شوند:

- زمان retry و شناسهٔ ردیابی؛
- زمان پاسخ و دیگر metadataهای انتقال پیام؛
- راز OTP.

در canonicalization نباید شناسهٔ حساب، ارز یا واحد مبلغ را بی‌صدا تغییر دهیم.

### حساب مقابل را سرور انتخاب می‌کند

سرور حساب تأمین یا تسویهٔ مقابل را برای `credit` و `debit` انتخاب می‌کند. حساب انتخاب‌شده و نسخهٔ سیاست در metadata اجرا می‌مانند. retry نباید حساب مقابل تازه‌ای انتخاب کند.

## برای replay چه چیزی ذخیره می‌کنیم؟

نتیجهٔ نهایی باید این اطلاعات را همراه خود داشته باشد:

- status اصلی HTTP؛
- کد پایدار برنامه؛
- نسخهٔ schema پاسخ؛
- body سریال‌شده؛
- headerهایی که بخشی از قرارداد پاسخ‌اند.

replay محتوای اصلی پاسخ را برمی‌گرداند. اگر پاسخ شامل موجودی بوده، همان موجودی زمان اجرای اصلی برمی‌گردد؛ برای ساخت پاسخ دوباره موجودی را نمی‌خوانیم. headerهای ردیابی و انتقال پیام می‌توانند برای درخواست تازه فرق کنند.

پس از deploy نسخهٔ جدید، پاسخ‌های قدیمی باید همچنان قابل‌خواندن باشند. تغییر قرارداد نباید معنای رکوردهای قبلی را بی‌صدا عوض کند.

## مسیر پردازش درخواست

### ۱. ورودی و دسترسی را بررسی کن

ساختار درخواست، شناسه‌ها، مبلغ مثبت به ریال، ارز IRR و متفاوت‌بودن حساب‌های انتقال را validate کن. خطای این مرحله رکورد عملیات نمی‌سازد.

پس از افزودن امنیت، احراز هویت و مجوز فعلی را پیش از نمایش پاسخ قبلی بررسی کن. V1 همچنان فقط برای اپراتور محلی مورداعتماد است.

### ۲. ابتدا تکلیف replay را مشخص کن

دستور canonical نسخه‌دار را بساز. lookup اولیهٔ نتیجهٔ commit‌شده اختیاری است. اگر رکورد موجود بود، دسترسی فعلی و تطابق دستور را بررسی کن؛ دستور یکسان پاسخ ذخیره‌شده می‌گیرد و دستور متفاوت conflict.

پیش از این تصمیم، موجودی فعلی، انتخاب حساب مقابل تازه یا سقف تجاری متغیر را دوباره بررسی نکن. درخواست قبلی قرار نیست با وضعیت امروز دوباره اجرا شود.

### ۳. شناسه را داخل تراکنش رزرو کن

اگر رکورد commit‌شده‌ای پیدا نشد، یک تراکنش محلی تازه باز کن. رزرو را با قید یکتای سراسری شناسهٔ تراکنش در `operations` درج و صریحاً flush کن. تا رزرو موفق نشده، حسابی قفل نکن و دادهٔ پولی ننویس.

وضعیت اولیهٔ `PENDING` فقط داخل همین تراکنش commit‌نشده وجود دارد. این وضعیت، رکورد پردازش مستقل یا lease توزیع‌شده نیست. خواندن دادهٔ commit‌نشده یا dirty read مجاز نیست.

### ۴. حساب‌ها را با ترتیب ثابت قفل کن

همهٔ حساب‌های مشتری و سیستمی درگیر را با ترتیب سراسری قفل کن. وضعیت آن‌ها را طبق پروتکل CBS04 بخوان.

شناسه‌های درخواستی در `operations` دادهٔ درخواست و ممیزی‌اند و به حساب foreign key ندارند. این جداسازی اجازه می‌دهد رد درخواستِ حساب ناموجود را هم ذخیره کنیم. در مقابل، سطر ثبت حسابداری یا posting موفق باید ارجاع اجباری به حساب واقعی داشته باشد.

### ۵. قواعد کسب‌وکار و سرریز را بررسی کن

پیش از تغییر موجودی، همهٔ تغییرات projection، یعنی نمای ذخیره‌شدهٔ موجودی، را با محاسبات دارای کنترل سرریز حساب کن. حساب ناموجود، کسری موجودی یا سرریز موجودی حاصل، نتیجهٔ نهایی `REJECTED` می‌سازند. پاسخ اصلی رد ذخیره می‌شود، اما سند حسابداری یا journal، posting و تغییر موجودی نداریم.

پیشنهاد برای مرور این است که عبور از سقف تجاری متغیر هم رد نهایی باشد و فقط برای عملیات تازه ارزیابی شود. مقدار سقف و کد عمومی خطا هنوز مشخص نیستند.

### ۶. اثر مالی و نتیجه را با هم ذخیره کن

در موفقیت، این موارد باید با هم ثبت شوند:

- یک journal کامل و متوازن، یعنی سند حسابداری؛
- postingهای تغییرناپذیر، یعنی سطرهای ثبت حسابداری؛
- تمام projectionهای درگیر؛
- نتیجهٔ نهایی `SUCCEEDED`.

افتتاحیه از همین سازوکار هویت استفاده می‌کند. پاسخ ذخیره‌شدنی را پیش از commit سریال کن تا خطای serialization، عملیات موفقی بدون پاسخ ثبت‌شده باقی نگذارد.

### ۷. فقط نتیجهٔ نهایی را commit کن

رد کسب‌وکار را به‌صورت مقدار از مرز تراکنش برگردان. تبدیل آن به خطای HTTP نباید باعث rollback نتیجهٔ رد شود. خطای فنی باید رزرو و تمام نوشته‌های مالی را با هم rollback کند.

پس از خطای persistence، در تراکنش خراب یا rollback-only ادامه نده. اجرای کنترلر، تماس شبکه و دسترسی به cache نباید داخل بازهٔ نگهداری قفل‌های مالی باشند.

`PENDING` هرگز نباید commit شود. schema و مسیر تراکنش باید این چرخه را روشن کنند؛ قید ردیفی به‌تنهایی رابطهٔ موفقیت و سند را هنگام commit تضمین نمی‌کند. رکورد غیرنهاییِ commit‌شده نقض قاعدهٔ صحت یا invariant است و به درخواست دیگر اجازهٔ تصاحب اجرا نمی‌دهد. ترمیم چنین رکوردی به بررسی کنترل‌شده نیاز دارد.

### ۸. پس از تأیید commit پاسخ بده

پاسخ نهایی را فقط پس از تأیید commit برگردان. در آینده، Redis پس از commit و به‌صورت best-effort پر می‌شود؛ شکست cache نتیجهٔ commit‌شده را تغییر نمی‌دهد.

اگر تأیید commit گم شد، با همین پروتکل نتیجه را بازیابی کن. اگر recovery تا پایان deadline کامل نشد، نتیجه را موقت یا نامطمئن اعلام کن.

## اگر دو درخواست هم‌زمان برسند

| گام | درخواست A | درخواست B با همان شناسه |
| --- | --- | --- |
| ۱ | lookup نتیجه‌ای پیدا نمی‌کند | ممکن است lookup آن هم نتیجه‌ای پیدا نکند |
| ۲ | رزرو را درج و flush می‌کند | برای رزرو همان شناسه، با انتظار محدود رقابت می‌کند |
| ۳ | موفقیت یا رد را commit می‌کند | تا رزرو را نگرفته، هیچ دادهٔ مالی نمی‌نویسد |
| ۴ | پاسخ commit‌شده را برمی‌گرداند | اگر درج با خطای موردانتظار duplicate key شکست خورد، تراکنش را کنار می‌گذارد یا rollback می‌کند و recovery تازه‌ای شروع می‌کند |
| ۵ | اثر تازه‌ای ندارد | دستور یکسان پاسخ اصلی می‌گیرد؛ دستور متفاوت conflict |

رزرو A تا پیش از commit قطعی نیست. اگر A rollback شود، B می‌تواند شناسه را رزرو و دستور را اجرا کند؛ در این حالت نتیجهٔ قبلی برای replay نداریم. ترتیب رسیدن درخواست‌ها هم برنده را تعیین نمی‌کند.

رفتار انتظار و طبقه‌بندی خطاها باید روی ترکیب منتخب SQL Server، JDBC و JPA تست شوند. فقط نقض قید یکتای مشخص شناسهٔ تراکنش، برخورد هویت محسوب می‌شود. هر integrity error به‌معنی وجود عملیات قبلی نیست.

### lookup خالی، وضعیت نامطمئن را حل نمی‌کند

ممکن است recovery هنوز رکورد نهایی پیدا نکند، چون تراکنش قبلی تعیین تکلیف نشده است. نبود رکورد ثابت نمی‌کند که اجرای قبلی حتماً تمام شده است.

همان پروتکل رزرو یکتا را در تراکنش تازه تکرار کن یا با تمام‌شدن بودجهٔ retry و deadline، خطای موقت برگردان. تراکنش حل‌نشدهٔ قبلی همچنان بر سر همان شناسه رقابت می‌کند. recovery باید از دیتابیس مرجع بخواند، نه replica عقب‌مانده.

## رفتار در خرابی و retry

| وضعیت | رفتار لازم |
| --- | --- |
| ورودی نامعتبر یا دسترسی ردشده | بدون رزرو؛ خطای اعتبارسنجی یا دسترسی برگردان |
| توقف پیش از commit و rollback تراکنش | از این تلاش تغییری در عملیات، journal، posting و projection باقی نمی‌ماند؛ همان شناسه بعداً قابل‌اجراست |
| رد commit‌شده و سپس تغییر موجودی، حساب یا سیاست | همان رد اصلی را replay کن؛ تلاش مالی تازه شناسهٔ تازه می‌خواهد |
| موفقیت commit‌شده و پاسخ گم‌شده | موفقیت اصلی را replay کن؛ سند یا بررسی موجودی تازه نداریم |
| قربانی deadlock یا rollback موقتی که صریحاً طبقه‌بندی شده | کل تراکنش را با همان شناسه و دستور، در تراکنش تازه و با تعداد تلاش محدود retry کن؛ backoff بیرون تراکنش باشد |
| timeout قفل یا اتصال، یا commit نامطمئن | rollback را فرض نکن؛ هویت را در تراکنش تازه بازیابی کن و موقت یا نامطمئن‌بودن نتیجه را حفظ کن |
| پایان بودجهٔ retry | پاسخ پیشنهادی 503؛ همان شناسه برای recovery حفظ شود و ادعا نشود که commit رخ نداده است |
| integrity error یا خطای برنامه‌نویسی، غیر از برخورد هویت موردانتظار | rollback و بررسی؛ خطا را به رد کسب‌وکار تبدیل نکن و بدون تشخیص علت retry نکن |

تعداد تلاش‌ها، backoff، مهلت انتظار قفل و deadline کل درخواست در CBS04 تعیین می‌شوند و هنوز بازند. retry نامحدود نداریم. رد نهاییِ commit‌شده را هم خودکار دوباره اجرا نمی‌کنیم.

## نگهداری داده و هزینه‌ها

تصمیم پذیرفته‌شدهٔ کاربر در ۲۰۲۶-۱۰-۲۳ برای V1 این است که شناسهٔ نهایی commit‌شده، دستور canonical و پاسخ اصلی بدون تاریخ حذف بمانند. job پاک‌سازی عملیات نداریم. موفقیت و رد نهایی هر دو شناسه را دائماً رزرو می‌کنند. خطای اعتبارسنجی و تراکنش rollback‌شده رزرو commit‌شده ندارند. اصلاح یا برگشت با شناسهٔ جدید مرتبط انجام می‌شود و replay اصلی حفظ می‌شود. فقط سیاست نگهداری پذیرفته شده و سایر جزئیات پیش‌نویس همچنان نیازمند مرورند. TTL در Redis عمر شناسه در SQL Server را تعیین نمی‌کند.

آرشیو آینده باید هم امکان replay پاسخ و هم حفاظت یکتایی را حفظ کند. tombstone، یعنی رکورد نشانگر هویت قبلی، به‌تنهایی جلوی اجرای دوباره را می‌گیرد، اما پاسخ اصلی را بازتولید نمی‌کند. جایگزینی پاسخ کامل با آن تغییر قرارداد است و تصمیم جدا می‌خواهد.

هزینه‌های قابل‌اندازه‌گیری:

- یک ردیف عملیات و نگهداری unique index برای هر تصمیم نهایی؛
- فضای دستور canonical و پاسخ اصلی؛
- رقابت درخواست‌های تکراری و lookupهای recovery.

رد درخواست journal ندارد، اما commit رکورد عملیات همچنان هزینه دارد. کنترل پذیرش و rate limit باید جلوی سیل شناسه‌های تازه را بگیرند؛ idempotency چنین کاری نمی‌کند. یکتایی intent در مرحلهٔ OTP نیز مستقل از یکتایی شناسهٔ تراکنش است.

## پیش از پیاده‌سازی چه چیزی باید مرور شود؟

- قالب و مقایسهٔ شناسه، encoding دستور canonical و سازگاری نسخهٔ actor؛
- رزرو داخل تراکنش و نحوهٔ ثبت نتیجهٔ نهایی؛
- rollback و recovery پس از duplicate key؛
- طبقه‌بندی رد ناشی از سقف تجاری؛
- سیاست نگهداری و فضای ذخیره‌سازی؛
- انتخاب قفل‌ها، طبقه‌بندی خطاها و deadline در CBS04.

این سند سقف تجاری عددی تعیین نمی‌کند.

## تست‌های لازم برای پذیرش

همهٔ موارد زیر به تست واقعی نیاز دارند:

| موضوع | سناریوهای لازم |
| --- | --- |
| رقابت | درخواست‌های یکسان و متعارض روی دو instance؛ rollback درخواست برنده |
| خرابی تراکنش | deadlock، timeout، گم‌شدن تأیید commit و خطای serialization |
| رد نهایی | replay پس از تغییر وضعیت یا سیاست؛ ذخیرهٔ رد برای حساب ناموجود |
| ماندگاری | restart برنامه و پاک‌شدن cache |
| سازگاری | ثبات بایت‌های پاسخ و سازگاری نسخهٔ fingerprint |
| صحت مالی | نبود `PENDING` commit‌شده، تعداد journalها و بازسازی مستقل موجودی |

این فهرست برنامهٔ تست است و موفقیت هیچ تستی را ثابت نمی‌کند.

## نکات کلیدی

- در retry همان شناسه و همان دستور را حفظ کن.
- نتیجهٔ نهایی را از SQL Server بازیابی کن؛ cache مرجع تصمیم مالی نیست.
- رد نهایی را هم replay کن، حتی اگر موجودی یا سیاست بعداً تغییر کرده باشد.
- در commit نامطمئن، از نبود رکورد نتیجه نگیر که اجرا تمام شده است.

## منابع اصلی

- [قیدهای SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints): قید `UNIQUE` با unique index حفاظت می‌شود، اما replay پاسخ را پیاده نمی‌کند.
- [TRY/CATCH و وضعیت تراکنش](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/try-catch-transact-sql): مدیریت خطا باید تراکنشی را که دیگر قابل‌commit نیست در نظر بگیرد.
- [راهنمای deadlock](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide): قربانی deadlock به recovery در سطح تراکنش نیاز دارد.

تاریخ مرور منابع ۲۰۲۶-۱۰-۲۲ است. رفتار دقیق باید پیش از پذیرش پیاده‌سازی، با نسخهٔ ثابت‌شدهٔ سرور و درایور تست شود.

## مرز تراکنش پذیرفته‌شده، ۲۰۲۶-۱۰-۲۳

هر تلاش مالی با Spring `TransactionTemplate` و propagation از نوع REQUIRED در coordinator غیرتراکنشی اجرا شود؛ نبود تراکنش بیرونی در ورودی الزاماً کنترل شود. نتیجهٔ Success/Rejected مقدار عادی است؛ exception فنی rollback می‌کند. retry، بازیابی duplicate و نگاشت HTTP بیرون تلاش باشند. رزرو، رد یا نتیجهٔ مالی موفق با REQUIRES_NEW جداگانه commit نشوند. پایان template فقط با نبود تراکنش بیرونی تأیید commit است. guard صریح یا ورودی NEVER در bean پروکسی‌شده این شرط را اجرا کند؛ self-invocation نباید آن را دور بزند. این پذیرش مکانیزم است، نه رفتار SQL یا کل پروتکل. [پیش‌نویس CBS04](Transaction-protocol.md) گام مرور بعدی است.

اصلاح شناسهٔ حساب در ۲۰۲۶-۱۰-۲۳: دستور canonical شناسهٔ حساب parseشده را با UUID.toString ثبت خواهد کرد؛ قواعد هویت transaction ID عوض نمی‌شود. AccountLockOrder.DESCENDING ترتیب قفل برنامه است، نه ترتیب فیلد fingerprint. کد parsing/fingerprint و قفل SQL هنوز پیاده نشده‌اند.
