# طراحی دفترکل V1

[English](../en/Ledger.md) · [ADR-007 پذیرفته‌شده](../adr/ADR-007-double-entry-ledger.fa.md) · [مرور قیدها](Database-review.md) · [بدهکار و بستانکار در انواع حساب](Debit-and-credit.md) · [راهنمای Journal و projection](Journal-projection.md)

کاربر در ۲۰۲۶-۱۰-۲۲ گزینهٔ E را انتخاب کرد: دفترکل دوطرفه با journal‌های چندسطری در همان SQL Server سرویس موجودی. این گسترش دامنه، انتخاب پروژه است و به نیازمندی شرکت نسبت داده نمی‌شود. schema در CBS09 اکنون پیاده و روی SQL Server تست شده است؛ [Schema.md](Schema.md) را ببینید. handler و اجرای posting مالی و هم‌زمانی/کارایی مالی هنوز پیاده نشده‌اند.

## چرا ذخیرهٔ موجودی به‌تنهایی کافی نیست؟

اگر فقط بدانیم موجودی حساب A برابر ۱۰۰ ریال است، از روی همین عدد نمی‌توانیم تاریخچهٔ حساب را بازسازی کنیم. دفترکل باید تغییرها را هم نگه دارد تا موجودی هر حساب را مستقلاً از آن‌ها محاسبه کنیم. در مدل منتخب، posting‌ها تاریخچهٔ تغییرناپذیرند و projection همان موجودی فعلی است که هم‌زمان با آن‌ها ثبت می‌شود.

## مسئولیت چهار جدول

journal همان سند حسابداری است و هر posting یک سطر بدهکار یا بستانکار آن است. projection، موجودی ذخیره‌شدهٔ حساب است که باید با تاریخچهٔ postingها برابر بماند.

| جدول | مسئولیت |
| --- | --- |
| `accounts` | هویت، نوع و ارز حساب، همراه projection ماندگار موجودی فعلی |
| `operations` | شناسهٔ تراکنش سراسری، fingerprint درخواست، و پاسخ نهایی موفقیت یا رد کسب‌وکار |
| `journals` | سرسند حسابداری با ارجاع یکتا به یک عملیات موفق |
| `postings` | سطرهای تغییرناپذیر بدهکار یا بستانکار، با ارجاع به journal و حساب و مبلغ مثبت به ریال |

هر mutation موفق در نسخهٔ اولیه دقیقاً یک journal دارد. journal حداقل یک posting بدهکار و یک posting بستانکار می‌خواهد و جمع دو سمت باید برای هر ارز جداگانه برابر باشد. عملیات اولیه دو posting دارند.

یک دیتابیس و یک SQL schema کافی است. namespace جدا برای ledger صرفاً انتخاب سازمان‌دهی است. V1 به `ledger_transactions`، `transfer_requests` یا سرویس دفترکل جدا نیاز ندارد. intent، outbox و جدول consumer در مراحل بعد مسئولیت خودشان را دارند.

## معنای حساب‌ها و یک مثال

### مبلغ و نوع حساب

V1 فقط IRR با مبلغ ریال می‌پذیرد؛ هر واحد دقیقاً یک ریال است. مبلغ و projection در جاوا `long` و در SQL Server از نوع `BIGINT` خواهند بود و محاسبات باید overflow را کنترل کنند. سقف‌های تجاری هنوز مرور می‌خواهند.

نرخ FX و محاسبات میانی آینده از `BigDecimal` استفاده می‌کنند و پیش از posting به سیاست گردکردن نیاز دارند. طراحی چندارزی در CBS38 بررسی می‌شود.

نوع حساب‌ها و قواعد علامت در CBS02–05 بازبینی می‌شوند. مدل اولیه، حساب مشتری را بدهی سرویس به مشتری با ماهیت بستانکار می‌داند. حساب مقابل تأمین یا تسویه را سرور انتخاب می‌کند و ماهیت آن بدهکار است.

- موجودی مشتری برابر جمع بستانکار منهای جمع بدهکار است و نباید منفی شود.
- موجودی حساب مقابل برابر جمع بدهکار منهای جمع بستانکار است. حساب مصنوعی تأمین یا تسویه می‌تواند در کل بازهٔ علامت‌دار `long` قرار بگیرد؛ این سیاست وجود نقدینگی بیرونی را ثابت نمی‌کند.

تسویهٔ واقعی، اضافه‌برداشت و کارمزد به تصمیم‌های جداگانه نیاز دارند. برای نمونه، ثبت عملیات به مبلغ ۱۰۰ ریال چنین خواهد بود:

| عملیات | بدهکار | بستانکار |
| --- | --- | --- |
| افزایش موجودی A | تأمین یا تسویه: ۱۰۰ ریال | مشتری A: ۱۰۰ ریال |
| برداشت از A | مشتری A: ۱۰۰ ریال | تأمین یا تسویه: ۱۰۰ ریال |
| انتقال از A به B | مشتری A: ۱۰۰ ریال | مشتری B: ۱۰۰ ریال |
| موجودی افتتاحیهٔ A | تأمین یا تسویه: ۱۰۰ ریال | مشتری A: ۱۰۰ ریال |

بدهکار و بستانکار همیشه معادل کاهش و افزایش نیستند. نام‌های `credit` و `debit` در API تغییر موجودی مشتری را بیان می‌کنند. کلاینت حساب سیستمی دلخواه انتخاب نمی‌کند. حساب تأمین باید در retry ثابت بماند و طبق سیاست fingerprint در هویت مؤثر عملیات ثبت شود.

### افتتاحیه هم عملیات مالی است

projection هر حساب از صفر شروع می‌شود. برای موجودی غیرصفر، عملیات داخلی opening از همان مسیر ثبت حسابداری عبور می‌کند؛ endpoint عمومی پنجم نداریم. شناسهٔ داخلی هم یکتایی سراسری و سیاست تولید بررسی‌شده می‌خواهد.

موجودی غیرصفر را با SQL بدون journal مقداردهی نکنید. حساب صفر می‌تواند journal نداشته باشد. عملیات ردشده هم journal و posting ندارد.

## مرز تراکنش و رفتار هنگام خرابی

CBS03–04 باید پیش از migration، رقابت هویت، isolation و retry کل تراکنش را مشخص کنند. ترتیب پیشنهادی اجرا:

1. هویت عملیات را رزرو یا نتیجهٔ قبلی آن را بازیابی کنید.
2. تمام حساب‌های مشتری و سیستمی درگیر را با ترتیب ثابت قفل کنید.
3. موجودی، ارز و تغییر مبلغ را با محاسبات دارای کنترل overflow بررسی کنید.
4. کامل‌بودن و توازن سند را پیش از ثبت اعتبارسنجی کنید.
5. نتیجهٔ موفق، سند، تمام posting‌ها و projection همهٔ حساب‌ها را در یک تراکنش محلی commit کنید.

outbox از P6 به همین تراکنش اضافه می‌شود. استعلام موجودی، نمای هم‌زمان و commit‌شده را می‌خواند و منتظر Kafka نمی‌ماند.

رد نهایی فقط نتیجهٔ عملیات را ثبت می‌کند و اثر پولی ندارد. خطای فنی پیش از commit باید همهٔ تغییرهای جدید عملیات، journal، posting و projection را rollback کند.

اگر پاسخ پس از commit گم شد، همان شناسهٔ تراکنش پاسخ اصلی را بازیابی می‌کند. replay journal یا posting تازه نمی‌سازد.

اگر رقابت هویت تراکنش را شکست داد، recovery را در تراکنش معتبر تازه انجام دهید. lock order ثابت به‌تنهایی حذف تمام deadlock‌های SQL Server را تضمین نمی‌کند.

### حساب تأمین می‌تواند گلوگاه شود

حتی `credit`های مشتریان متفاوت ممکن است برای یک حساب تأمین مشترک منتظر بمانند. هزینهٔ این رقابت باید اندازه‌گیری شود. تست پیشرفت مستقل را با مجموعه‌هایی اجرا کنید که هیچ حساب مشترکی ندارند؛ مثلاً دو انتقال مستقل. تقسیم حساب تأمین یا تغییر atomicity به تصمیم بررسی‌شده نیاز دارد.

## قیدها، تطبیق و اصلاح

### چه چیزی را constraint تضمین می‌کند؟

پیش از DDL، کلیدها، ارجاع‌های اجباری، یکتایی journal برای operation، نوع حساب، مبلغ مثبت، سمت ثبت و سازگاری ارز را مرور کنید. `CHECK` ردیفی جمع posting‌ها یا کامل‌بودن journal هر موفقیت را تضمین نمی‌کند. این invariant‌های چندردیفی به ساخت journal متوازن، مسیر ثبت واحد، محدودکردن writer‌های دیگر و تست خرابی SQL Server نیاز دارند.

### reconciliation مستقل

reconciliation، یعنی تطبیق تاریخچه با نتیجهٔ ذخیره‌شده، باید این موارد را مستقل بررسی کند:

- توازن هر سند به‌ازای ارز و وجود دقیقاً یک سند برای هر عملیات موفق؛
- نبود سند برای عملیات ردشده و نبود سطر بدون مرجع معتبر؛
- برابری projection هر حساب با کل تاریخچهٔ ثبت‌های آن، شامل افتتاحیه.

برای reconciliation از snapshot سازگارِ commit‌شده یا fixture بدون writer هم‌زمان استفاده کنید. جمع‌ها را با accumulator دقیق و بزرگ‌تر، مثل `BigInteger` یا محاسبات decimal بررسی‌شدهٔ SQL، حساب کنید و بعد بازهٔ `long` را کنترل کنید.

توازن به‌تنهایی ثبت در حساب اشتباه را کشف نمی‌کند. حساب مقصد و نتیجهٔ موردانتظار را هم مستقل بررسی کنید.

### اصلاح و ترمیم

journal و posting‌های commit‌شده append-only هستند. اصلاح مالی با operation و journal معکوس تازه، با هویت مستقل، انجام می‌شود و اصل تاریخچه باقی می‌ماند. endpoint عمومی reversal در V1 چهارعملیاتی نیست.

ترمیم projection به فرایند نگهداری کنترل‌شده و شواهد reconciliation نیاز دارد. تاریخچه و پاسخ قبلی را بی‌صدا بازنویسی نکنید. حذف شناسهٔ نگهداری‌شده هم نباید اجرای دوبارهٔ فرمان را ممکن کند.

smoke test هیچ‌یک را ثابت نمی‌کند. migration کسب‌وکار پیش از مرور constraint‌ها نوشته نمی‌شود. bootstrap فعلی هم کد مالی ندارد که نیازمند جایگزینی باشد.

## نکات کلیدی

- journal متوازن، postingها، projectionها و نتیجهٔ موفق در یک تراکنش commit می‌شوند.
- افتتاحیهٔ غیرصفر هم journal می‌خواهد؛ rejection و replay، journal تازه ندارند.
- reconciliation باید مستقل از مسیر اجرا، موجودی همهٔ حساب‌ها را از تاریخچه بازسازی کند.
- پذیرش طراحی جای SQL Server integration test را نمی‌گیرد.

## گام دامنهٔ posting/journal در CBS05، ۲۰۲۶-۱۰-۲۳

PostingSide و نوع‌های تغییرناپذیر Posting و Journal پیاده شدند. Posting شناسهٔ حساب، سمت و Money مثبت می‌خواهد. balanceDelta(category) برای مشتری CREDIT را مثبت و DEBIT را منفی می‌کند؛ برای تأمین DEBIT مثبت و CREDIT منفی است. این متد ثابت نمی‌کند نوع داده‌شده متعلق به حساب resolveشده است؛ lookup حساب و تطابق ارز در مسیر projection آینده کنترل می‌شوند. مثبت‌بودن مبلغ باعث می‌شود منفی‌کردن حتی Long.MAX_VALUE قابل‌نمایش باشد.

Journal نسخهٔ مستقل و تغییرناپذیر فهرست را می‌گیرد، حداقل دو سطر non-null و یک ارز می‌خواهد و جمع DEBIT/CREDIT را دقیق با BigInteger می‌سنجد. مبلغ مثبت و توازن جمع، وجود هر دو سمت را الزام می‌کند. سند چندسطری و جمع متوازن بزرگ‌تر از long مجاز است؛ این به معنی قرارگرفتن projection حساب در بازه نیست. سند چندارزی در این گام V1 رد می‌شود و FX مرور جدا می‌خواهد.

مثال پیاده‌شده با فرض sourceId/destinationId تایپ‌شده و importهای جاوا:

```java
var amount = new Money(100, Currency.getInstance("IRR"));
var journal = new Journal(List.of(
        new Posting(sourceId, PostingSide.DEBIT, amount),
        new Posting(destinationId, PostingSide.CREDIT, amount)
));
```

این فقط مجموعهٔ معتبر posting می‌سازد. پول جابه‌جا یا حساب قفل نمی‌کند؛ شناسهٔ header/عملیات و commit هم ندارد. هویت ماندگار و ارجاع عملیات در مرحلهٔ بعد می‌آید. پیش از persistence، همهٔ حساب‌ها و ارز آن‌ها بررسی، تغییر خالص هر حساب با accumulator دقیق بزرگ‌تر محاسبه و تمام projectionهای حاصل پیش از نوشتن اعتبارسنجی شوند. اعمال سطرها یکی‌یکی ممکن است با تکرار حساب در سند، نتیجهٔ خالص معتبر را اشتباه رد کند. مجوز دیتابیس همچنان تاریخچهٔ ماندگار را append-only نگه می‌دارد؛ immutability جاوا کافی نیست.

## محاسبهٔ خالص projection در CBS05، ۲۰۲۶-۱۰-۲۳

متد `Journal.projectBalances(Map<AccountId, Account>)` اکنون snapshotهای پیشنهادی تغییرناپذیر را برای حساب‌های شرکت‌کننده در journal محاسبه می‌کند. هر posting را به حساب داخل map وصل می‌کند، حساب غایب، ناسازگاری کلید با شناسه و ناسازگاری ارز را رد می‌کند و نوع حساب واقعی را به `balanceDelta` می‌دهد. حساب اضافه‌ای که posting ندارد در خروجی نمی‌آید؛ حساب شرکت‌کننده با تغییر خالص صفر در خروجی می‌ماند.

تغییرات هر حساب با `BigInteger` دقیق جمع می‌شوند. فقط مقدار نهایی، یعنی ماندهٔ فعلی به‌علاوهٔ تغییر خالص، با `longValueExact` به long تبدیل و با سازندهٔ Account اعتبارسنجی می‌شود. ممکن است تغییر خالص از long بزرگ‌تر باشد ولی ماندهٔ قبلی و جدید حساب تأمین علامت‌دار هر دو در محدوده باشند. اگر هر حسابی نامعتبر باشد خروجی جزئی برنمی‌گردد و snapshotهای ورودی تغییر نمی‌کنند. map خروجی تغییرناپذیر است؛ ترتیب پیمایش آن هیچ تضمینی برای ترتیب قفل ندارد.

یادگیرنده برای موجودی اولیهٔ ۵۰، بدهکار ۱۰۰ و بستانکار ۱۵۰، ماندهٔ نهایی ۱۰۰ ریال را درست پیش‌بینی کرد. سطر سوم برای توازن، بدهکار ۵۰ حساب تأمین است. پیاده‌سازی به‌جای رد ماندهٔ موقت منفی ۵۰، نتیجهٔ نهایی ۱۰۰ را بررسی می‌کند. جابه‌جایی ترتیب postingها نتیجه را تغییر نمی‌دهد. این محاسبهٔ دامنه سیاست رد انتقال به همان حساب در API را عوض نمی‌کند.

فراخوان در آینده باید snapshotهای فعلی را طبق پروتکل پذیرفته‌شدهٔ تراکنش و قفل تهیه کند. این متد ردیف دیتابیس را نمی‌خواند یا قفل نمی‌کند، مجوز نمی‌سنجد، projection ذخیره نمی‌کند و نتیجهٔ نهایی عملیات نمی‌سازد. فعلاً ورودی نامعتبر دامنه IllegalArgumentException، ورودی null خطای NullPointerException و سرریز نهایی ArithmeticException می‌دهد. نگاشت خطا به HTTP و نتیجهٔ کسب‌وکار هنوز در برنامه است.

فرمان Maven verify با Java 21.0.11 در ۸٫۳۵۴ ثانیه، ۹۲ تست را بدون failure، error یا skip گذراند: ۱۳ مورد projection و ۷۹ مورد قبلی. تست‌ها انتقال و اثر نوع حساب، تجمیع حساب تکراری، ترتیب معکوس سطرها، ماندهٔ منفی و سرریز موقت، تغییر خالص بزرگ‌تر از long، سرریز نهایی در هر دو جهت، نامنفی‌بودن مشتری، حساب غایب یا اشتباه، ارز، null و خروجی تغییرناپذیر محدود به شرکت‌کنندگان را پوشش می‌دهند. این شواهد دامنهٔ مستقل از زیرساخت است؛ اتمیک‌بودن یا هم‌زمانی SQL Server را ثابت نمی‌کند. ادامهٔ CBS05 اعتبارسنجی command و مرز شناسهٔ تراکنش، پیش از اتصال HTTP است.

بازآرایی در ۲۰۲۶-۱۰-۲۳: متد projectBalances اکنون سه مرحلهٔ کپی snapshotها، محاسبهٔ دقیق تغییر خالص و ساخت projection حساب‌ها را نشان می‌دهد. متدهای خصوصی پیدا و اعتبارسنجی‌کردن حساب posting، جمع تغییرات، ساخت snapshot نهایی و برگرداندن خروجی تغییرناپذیر را انجام می‌دهند. رفتار عمومی، پیام خطاها و توضیح invariantها حفظ شدند. تست‌های متمرکز دفترکل با Java 21 در ۵٫۵۸۸ ثانیه، ۳۶ مورد را بدون failure، error یا skip گذراندند. مجموعهٔ کامل ۹۲ تست برای این بازآرایی دوباره اجرا نشد.

اعتبارسنجی پیش از انتشار، ۲۰۲۶-۱۰-۲۳: Maven verify با Java 21.0.11 پس از بازآرایی projectBalances همهٔ ۹۲ تست را در ۷٫۲۶۷ ثانیه بدون failure، error یا skip گذراند. محدودیت قبلی اجرای صرفاً متمرکز با این اجرا رفع شد؛ رفتار SQL Server هنوز آزموده نشده است.

## پیاده‌سازی تأییدشدهٔ CBS09، ۲۰۲۶-۱۰-۲۳

V1 چهار جدول ledger در dbo را با کلید مرورشده، CHECK نام‌دار، FK ارز، state پاسخ و index می‌سازد. Flyway با db-migrate صریح اجرا می‌شود و migration عادی runtime غیرفعال است. cbs_migrator جدا مالک schema تاریخچهٔ cbs_migrations با اختیار DDL مرورشدهٔ dbo است؛ cbs_app و cbs_initializer مجوز object/column تست‌شده دارند. schema خصوصی تاریخچه، جزئیات ADR-010 را برای پرهیز از DML کلی کسب‌وکار دقیق‌تر می‌کند. پنجاه تست تازهٔ schema، اجرای کامل را به ۲۴۰ تست مستقل از زیرساخت و ۹۴ تست SQL Server بدون failure، error یا skip در ۱۷٫۸۷۹ ثانیه رساندند. هر دو دیتابیس محلی migrate/validate شدند؛ نبود تنظیمات و مهاجرت با runtime شکست می‌خورند. سلامت برنامه فقط با runtime موفق بود. بازتولید و محدودیت دقیق در [Schema.md](Schema.md) آمده است. گام بعد CBS10، نگاشت‌ها، journal افتتاحیه و موجودی committed است. پذیرش رسمی یادگیرنده جدا می‌ماند.

## پیاده‌سازی persistence و query در CBS10، ۲۰۲۶-۱۰-۲۳

نگاشت چهار جدول روی V1 بدون تغییر validate می‌شود. استعلام موجودی اکنون query projection از SQL Server در تراکنش read-only و HTTP واقعی است؛ mutation همچنان fallback برابر 503 دارد. fixture افتتاحیه فقط در تست، canonical intent، history متوازن، هر دو projection و موفقیت را اتمیک commit می‌کند؛ سه خطای تزریقی در مرز نوشتن کامل rollback می‌شوند. قفل بومی JPA تا پایان تراکنش دارنده حفظ و state قدیمی مدیریت‌شده refresh می‌شود. اجرای کامل ۲۴۰ تست مستقل از زیرساخت و ۱۰۳ تست SQL Server را بدون failure، error یا skip در ۲۳٫۷۶۰ ثانیه گذراند. [Persistence.md](Persistence.md) را ببینید. گام بعد CBS11–12، credit/coordinator/replay ماندگار است؛ پذیرش رسمی یادگیری جداست.
