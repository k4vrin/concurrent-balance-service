# طراحی دفترکل V1

[English](../en/Ledger.md) · [ADR-007 پذیرفته‌شده](../adr/ADR-007-double-entry-ledger.fa.md) · [مرور قیدها](Database-review.md)

کاربر در ۲۰۲۶-۱۰-۲۲ گزینهٔ E را انتخاب کرد. V1 دفترکل دوطرفهٔ چندسطری را در همان دیتابیس SQL Server مربوط به API موجودی دارد. این توسعهٔ طراحی پروژه است و به نیازمندی شرکت نسبت داده نمی‌شود. schema مالی، موتور posting و endpoint مالی هنوز پیاده‌سازی نشده‌اند؛ رفتار و کارایی SQL Server نیز آزموده نشده‌اند.

## مسئولیت چهار جدول

| جدول | مسئولیت |
| --- | --- |
| `accounts` | هویت، نوع، ارز و projection ماندگار موجودی فعلی |
| `operations` | transaction ID سراسری، fingerprint درخواست و پاسخ نهایی موفق یا رد کسب‌وکار |
| `journals` | سرسند حسابداری با ارجاع یکتا به یک عملیات موفق |
| `postings` | سطرهای تغییرناپذیر بدهکار/بستانکار با حساب، سند و مبلغ مثبت در واحد خرد صحیح |

هر تغییر مالی موفق در ابتدا دقیقاً یک journal دارد. هر journal چند posting، دست‌کم یک بدهکار و یک بستانکار و توازن جداگانه به‌ازای ارز دارد. مسیرهای اولیه دو سطر دارند. یک دیتابیس و یک SQL schema کافی است. namespace جدا برای ledger و posting انتخاب سازمان‌دهی است و ضرورت حسابداری نیست. V1 به جدول اضافی `ledger_transactions` یا `transfer_requests` یا سرویس مستقل دفترکل نیاز ندارد. intent، outbox و جدول مصرف‌کننده در مراحل بعد مسئولیت جدا دارند.

## معنای حساب و نمونه

V1 یک ارز مشخص و مبلغ صحیح در بازهٔ Java long دارد. نوع حساب و قواعد علامت در CBS02–05 بازبینی می‌شوند. مدل اولیه حساب بدهی مشتری با ماهیت بستانکار و حساب مقابل تأمین/تسویهٔ انتخاب‌شده توسط سرور با ماهیت بدهکار است. موجودی مشتری برابر بستانکار منهای بدهکار و موجودی حساب مقابل برابر بدهکار منهای بستانکار است. موجودی مشتری منفی نمی‌شود. حساب تأمین/تسویهٔ مصنوعی می‌تواند در بازهٔ long علامت‌دار باشد؛ این سیاست اثبات نقدینگی بیرونی نیست. تسویهٔ واقعی، اضافه‌برداشت و کارمزد تصمیم جدا می‌خواهند.

| عملیات به مبلغ ۱۰۰ | بدهکار | بستانکار |
| --- | --- | --- |
| افزایش موجودی A | تأمین/تسویه ۱۰۰ | مشتری A به مبلغ ۱۰۰ |
| برداشت از A | مشتری A به مبلغ ۱۰۰ | تأمین/تسویه ۱۰۰ |
| انتقال A به B | مشتری A به مبلغ ۱۰۰ | مشتری B به مبلغ ۱۰۰ |
| موجودی افتتاحیهٔ A | تأمین/تسویه ۱۰۰ | مشتری A به مبلغ ۱۰۰ |

بدهکار و بستانکار همیشه به معنی افزایش و کاهش نیستند. نام credit/debit در API تغییر موجودی مشتری را بیان می‌کند. فراخواننده حساب سیستمی دلخواه تعیین نمی‌کند. تنظیم حساب تأمین باید در retry ثابت و طبق سیاست fingerprint در هویت مؤثر عملیات ثبت شود.

projection حساب از صفر شروع می‌شود. افتتاحیهٔ غیرصفر از عملیات داخلی opening و همان مسیر ثبت حسابداری عبور می‌کند و endpoint عمومی پنجم نیست. هویت داخلی نیز یکتایی سراسری و سیاست تولید بررسی‌شده لازم دارد. موجودی غیرصفر با SQL بدون سند ساخته نشود. حساب خالی می‌تواند بدون سند باشد؛ عملیات ردشده journal و posting ندارد.

## مرز تراکنش و خرابی

CBS03–04 پیش از migration رقابت هویت، isolation و retry کل تراکنش را مشخص می‌کنند. هویت عملیات رزرو یا بازیابی شود؛ تمام حساب‌های مشتری و سیستمی با ترتیب ثابت قفل شوند؛ موجودی، ارز و deltaها با حساب checked بررسی شوند. سند کامل و متوازن پیش از ثبت اعتبارسنجی شود. نتیجهٔ موفق، journal، همهٔ postingها و projection تمام حساب‌ها در یک تراکنش محلی commit شوند. outbox فقط از P6 به همین commit اضافه می‌شود. خواندن موجودی از projection هم‌زمان و commitشده است و منتظر Kafka نمی‌ماند.

رد نهایی کسب‌وکار فقط نتیجهٔ عملیات را بدون اثر مالی ثبت می‌کند. خطای فنی پیش از commit همهٔ تغییرات جدید هویت، سند، سطرها و موجودی را rollback می‌کند. پاسخ گمشده پس از commit با همان transaction ID و پاسخ اصلی بازیابی می‌شود. replay سند و posting تازه نمی‌سازد. بعد از شکست تراکنش بر اثر رقابت هویت، بازیابی در تراکنش معتبر جدید باشد. ترتیب قفل به‌تنهایی نبود هر نوع deadlock در SQL Server را ثابت نمی‌کند.

حساب تأمین مشترک می‌تواند حتی برای مشتریان متفاوت گلوگاه قفل باشد. این هزینه اندازه‌گیری شود. تست پیشرفت مستقل از مجموعهٔ کامل حساب‌های مجزا، مثلاً دو انتقال مستقل، استفاده کند. تقسیم حساب تأمین یا تضعیف اتمیک‌بودن تصمیم بررسی‌شده می‌خواهد.

## قید، تطبیق و اصلاح

پیش از DDL، کلیدها، ارجاع‌های اجباری، یکتایی journal برای operation، سیاست نوع حساب، مبلغ مثبت، سمت معتبر و سازگاری ارز بررسی شوند. CHECK معمولی توازن مجموع سطرها یا وجود سند کامل برای موفقیت را تضمین نمی‌کند. ساخت متوازن، مسیر ثبت واحد، محدودکردن writer دیگر و تست خرابی روی SQL Server این قواعد چندردیفی را حفظ می‌کنند.

reconciliation مستقل باید توازن هر سند به‌ازای ارز، یک سند برای هر عملیات موفق، نبود سند برای رد، نبود سطر یتیم و برابری projection هر حساب با تمام تاریخچهٔ posting شامل افتتاحیه را بررسی کند. از snapshot سازگار commitشده یا fixture بدون writer هم‌زمان استفاده شود. جمع با accumulator دقیق و بزرگ‌تر، مانند BigInteger یا محاسبهٔ decimal بررسی‌شدهٔ SQL، انجام و سپس بازهٔ long کنترل شود. توازن به‌تنهایی ثبت در حساب اشتباه را نمی‌گیرد؛ مقصد و نتیجهٔ موردانتظار مستقل نیز تطبیق داده شوند.

journal و posting ثبت‌شده تغییر و حذف نمی‌شوند. اصلاح مالی با عملیات و سند معکوس جدید و هویت مستقل انجام می‌شود و شواهد قبلی می‌مانند. endpoint عمومی reversal در دامنهٔ چهارعملیاتی V1 نیست. تعمیر projection روش نگهداری کنترل‌شده و شواهد تطبیق می‌خواهد؛ تاریخچه یا پاسخ قبلی بی‌صدا بازنویسی نشود. حذف هویت نگهداری‌شده نباید اجرای دوبارهٔ فرمان را ممکن کند.

## تحویل و شواهد

CBS02–04 قید و هویت و تراکنش را مرور می‌کنند؛ CBS05 قواعد دامنه، CBS09 migration چهارجدولی بررسی‌شده، CBS10 mapping و افتتاحیه و خواندن commitشده، CBS11–15 مسیرهای HTTP و CBS16–20 رقابت، rollback، replay و تطبیق مستقل را اضافه می‌کنند. CBS21–22 هزینهٔ خواندن posting، فضا، log و رقابت حساب تأمین را می‌سنجند. هر جلسه یک زیرگام هدایت‌شده باشد؛ checkpoint فعلی CBS00 حفظ می‌شود.

پذیرش به تست واقعی SQL Server با تعداد مثبت، مرز اعداد، عملیات ترکیبی، duplicate دو instance، خرابی پس از نوشتن سطرها و projection، restart و پاسخ گمشده نیاز دارد. smoke test سلامت هیچ‌کدام را ثابت نمی‌کند. migration کسب‌وکار پیش از مرور قیدها اضافه نشود. اسکلت فعلی پیاده‌سازی مالی ندارد که نیاز به جایگزینی داشته باشد.
