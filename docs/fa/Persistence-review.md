[قرارداد پیاده‌سازی](CBS09-contract.md) ذخیره‌سازی، SQL قفل، قیدها، مقدار اولیهٔ retry و اختیار را انتخاب می‌کند. بندهای انتخاب باز در ادامه تاریخی‌اند، مگر در قرارداد حفظ شده باشند. تأیید migration/entity/عملیات مالی در CBS09–20 انجام می‌شود؛ DDL کسب‌وکار اعمال نشده است.

# مرور SQL Server پیش از migration

[English](../en/Persistence-review.md) · [سقف پذیرفته‌شده](Amount-limits.md) · [مرور دیتابیس](Database-review.md) · [پروتکل تراکنش](Transaction-protocol.md) · [راهنمای تست](SQL-server-tests.md)

وضعیت در ۲۰۲۶-۱۰-۲۳: بخشی از مرور CBS02–04 با مشاهدهٔ واقعی SQL Server انجام شده است. migration کسب‌وکار و handler مالی نداریم. پذیرش طراحی ledger و سقف عددی به‌تنهایی معیار persistence را کامل نمی‌کند.

## دلیل این آزمایش‌ها

فرض کنیم دو debit موجودی ۱۰۰ را بخوانند و هرکدام خرج ۸۰ را تأیید کنند. اعتبارسنجی snapshot بدون قفل جلوی هر دو تأیید را نمی‌گیرد. تراکنش باید تا پایان نوشتن journal، projection و نتیجه، موجودی مبنای تصمیم را محافظت کند. بستن result در JDBC پایان تراکنش نیست.

خطر idempotency متفاوت است. Java رشته‌های `transfer-001`، `Transfer-001` و `transfer-001 ` را متفاوت می‌داند. TransactionId مورد سوم را رد می‌کند و بزرگی و کوچکی حروف را حفظ می‌کند. کلید هویت دیتابیس باید در همهٔ مسیرهای مجاز نوشتن با دامنهٔ پذیرفته‌شده سازگار باشد. انتخاب collation به‌تنهایی شواهد کافی نیست.

## چهار مورد تازهٔ integration

[SqlServerProtocolReviewIT](../../src/test/java/dev/kavrin/balance/infrastructure/sqlserver/SqlServerProtocolReviewIT.java) از اتصال تست اختصاصی CBS08 و fixture موقت با نام تولیدشده استفاده می‌کند. فرمان اجرا `./mvnw -Psqlserver-it verify` است. مجوز مدیر، migration یا جدول دائمی نیاز ندارد.

| مورد | نتیجهٔ مشاهده‌شده |
| --- | --- |
| مقایسه با Latin1_General_100_BIN2 صریح | بزرگی و کوچکی حروف تفاوت دارد، ولی فاصلهٔ انتهایی همچنان برابر مقایسه می‌شود. DATALENGTH برای دو رشتهٔ Unicode مقدار ۲۴ و ۲۶ بایت می‌دهد. |
| خواندن عادی READ_COMMITTED | پس از بستن result، اتصال دیگر ردیف را تغییر می‌دهد، درحالی‌که تراکنش خواننده هنوز باز است. خواندن بعدی به‌جای ۷ مقدار ۹ می‌بیند. |
| UPDLOCK/HOLDLOCK و rollback دارنده | خواندن قفل‌دار دوم برای کلید ۱ خطای 1222 می‌دهد. تغییر کلید موجود ۲ در زمان نگه‌داشتن کلید ۱ موفق است. پس از rollback دارنده، خواندن قفل‌دار تازهٔ کلید ۱ موفق می‌شود. |
| UPDLOCK/HOLDLOCK و commit دارنده | همان محافظت و پیشرفت کلید مستقل برقرار است؛ پس از commit دارنده، خواندن قفل‌دار تازه موفق می‌شود. |

query مورد بررسی، جست‌وجوی برابری پارامتری روی کلید اصلی است:

```sql
SELECT probe_value
FROM <generated temporary fixture> WITH (UPDLOCK, HOLDLOCK)
WHERE fixture_id = ?;
```

تست‌ها READ_COMMITTED را صریح انتخاب می‌کنند و کلید fixture عدد صحیح است. UPDLOCK هنگام خواندن، محافظت update می‌خواهد؛ HOLDLOCK برای جدول مربوط در همان تراکنش semantics سطح serializable می‌خواهد. این hintها تضمین نمی‌کنند که فقط ردیف فیزیکی قفل شود. جست‌وجوی کلید اصلی محدودهٔ جست‌وجو را کوچک می‌کند؛ scan، کلید غایب و escalation بررسی جدا می‌خواهند. [راهنمای قفل Microsoft](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver16) را ببینید.

statement و result دارنده پیش از اجرای درخواست رقیب بسته می‌شوند. LOCK_TIMEOUT رقیب ۲۵۰ میلی‌ثانیه است و انتظار socket همان محدودیت harness را دارد. با XACT_ABORT صریحاً OFF، پس از خطای 1222 مقدار XACT_STATE همچنان ۱ است؛ تراکنش باز و قابل‌commit می‌ماند. تست پیش از تلاش تازه آن را rollback می‌کند. کد مالی باید خطای فنی را از callback تراکنش خارج کند و پیش از recovery یا retry، rollback کامل را انجام دهد. تنظیم آزمایش، مقدار timeout انتخابی production نیست.

ترتیب اجرا قطعی است؛ اتصال اول محافظت را می‌گیرد و سپس اتصال دوم درخواست متعارض می‌دهد. به sleep یا زمان‌بندی thread وابسته نیستیم و هم‌پوشانی برقرار است. این آزمایش کوچک پروتکل است؛ load test، تست قربانی deadlock یا اندازه‌گیری throughput نیست.

## قرارداد ذخیره‌سازی هویت هنوز باز است

مشاهدهٔ BIN2 تفاوت حروف را تأیید می‌کند، اما طراحی کامل ستون و قید transaction ID را تعیین نمی‌کند. SQL Server برای برابری رشته‌ها padding انجام می‌دهد؛ این دو رشته با collation باینری هم مشمول آن هستند. تغییر ANSI_PADDING راه‌حل semantics برابری نیست. [قواعد مقایسهٔ Microsoft](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/string-comparison-assignment?view=sql-server-ver16).

طراحی نهایی باید پیش از هر تبدیل اتلافی، کاراکتر بیرون از دامنهٔ ۱ تا ۱۲۸ کاراکتر ASCII شامل حروف، رقم و `._:-` را رد کند. تفاوت حروف باید کلید متفاوت بسازد و duplicate دقیق باید به قید یکتای سراسری با نام مشخص برخورد کند. علاوه بر اعتبارسنجی Java، نوشتن مستقیم و binding پارامتر را تست کنیم. فاصلهٔ ابتدا و انتها، control/NUL، کاراکتر Unicode شبیه ASCII و مرز طول لازم‌اند. مقایسهٔ موفق literal، یکتایی index یا تبدیل امن ستون را ثابت نمی‌کند. آزمایش اولیهٔ مقایسه به‌تنهایی طرح ذخیره‌سازی انتخاب نکرد. [مرور بعدی ذخیرهٔ شناسه](Transaction-id-storage.md) اکنون گزینهٔ فنی تست‌شده دارد؛ معیار کامل migration همچنان باز است.

## معیارهای باقی‌ماندهٔ migration

| مرز | وضعیت و شواهد موردنیاز |
| --- | --- |
| سقف کسب‌وکار | کاربر سقف مشترک 10000000000000 ریالی و رد ماندگار بالاتر از آن را انتخاب کرد. [مثال‌ها](Amount-limits.md) رفتار پذیرفته‌شده را توضیح می‌دهند. evaluator، نگاشت نتیجه و ذخیرهٔ سیاست باقی‌اند. |
| هویت سراسری | canonical bytes مستقل از زیرساخت داریم. [گزینهٔ Unicode BIN2](Transaction-id-storage.md) اکنون قید کاراکتر/طول، یکتایی با نام مشخص و commit/rollback درج رقیب را تأیید می‌کند. نگاشت operations واقعی، تعارض canonical و replay و commit نامطمئن باقی‌اند. |
| قفل حساب | نمونهٔ native JDBC با کلید صحیح تأیید شد. نگاشت UUID، lookup ترتیبی با AccountLockOrder، انتخاب adapter در JPA یا native، کلید غایب، escalation و deadlock باز هستند. |
| قیدهای چهار جدول | DDL نهایی accounts/operations/journals/postings، ارتباط ارز، شکل عملیات و ذخیرهٔ پاسخ و سیاست مرور می‌خواهند. intent ردشدهٔ حساب غایب نباید FK حساب بخواهد؛ posting واقعی باید FK داشته باشد. |
| چرخهٔ تراکنش | coordinator بدون تراکنش محیطی و REQUIRED TransactionTemplate پذیرفته شده است. flush رزرو، commit نشدن PENDING، rollback مرزهای نوشتن، recovery برای commit نامطمئن و تشخیص duplicate با نام قید تست و پیاده‌سازی می‌خواهند. |
| بودجهٔ retry | تعداد تلاش، backoff/jitter، انتظار قفل/دستور/تراکنش/pool و deadline کل انتخاب نشده‌اند. timeout قفل اثبات rollback نیست و خطای اتصال در commit هم اثبات commit نشدن نیست. |
| مجوزها | cbs_app در دیتابیس‌های برنامه همچنان فقط CONNECT دارد. هویت جدا برای migration، اختیار کنترل‌شدهٔ نوشتن مالی و محدودیت تغییر/حذف history مرور شوند. grant تازه نداریم. |
| reconciliation | projection از history با جمع دقیق و بازهٔ عددی بزرگ‌تر و نمای committed سازگار بازسازی شود. درج اتمیک به‌تنهایی توازن history را ثابت نمی‌کند. |

همهٔ نویسنده‌ها، از جمله افتتاح، بستن و ترمیم حساب، باید ترتیب کامل قفل حساب و پروتکل اتمیک ledger را رعایت کنند. ممنوع‌کردن تغییر و حذف history جلوی درج journal نامتوازن از مسیر دیگر را نمی‌گیرد. مسیر مجاز posting و reconciliation بخشی از مرور درستی باقی می‌مانند.

## شواهد ثبت‌شده

اجرای کامل profile با Java 21.0.11 در ۱۲٫۰۶۲ ثانیه **۲۴۰ تست مستقل از زیرساخت و ۹ تست SQL Server** را بدون failure، error یا skip گذراند. چهار مورد تازه ۰٫۸۹۰ ثانیه و پنج مورد CBS08 برابر ۰٫۵۷۳ ثانیه طول کشیدند. این‌ها زمان اجرای تست‌اند و هدف performance نیستند. گزارش‌های XML تازه بررسی شدند.

اجرای اول به‌دلیل محدودیت فایل‌سیستم نتوانست قفل cache در Maven را باز کند و تستی اجرا نکرد. اجرای بعدی با دسترسی مجاز موفق شد. شواهد مربوط به آزمایش موجود SQL Server 2022 CU22 Developer زیر emulation در ARM64 است. استقرار پشتیبانی‌شده روی ARM64، performance تولید، درستی schema حساب، تراکنش مالی کامل، نگاشت قفل JPA یا پذیرش یادگیرنده را ثابت نمی‌کند. مرور موارد بالا پیش از migrationهای CBS09 کامل شود.

## گام مرور شناسهٔ تراکنش، ۲۰۲۶-۱۰-۲۳

گزینهٔ فنی تست‌شده nvarchar(256) با collation صریح BIN2، NOT NULL، قید طول و کاراکتر برای ۱ تا ۱۲۸ کاراکتر و یکتایی سراسری با نام مشخص است. binding از نوع Unicode در JDBC، ورودی نامعتبر را برای ردشدن حفظ می‌کند. سی‌ویک مورد واقعی تازه شامل بررسی همهٔ واحدهای کد منفرد BMP و درج رقیب هستند. اجرای کامل profile با Java 21 در ۱۲٫۷۵۶ ثانیه، ۲۴۰ تست مستقل از زیرساخت و ۴۰ تست SQL Server را بدون failure، error یا skip گذراند؛ کلاس تازه ۲٫۰۹۱ ثانیه طول کشید. [طراحی، SQL، مثال‌ها و محدودیت‌ها](Transaction-id-storage.md) را ببینید. آمار قبلی تاریخی است. migration کسب‌وکار، repository زمان اجرا یا replay ماندگار اضافه نشده است. گام بعد، مرور adapter قفل حساب UUID و قرارداد کامل تراکنش چهار جدول و مجوزهاست؛ پذیرش رسمی یادگیرنده باز می‌ماند.
