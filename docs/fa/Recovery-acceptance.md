# بررسی بازیابی commit و پاسخ در CBS19

[English](../en/Recovery-acceptance.md) · [پروتکل retry](Retry-execution.md) · [پذیرش هسته](Core-acceptance.md)

## مرزهای خطا

خطای پیش از commit نباید operation یا اثر مالی بگذارد. شکست تأیید پس از commit ممکن است نتیجهٔ ماندگار داشته باشد. اگر پاسخ HTTP گم شد، retry همان identity نباید posting دیگری بسازد. این مرزها هم برای موفقیت و هم برای رد ماندگار لازم‌اند.

`SqlServerRecoveryIT` با دو context و pool مستقل HTTP، بیست‌وچهار تست واقعی SQL Server اضافه می‌کند. wrapperهای مخصوص تست مرز خطا را انتخاب می‌کنند؛ transaction manager، نوشتن SQL، history ماندگار و بازسازی مستقل واقعی می‌مانند.

| خطا | حالت‌ها | نتیجهٔ مورد انتظار |
| --- | --- | --- |
| پیش از commit | هر mutation، موفقیت/رد | delegate تراکنش واقعی را rollback می‌کند و بعد خطا می‌دهد. درخواست اول 503 با صفر operation/history و موجودی بدون تغییر می‌دهد؛ retry همان ID از برنامهٔ دیگر یک بار کامل می‌شود. |
| پس از commit | هر mutation، موفقیت/رد | delegate تغییر واقعی را commit می‌کند و سپس خطا می‌دهد. بازیابی تازه outcome اصلی را می‌دهد؛ رزرو دوم نداریم. |
| نتیجهٔ بازیابی پنهان | هر mutation، موفقیت/رد | بعد از commit واقعی، سه خواندن واقعی بازیابی عمداً غایب نمایش داده می‌شوند. درخواست بدون اجرای دوباره 503 می‌دهد. retry از برنامهٔ دیگر نتیجهٔ commit‌شده را بازیابی می‌کند. |
| پاسخ HTTP جایگزین‌شده | هر mutation، موفقیت/رد | filter تست پاسخ کامل واقعی را buffer و با HTTP 503 جایگزین می‌کند. برنامهٔ دیگر status و بایت‌های اصلی ماندگار را با یک اثر برمی‌گرداند. |

هر حالت برای درخواست خطادار یک رزرو می‌خواهد. موفقیت یک operation، یک journal متوازن و دو posting دارد؛ رد یک operation و هیچ history مالی ندارد. SQL مستقل همهٔ موجودی‌های مرتبط را با مجموع دقیق postingها بررسی می‌کند. دستور ردشده بعد از شارژ هم همان نتیجه را replay می‌کند. انتخاب counterpart و identity در مسیر تولیدی بدون تغییر می‌مانند.

## بررسی

اجرای متمرکز، ۲۴ تست SQL Server و ۴۲۱ تست قابل‌حمل را در 24.980 ثانیه گذراند. اجرای کامل Java 21 و Maven با `-Psqlserver-it verify` در ۲۰۲۶-۱۰-۲۹، **۴۲۱ تست قابل‌حمل + ۲۱۲ تست واقعی SQL Server** را با **صفر failure/error/skip** در **01:05 min** گذراند. جمع XMLهای تازهٔ Surefire/Failsafe بررسی شد.

این‌ها شبیه‌سازی کنترل‌شدهٔ تأیید، visibility خواندن و پاسخ HTTP پیرامون اثر واقعی دیتابیس‌اند. قطع فیزیکی TCP در دستور دقیق commit یا جداسازی crash بین hostها ادعا نمی‌شود. سناریوی process مستقل بسته‌بندی‌شده در [CBS20](Core-acceptance.md)، timeout واقعی قفل/rollback، retry همان ID و بازیابی پس از restart را بدون این wrapperها اضافه می‌کند.
