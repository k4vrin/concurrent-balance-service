# ماتریس نیازمندی و خطای V1

[English](../en/Requirements.md) · [قرارداد API](API-v1.md) · [تصمیم‌ها](Decisions.md) · [مرور قیدها](Database-review.md) · [نتیجهٔ کسب‌وکار و مرز commit](Operation-outcomes.md)

وضعیت در ۲۰۲۶-۱۰-۲۲: خروجی طراحی CBS01 با کمک دستیار و بر اساس گفت‌وگو و roadmap مخزن. رفتار مالی و تست‌های این ماتریس هنوز پیاده یا تأیید نشده‌اند. متن اصلی چالش را برای این سند مستقلاً بازبینی نکرده‌ایم؛ مبنا همان چهار عملیات ثبت‌شده در مخزن است. همهٔ سیاست‌های این سند الزام کارفرما نیستند.

## حالت‌ها و شواهد پیشنهادی

برای مثال، درخواست برداشتِ معتبر ممکن است به‌دلیل کسری موجودی رد شود. این رد باید با شناسه، fingerprint و پاسخ اصلی در `operations` commit شود، بدون اینکه پول جابه‌جا شود. بعداً همان درخواست باید همان پاسخ را بگیرد.

در موفقیت، تمام projection‌ها و یک journal متوازن با حداقل دو posting تغییرناپذیر با هم ثبت می‌شوند. replay journal تازه نمی‌سازد. این قواعد مخصوص mutation‌ها هستند؛ GET موجودی عملیات مالی ثبت‌شده نمی‌سازد.

### حساب ناموجود و foreign key

برای ذخیرهٔ رد حساب ناموجود، شناسهٔ داخل درخواست نباید به وجود حساب وابسته باشد. CBS02 باید آن را از ارجاع posting موفق جدا کند. به همهٔ فیلدهای درخواست، بدون بررسی، foreign key حساب اضافه نکنید.

## سیاست‌ها و معیارهای باز

- سقف تجاری جدا برای مبلغ تراکنش پذیرفته شده، اما عدد و معنای تنظیماتش هنوز باز است. `Long.MAX_VALUE` جای این سیاست را نمی‌گیرد. سقف قانونی را حدس نزنید؛ سقف تجاری موجودی هم هنوز تعیین نشده است.
- عبور از سقف تنظیم‌شده باید یا خطای admission validation باشد یا تصمیم کسب‌وکار ماندگار؛ این انتخاب هنوز باز است. رفتار replay پس از تغییر سیاست را مشخص کنید. برای عملیات موجود، پیش از بررسی دوبارهٔ قواعد متغیر، هویت ذخیره‌شده را بخوانید.
- شناسهٔ حساب اکنون UUID و ترتیب قفل برنامه مقایسهٔ unsigned نزولی ۱۲۸ بیتی است. قالب/مقایسهٔ transaction ID و encoding fingerprint هنوز مرور می‌خواهند؛ parsing ورودی UUID در HTTP و نگاشت/قفل SQL پیاده نشده‌اند.
- ذخیرهٔ رد حساب ناموجود، یکتایی رابطهٔ operation و journal و append-only بودن در CBS02–04 طراحی می‌شوند. پیش از این مرورها migration مالی ننویسید.
- تست‌های جدول هنوز برنامه‌اند. مرور شفاهی هدایت‌شده و این ماتریس، پیاده‌سازی مستقل یا پذیرش کامل CBS01 را ثابت نمی‌کنند. بخش باقی‌ماندهٔ مرور مستقل و تمرین PR در CBS00 هم شواهد جدا می‌خواهد.

## پیاده‌سازی جزئی CBS05، ۲۰۲۶-۱۰-۲۳

نوع `Money(long amount, Currency currency)` جایگزین RialAmount مثبت‌محور شد. ارز java.util.Currency باید non-null باشد و مقدار long مستقیم حفظ می‌شود. برای IRR، عدد 100 یعنی ۱۰۰ ریال. صفر و مقدار علامت‌دار قابل‌نمایش‌اند؛ مثبت‌بودن مبلغ دستور/posting جدا و هنوز باز است؛ سیاست علامت موجودی نوع حساب اکنون مستقل پیاده شده است. metadata ارز مبلغ را تبدیل نمی‌کند. تبدیل FX یا پشتیبانی ارز دیگر در API اضافه نشده است. تست مرزی هر دو انتهای long، مثبت، صفر، منفی، حفظ 100 IRR و ارز ناموجود را پوشش می‌دهد. Money اکنون جمع و تفریق هم‌ارز با کنترل overflow و مقایسهٔ هم‌ارز بدون تفریق پرخطر دارد. اعتبارسنجی JSON، سقف تجاری، سند، تراکنش و قید SQL هنوز باز هستند.

شاهد ۲۰۲۶-۱۰-۲۳: اجرای Java 21 `clean verify` نه تست، صفر failure/error/skip داشت؛ هشت حالت Money و تست HTTP سلامت قبلی.

شاهد محاسبه در ۲۰۲۶-۱۰-۲۳: Maven `verify` با Java 21 بیست تست و صفر failure/error/skip داشت؛ ۱۹ حالت Money و تست HTTP سلامت. نتیجهٔ صفر/علامت‌دار، مرز دقیق، overflow دو جهت، ارز متفاوت، operand تهی، مرز مقایسه و تغییرناپذیری ورودی بررسی شدند. رفتار دیتابیس تست نشده است.

گام نوع حساب در ۲۰۲۶-۱۰-۲۳: `AccountCategory.validateBalance(Money)` موجودی منفی CUSTOMER_LIABILITY را رد و موجودی علامت‌دار FUNDING_CLEARING مصنوعی را قبول می‌کند. موجودی برای هر دو نوع non-null است. این سیاست فقط یک مقدار را بررسی می‌کند؛ شیء حساب، محاسبهٔ سمت posting، سقف تجاری، نگاشت خطای HTTP، قفل یا تغییر دیتابیس پیاده نشده‌اند.

شاهد سیاست حساب در ۲۰۲۶-۱۰-۲۳: Maven `verify` با Java 21، سی‌ودو تست و صفر failure/error/skip داشت؛ ۱۲ حالت AccountCategory، نوزده Money و یک تست HTTP سلامت. اعتبارسنجی AccountCategory هنوز به مدل حساب یا use case مالی متصل نشده است.

گام مدل حساب در ۲۰۲۶-۱۰-۲۳: `Account(AccountId, AccountCategory, Money)` تغییرناپذیر است و فیلدهای اجباری و سیاست موجودی را در سازنده کنترل می‌کند. `applyBalanceDelta(Money)` ارز و overflow را با Money بررسی و نتیجه را با نوع حساب اعتبارسنجی می‌کند؛ snapshot تازه می‌دهد و اصل را تغییر نمی‌دهد. delta تغییر علامت‌دار داخلی projection است، نه مبلغ مثبت انتقال یا سمت DEBIT/CREDIT حسابداری. AccountId اکنون UUID غیرnull می‌خواهد و AccountLockOrder.DESCENDING ترتیب مشترک پذیرفته‌شده را فراهم می‌کند؛ parsing HTTP و قفل واقعی SQL هنوز باز هستند. ساخت snapshot غیرصفر نمایش وضعیت است و افتتاحیهٔ پولی در دیتابیس ایجاد نمی‌کند. سند افتتاحیه، posting متوازن، قفل و persistence اتمیک همچنان لازم و پیاده‌نشده‌اند. exception دامنه هنوز نگاشت HTTP یا نتیجهٔ کسب‌وکار ماندگار ندارد.

شاهد مدل حساب در ۲۰۲۶-۱۰-۲۳: Maven `verify` با Java 21، پنجاه‌وپنج تست و صفر failure/error/skip داشت؛ ۱۶ Account، هفت AccountId، دوازده AccountCategory، نوزده Money و یک تست HTTP سلامت. تغییر تا صفر، رد اضافه‌برداشت، تغییر علامت حساب تأمین، null، تفاوت ارز، overflow و تغییرناپذیری بررسی شدند. شاهد SQL Server نیست.

هویت UUID حساب در ۲۰۲۶-۱۰-۲۳: `AccountId(UUID)` جای شناسهٔ String را گرفت. `AccountLockOrder.DESCENDING` نیمهٔ بالایی و سپس پایینی را unsigned و نزولی مقایسه می‌کند. این فقط ترتیب است؛ repository یا قفل اجرا نشده است. بعداً تمام حساب‌های یکتای درگیر، شامل تأمین، طبق همین سیاست مرتب و پشت سر هم قفل شوند. transaction ID هویت جدا و ورودی کلاینت می‌ماند. UUID مجوز یا وجود حساب را ثابت نمی‌کند. نگاشت uniqueidentifier و index در مرور persistence بررسی می‌شود.

شاهد UUID/ترتیب در ۲۰۲۶-۱۰-۲۳: Maven verify با Java 21 پنجاه‌وشش تست و صفر failure/error/skip داشت؛ شش ترتیب، دو هویت UUID، شانزده Account، دوازده نوع حساب، نوزده Money و یک smoke. تست شناسهٔ String جایگزین شده، نه skip. مرز unsigned هر دو نیمه، برابری، ترتیب دو جهت، حدود/تعدی و null بررسی شدند.

گام دامنهٔ دفترکل: Posting مبلغ مثبت و فیلد اجباری را کنترل می‌کند و علامت delta به نوع حساب وابسته است. Journal مجموعهٔ تغییرناپذیر تک‌ارزی با حداقل دو سطر و توازن دقیق BigInteger را می‌سنجد. آماده‌سازی خالص projection هر حساب، تطابق ارز حساب واقعی، هویت عملیات/header و persistence هنوز باز هستند. مثال و مرز اجرا در Ledger.md آمده است.

شاهد دامنهٔ دفترکل در ۲۰۲۶-۱۰-۲۳: Maven verify با Java 21 هفتادونه تست و صفر failure/error/skip داشت؛ یازده Journal، دوازده Posting و پنجاه‌وشش حالت قبلی. توازن چندسطری، فهرست تغییرناپذیر، تک‌ارزی، delta وابسته به ماهیت، جمع دقیق فراتر از long و رد عدم‌توازن پنهان‌شده با overflow بررسی شدند. دیتابیس تست نشده است.

## محاسبهٔ خالص projection در CBS05، ۲۰۲۶-۱۰-۲۳

متد `Journal.projectBalances(Map<AccountId, Account>)` اکنون snapshotهای پیشنهادی تغییرناپذیر را برای حساب‌های شرکت‌کننده در journal محاسبه می‌کند. هر posting را به حساب داخل map وصل می‌کند، حساب غایب، ناسازگاری کلید با شناسه و ناسازگاری ارز را رد می‌کند و نوع حساب واقعی را به `balanceDelta` می‌دهد. حساب اضافه‌ای که posting ندارد در خروجی نمی‌آید؛ حساب شرکت‌کننده با تغییر خالص صفر در خروجی می‌ماند.

تغییرات هر حساب با `BigInteger` دقیق جمع می‌شوند. فقط مقدار نهایی، یعنی ماندهٔ فعلی به‌علاوهٔ تغییر خالص، با `longValueExact` به long تبدیل و با سازندهٔ Account اعتبارسنجی می‌شود. ممکن است تغییر خالص از long بزرگ‌تر باشد ولی ماندهٔ قبلی و جدید حساب تأمین علامت‌دار هر دو در محدوده باشند. اگر هر حسابی نامعتبر باشد خروجی جزئی برنمی‌گردد و snapshotهای ورودی تغییر نمی‌کنند. map خروجی تغییرناپذیر است؛ ترتیب پیمایش آن هیچ تضمینی برای ترتیب قفل ندارد.

یادگیرنده برای موجودی اولیهٔ ۵۰، بدهکار ۱۰۰ و بستانکار ۱۵۰، ماندهٔ نهایی ۱۰۰ ریال را درست پیش‌بینی کرد. سطر سوم برای توازن، بدهکار ۵۰ حساب تأمین است. پیاده‌سازی به‌جای رد ماندهٔ موقت منفی ۵۰، نتیجهٔ نهایی ۱۰۰ را بررسی می‌کند. جابه‌جایی ترتیب postingها نتیجه را تغییر نمی‌دهد. این محاسبهٔ دامنه سیاست رد انتقال به همان حساب در API را عوض نمی‌کند.

فراخوان در آینده باید snapshotهای فعلی را طبق پروتکل پذیرفته‌شدهٔ تراکنش و قفل تهیه کند. این متد ردیف دیتابیس را نمی‌خواند یا قفل نمی‌کند، مجوز نمی‌سنجد، projection ذخیره نمی‌کند و نتیجهٔ نهایی عملیات نمی‌سازد. فعلاً ورودی نامعتبر دامنه IllegalArgumentException، ورودی null خطای NullPointerException و سرریز نهایی ArithmeticException می‌دهد. نگاشت خطا به HTTP و نتیجهٔ کسب‌وکار هنوز در برنامه است.

## اعتبارسنجی شناسهٔ تراکنش در CBS05، ۲۰۲۶-۱۰-۲۳

یادگیرنده رد `" transfer-001 "` را به‌جای trim و تبدیل آن به شناسهٔ موجود انتخاب کرد. `operation.domain.TransactionId` اکنون قالب پایهٔ مستندشده را پیاده می‌کند: ۱ تا ۱۲۸ حرف یا رقم ASCII و نشانه‌های `.`, `_`, `:`, `-`. شناسه دقیق، حساس به بزرگی حروف و بدون نرمال‌سازی است. متن شبیه UUID پذیرفته می‌شود ولی به UUID تبدیل نمی‌شود و اجباری هم نیست. AccountId نوع جداگانهٔ مبتنی بر UUID می‌ماند.

```java
new TransactionId("transfer-001");   // valid, preserved exactly
new TransactionId("Transfer-001");   // valid, distinct identity
new TransactionId(" transfer-001 "); // IllegalArgumentException
```

ورودی null خطای NullPointerException و قالب نامعتبر IllegalArgumentException می‌دهد. این value object شناسه رزرو نمی‌کند، دستورها را مقایسه نمی‌کند، پاسخ را replay نمی‌کند و یکتایی دیتابیس را تضمین نمی‌کند. مسیر HTTP و coordinator هنوز متصل نشده است؛ در آن مسیر باید پیش از رزرو، شناسهٔ معتبر ساخته شود. مقایسه و collation در SQL Server باید بعداً با هویت دقیق و حساس به بزرگی حروف هماهنگ و روی SQL Server آزموده شوند. پذیرش رد فاصله، تأیید باقی پیش‌نویس fingerprint، ذخیره‌سازی یا recovery نیست.

## commandهای نوع‌دار مالی در CBS05، ۲۰۲۶-۱۰-۲۳

ورودی‌های پیاده‌شدهٔ application عبارت‌اند از `CreditCommand(TransactionId, AccountId, Money)`، `DebitCommand(TransactionId, AccountId, Money)` و `TransferCommand(TransactionId, AccountId sourceAccountId, AccountId destinationAccountId, Money)`. این recordهای تغییرناپذیر در `operation.application` قرار دارند و از DTO مربوط به JSON و entity دیتابیس مستقل‌اند. شناسه‌ها و مبلغ باید غیرnull، مبلغ مثبت و ارز IRR باشد. برای انتقال، مقدار UUID دو حساب هم باید متفاوت باشد. helper داخلی CommandValidation قاعدهٔ مشترک مبلغ را نگه می‌دارد؛ پشتیبانی Money از صفر، عدد علامت‌دار و ارزهای دیگر تغییر نمی‌کند.

مثال با فرض وجود sourceId و destinationId نوع‌دار:

```java
var command = new TransferCommand(
        new TransactionId("transfer-001"), sourceId, destinationId,
        new Money(100, Currency.getInstance("IRR")));
```

ساخت command شناسه رزرو نمی‌کند و پول جابه‌جا نمی‌کند. adapter یا coordinator آینده باید آن را پیش از رزرو بسازد. فیلد غایب فعلاً NullPointerException می‌دهد؛ مبلغ نامثبت، ارز نامجاز و انتقال به همان حساب IllegalArgumentException می‌دهند. مقایسهٔ مقدار AccountId انتقال به خود را حتی با دو wrapper جدا تشخیص می‌دهد. BalanceService اولیه همچنان اسکلت متصل‌نشده است؛ این گام handler یا API مالی ثبت نمی‌کند. commandهای credit/debit فقط حساب مشتری را دارند؛ انتخاب حساب تأمین در مسیر اجرای آینده با سرور است.

وجود حساب، مجوز، کفایت موجودی و سرریز projection نهایی در این سازنده‌ها بررسی نمی‌شوند. درخواست با ساختار معتبر و حساب غایب همچنان به مسیر رد نهایی پذیرفته‌شده نیاز دارد. مبلغ اعشاری، عدد بیرون از long و متن UUID نامعتبر باید در parser آیندهٔ HTTP رد شوند؛ Money مبتنی بر long نمی‌تواند همان ورودی JSON نامعتبر را نمایش دهد. Long.MAX_VALUE در مرز نمایش پذیرفته می‌شود؛ مقدار سقف کسب‌وکار و طبقه‌بندی آن در سیاست قابل‌تغییر و replay هنوز باز است و پیش از اجرای مالی باید مرور شود. بیشینهٔ نوع داده سقف کسب‌وکار نیست.

## اصلاح سیاست ارزهای پشتیبانی‌شده، ۲۰۲۶-۱۰-۲۳

به درخواست کاربر، ارزهای مجاز دیگر داخل CommandValidation یا سازندهٔ commandها ثابت نیستند. `CommandValidation.requirePositiveAmount` فقط وجود و مثبت‌بودن مبلغ را بررسی می‌کند. CreditCommand، DebitCommand و TransferCommand ارز Money را برای سیاست جداگانهٔ `SupportedCurrencies(Set<Currency>)` حفظ می‌کنند. این تصمیم محدودیت قبلی IRR در سازنده‌ها را جایگزین می‌کند. سیاست استقرار اولیهٔ V1 همچنان IRR است؛ validator مبتنی بر مجموعه، تبدیل FX یا واحد ارزهای دیگر را تعریف نمی‌کند.

SupportedCurrencies از مجموعهٔ ورودی کپی تغییرناپذیر می‌سازد و متد `requireSupported(Currency)` دارد. ارز مجاز از ورودی می‌آید و داخل کد اعتبارسنجی production ثابت نیست. مجموعه، عضو یا ارز null رد می‌شود؛ مجموعهٔ صریحاً خالی همهٔ ارزها را غیرفعال می‌کند. تغییر مجموعهٔ اصلی، snapshot قبلی سیاست را عوض نمی‌کند. در آینده تنظیمات یا adapter دیتابیس می‌تواند snapshot تازه بدهد؛ سیاست وارد payload دستور نمی‌شود و سازندهٔ value object هم دیتابیس نمی‌خواند. loader، جدول یا bean زمان اجرا هنوز پیاده نشده است.

نمونهٔ اتصال با مجموعهٔ سیاست ورودی، پیش از اجرا:

```java
var policy = new SupportedCurrencies(currenciesFromConfiguration);
policy.requireSupported(command.amount().currency());
```

coordinator آینده باید پیش از ارزیابی دوبارهٔ این سیاست قابل‌تغییر، نتیجهٔ نهایی موجود را پیدا کند. retry منطبق باید حتی پس از غیرفعال‌شدن ارز، نتیجهٔ اصلی را replay کند. برای عملیات تازه، پشتیبانی ارز با یک snapshot سازگار و پیش از رزرو بررسی می‌شود. قالب معتبر ارز با مجازبودن در سیاست فعلی فرق دارد. خرابی بارگذاری دیتابیس خطای فنی است؛ نباید آن را مجموعهٔ خالی یا تصمیم نهایی رد ارز تعبیر کرد. پروتکل بارگذاری و تازه‌سازی سیاست هنوز به طراحی و تست اتصال نیاز دارد.

Maven verify با Java 21.0.11 در ۷٫۵۶۵ ثانیه، ۱۳۷ تست را بدون failure، error یا skip گذراند. نُه مورد سیاست، چند ارز مجاز، رد ارز بیرون از مجموعه، مجموعهٔ بدون IRR، مجموعهٔ خالی و null و snapshot تغییرناپذیر را می‌سنجند. سیزده تست command اکنون حفظ ارز را به‌جای رد ثابت ارز بررسی می‌کنند. HTTP، ترتیب replay و بارگذاری سیاست از دیتابیس هنوز پیاده نشده‌اند؛ این شواهد اعتبارسنجی مستقل از زیرساخت است.
