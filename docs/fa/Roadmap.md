> بخش فعلی CBS17، ۲۰۲۶-۱۰-۲۹: [رقابت transaction ID بین instanceها](Cross-instance-replay.md) اکنون ۱۶ تست هماهنگ HTTP/SQL با شاهد واقعی تعارض constraint نام‌دار، پاسخ ماندگار و reconciliation دارد. regression کامل با ۴۲۱ تست قابل‌حمل و ۱۷۸ تست واقعی SQL Server و صفر failure/error/skip موفق بود. انتقال معکوس، پیشرفت مستقل و faultهای گسترده‌تر در CBS18–19 می‌مانند.

> بخش فعلی CBS16، ۲۰۲۶-۱۰-۲۹: [mutationهای هم‌زمان با ID متفاوت](Concurrency-execution.md) اکنون پنج تست هماهنگ HTTP تا SQL Server، شمارش دقیق outcome/history و reconciliation مستقل پیش و پس از replay دارند. regression کامل با ۴۲۱ تست قابل‌حمل و ۱۶۲ تست واقعی SQL Server و صفر failure/error/skip موفق بود. رقابت بین instanceها و معیارهای بعدی CBS17–19 باز می‌مانند.

> به‌روزرسانی فعلی CBS15، ۲۰۲۶-۱۰-۲۹: [retry محدود تراکنش و بازیابی نتیجهٔ نامعلوم](Retry-execution.md) برای credit، debit و transfer پیاده شد. بررسی کامل با ۴۲۱ تست قابل‌حمل و ۱۵۷ تست واقعی SQL Server و صفر failure/error/skip موفق بود. مرحلهٔ بعد شواهد گسترده‌تر concurrency و بازیابی در CBS16–19 است؛ پذیرش یادگیری مستقل می‌ماند.

> به‌روزرسانی CBS14، ۲۰۲۶-۱۰-۲۶: [انتقال اتمیک](Transfer-execution.md) کنار credit، debit و استعلام موجودی مرجع پیاده شده است. regression کامل، ۳۸۵ تست قابل‌حمل و ۱۵۴ تست واقعی SQL Server، شامل هر ۲۰ تست انتقال را با صفر failure/error/skip گذراند. معیارهای retry، رقابت گسترده‌تر و پذیرش مستقل یادگیری باز هستند. گفته‌های قبلی دربارهٔ unavailable بودن مسیرها در ادامه تاریخی‌اند.

> به‌روزرسانی CBS13، ۲۰۲۶-۱۰-۲۵: [debit ماندگار](Debit-execution.md) کنار credit با فعال‌سازی صریح و استعلام موجودی مرجع پیاده شده است. انتقال تا CBS14 unavailable می‌ماند. اجرای کامل ۳۵۱ تست مستقل و ۱۳۴ تست واقعی SQL Server را با صفر failure/error/skip گذراند. گفته‌های قدیمی pending/unavailable در ادامه تاریخی‌اند.

> مرحلهٔ فعلی credit، ۲۰۲۶-۱۰-۲۴: [credit ماندگار](Credit-execution.md) و بخش نخست replay/conflict با قبولی ۳۰۵ تست مستقل از زیرساخت و ۱۲۰ تست SQL Server پیاده شده‌اند. debit/transfer و پذیرش گسترده‌تر retry، شکست و عملیات ترکیبی باز هستند. توضیح تاریخی CBS08–10 در ادامه دامنهٔ کل suite فعلی نیست.

> به‌روزرسانی bootstrap در ۲۰ اکتبر ۲۰۲۶: SQL Server جای هدف پیشنهادی قبلی Oracle را گرفته است. P0 شروع شده و کامل نیست. وجود وابستگی‌ها و موفقیت تست سلامت، صحت مالی را ثابت نمی‌کنند.

مثلاً وجود dependency مربوط به Kafka، مرحلهٔ رویدادها را کامل نمی‌کند. آن مرحله باید خرابی broker، duplicate و recovery را هم با تست نشان دهد.

### اندازهٔ PR‌ها

P1 به قرارداد و پایهٔ HTTP، schema، موجودی، credit، debit، transfer و تست concurrency/API تقسیم می‌شود. هر عملیات مالی یک vertical slice کامل از HTTP تا SQL Server است.

P6 هم PR جدا برای outbox، publisher، consumer و failure test دارد. نام شاخه‌های جدول نمونه‌اند و ایجادشدن شاخه را نشان نمی‌دهند.

## baseline چالش

### چهار عملیات و مبلغ

V1 معنای `credit`، `debit`، `transfer` و `getBalance` را از [HTTP API](API-v1.md) ارائه می‌کند. interface فعلی bootstrap داخلی است؛ امضاهایش می‌توانند تغییر کنند و مرز release نیستند. شناسهٔ رشته‌ای حساب می‌تواند داخل برنامه به نوع مشخص تبدیل شود.

IRR با `long` و واحد ریال مدل می‌شود؛ هر واحد یک ریال است، مبلغ باید مثبت باشد و overflow کنترل شود. سیاست پولی در Decisions.md آمده است. افتتاحیهٔ غیرصفر فقط با عملیات opening و posting متوازن طبق Ledger.md ثبت می‌شود. انتقال موفق دقیقاً همان مبلغ را میان دو حساب موجود و متفاوت جابه‌جا می‌کند.

### شناسه، fingerprint و replay

شناسهٔ تراکنش در نسخهٔ تک‌مستأجر میان همهٔ نوع‌های عملیات یکتاست. payload یا نوع متفاوت با همان شناسه conflict می‌گیرد. fingerprint شامل نوع عملیات، حساب‌ها، مبلغ، ارز و بعد از افزودن احراز هویت، actor است.

راز OTP، زمان retry و correlation ID وارد fingerprint نمی‌شوند. پیش از replay، مجوز فعلی را بررسی کنید. ADR-002 replay رد کسب‌وکار و retry خطای موقت را جدا تعریف می‌کند.

### تست‌های P1

- credit هم‌زمان، debit رقابتی و ترکیب هر سه mutation؛
- duplicate هم‌زمان هر mutation و همان شناسه با درخواست متفاوت؛
- انتقال خلاف جهت و پیشرفت حساب مستقل هنگام قفل حساب دیگر؛
- حساب ناموجود، مبلغ نامعتبر، self-transfer، overflow و rollback.

از barrier یا latch، انتظار محدود و جمع‌آوری exception‌های worker استفاده کنید. load test همهٔ interleaving‌های ممکن را ثابت نمی‌کند.

## مرز توسعه‌ها

### امنیت پیش از دسترسی مشترک

V1 در کنار تست سرویس و SQL، HTTP integration test دارد. API اولیه روی loopback و برای اپراتور مورداعتماد توسعه است. P3 پیش از دسترسی اشتراکی یا خارجی، احراز هویت، مالکیت، role، مجوز credit/debit و مجوز replay را اضافه می‌کند.

P4 نباید endpoint دیگری برای bypass تأیید باقی بگذارد. credit/debit پیش از دسترسی مشتری، عملیات privileged می‌شوند.

### تأیید انتقال

OTP یک intent مشخص را تأیید می‌کند؛ جای idempotency، مالکیت یا funds check را نمی‌گیرد. ساخت intent در پیشنهاد فعلی پول رزرو نمی‌کند. موجودی در confirm دوباره بررسی می‌شود و ممکن است کافی نباشد.

### cache و رویداد

Redis پاسخ نهایی immutable را سریع‌تر برمی‌گرداند، اما تصمیم نمی‌گیرد که پول باید تازه جابه‌جا شود یا نه. Kafka واقعیت commit‌شده را حمل می‌کند و مجری عملیات synchronous موجودی نیست. تاریخچهٔ consumer با تأخیر به‌روز می‌شود و مرجع endpoint موجودی نیست.

### CDC مشروط است

Debezium بعد از polling outbox بررسی می‌شود. راه‌اندازی CDC روی SQL Server شواهد عملی می‌خواهد. P7 یک feasibility gate است؛ اگر سازگاری یا دسترسی کافی نبود، polling publisher آزموده‌شده باقی می‌ماند و دلیل ثبت می‌شود.

## اولین خروجی اجرایی

1. پیش از migration اول، ADR-001 تا ADR-003 و جدول مرور دیتابیس را بررسی کنید.
2. با bootstrap موجود Java 21 و Spring Boot و Maven، قرارداد HTTP و مسیرهای کامل موجودی، credit، debit و transfer تا SQL Server را بسازید.
3. baseline آزموده‌شدهٔ P1/P2 را جدا tag کنید تا feature‌های اختیاری، تکمیل چالش را مبهم نکنند.

## مسیر باقی‌مانده تا اولین نسخهٔ پذیرفته‌شده، ۲۰۲۶-۱۰-۲۳

هدف اولین پذیرش، هستهٔ منتخب چالش در CBS20/G1 همراه HTTP در CBS23 است. این معیار پذیرش پروژهٔ ماست؛ تأیید شرکت یا آمادگی production را تضمین نمی‌کند. دامنهٔ منتخب دفترکل، SQL و API از interface اولیهٔ چالش گسترده‌تر است. مدل‌های دامنه، command معتبر، snapshot سیاست ارز و نوع نتیجه موجودند؛ اجرای مالی HTTP، schema و صحت واقعی دیتابیس هنوز پیاده نشده‌اند.

| ترتیب | کارها | خروجی باقی‌مانده و شاهد پذیرش |
| --- | --- | --- |
| ۱ | CBS23 سپس CBS06 | تعریف DTO درخواست و پاسخ، parse سخت‌گیرانهٔ JSON و UUID و مبلغ، خطاهای ثابت و جداسازی HTTP از command؛ مقایسهٔ canonical نسخه‌دار. تست قرارداد جای اجرای ماندگار را نمی‌گیرد. |

| ۳ | تکمیل CBS02–04 و CBS09 | مرور نهایی قید و تراکنش پیش از migration؛ شامل سقف کسب‌وکار و طبقه‌بندی آن، collation، SQL قفل و مجوز زمان اجرا. ساخت accounts، operations، journals و postings و تست مستقیم SQL برای قید و حفاظت تاریخچه. |

| ۵ | CBS11–12 | credit با تأمین منتخب سرور، مرز محافظت‌شدهٔ TransactionTemplate، پاسخ موفق ماندگار، replay و conflict. سند متوازن، هر دو projection و نتیجه با هم commit شوند؛ restart و retry همان شناسه آزموده شود. |
| ۶ | CBS13–15 | debit و انتقال اتمیک، رد نهایی بدون journal و طبقه‌بندی خرابی فنی. برداشت دقیق موجودی، replay کسری وجه، ترتیب قفل و rollback پس از نوشتن جزئی ثابت شود. هر برش HTTP متصل شود. |

| ۸ | CBS20 | سناریوی ترکیبی و خطای مستقل، راهنمای اجرای Docker و تست و محدودیت‌های دوزبانه، مرور کد و شواهد CI و نمایش چهار عملیات واقعی HTTP تا SQL. معیار ناموفق پیش از پذیرش رفع شود. |

در پایان، credit، debit، transfer و خواندن موجودی از محیط تمیز طبق راهنما اجرا می‌شوند. موفقیت، تاریخچهٔ متوازن تغییرناپذیر، projectionها و پاسخ ماندگار را اتمیک commit می‌کند. اعتبارسنجی رکورد مالی نمی‌سازد؛ رد کسب‌وکار پاسخ را بدون تغییر مالی نگه می‌دارد؛ retry منطبق پاسخ اصلی را می‌گیرد؛ payload متفاوت اجرا نمی‌شود؛ خرابی فنی و recovery حداکثر یک اثر commit‌شده را حفظ می‌کنند. تطبیق مستقل در نمای سازگار، موجودی را از تاریخچه تأیید می‌کند.

استقرار اولیه محدود به loopback و اپراتور مورداعتماد است. پیش از دسترسی اشتراکی یا بیرونی، احراز هویت و مالکیت لازم است. آزمایش کارایی CBS21–22، امنیت CBS24–25، OTP، cache پاسخ Redis، Kafka و outbox، CDC و FX پس از هسته می‌آیند. مدیریت ارز از دیتابیس پیش‌نیاز نسخهٔ اول نیست؛ ابتدا مجموعهٔ مجاز را از تنظیمات بدهید و در صورت نیاز منبع دیتابیسی را بعداً اضافه کنید.

تاریخ تحویل تعیین نشده است. سازگاری و اتصال SQL Server اولین ابهام زیرساختی است؛ برآورد زمانی را با پیشرفت واقعی آن تنظیم کنید. تعداد تست درصد تکمیل یا تسلط نیست. آخرین Maven verify پیش از انتشار با Java 21.0.11 تعداد ۱۵۰ تست را در ۷٫۳۱۴ ثانیه بدون failure، error یا skip گذراند. شواهد مالی SQL Server هنوز نداریم.

## نقطهٔ اجرای CBS23 در ۲۰۲۶-۱۰-۲۳

پایهٔ adapter HTTP با parser سخت‌گیرانهٔ DTO، دستور تایپ‌شده، DTO موفقیت/استعلام و ProblemDetail پایدار پیاده شده است. fallback پاسخ 503 می‌دهد و تست قرارداد با test double شاهد صحت مالی نیست. [شواهد](HTTP-adapter-evidence.md). گام بعد CBS06 برای مقایسهٔ canonical نسخه‌دار است؛ سپس CBS07–08 برای SQL Server و harness و بستن مرور CBS02–04 پیش از migration تجاری CBS09. در CBS10–20 باید fallback با مسیر ماندگار جایگزین شود و رفتار HTTP تا SQL Server اثبات شود. پذیرش رسمی و تسلط مستقل باز است.

## نقطهٔ اجرای CBS06 در ۲۰۲۶-۱۰-۲۳

قصد canonical نسخهٔ ۱ و fingerprint تأمین حفظ‌شده به‌صورت Portable پیاده شدند. verify کامل Java 21 تعداد ۲۲۳ تست را بدون failure، error یا skip گذراند؛ ۲۲ مورد canonical است. [قالب و مرز مقایسه/replay تأمین](Canonical-request.md). پذیرش رسمی کار و یادگیرنده باز است. گام اجرایی بعد CBS07–08 برای محیط Docker SQL Server و harness است؛ بستن مرور CBS02–04 پیش از migrationهای CBS09 لازم می‌ماند. این نتیجه اجرای HTTP، replay ماندگار یا semantics دیتابیس را اثبات نمی‌کند.

## پیاده‌سازی تأییدشدهٔ CBS09، ۲۰۲۶-۱۰-۲۳

V1 چهار جدول ledger در dbo را با کلید مرورشده، CHECK نام‌دار، FK ارز، state پاسخ و index می‌سازد. Flyway با db-migrate صریح اجرا می‌شود و migration عادی runtime غیرفعال است. cbs_migrator جدا مالک schema تاریخچهٔ cbs_migrations با اختیار DDL مرورشدهٔ dbo است؛ cbs_app و cbs_initializer مجوز object/column تست‌شده دارند. schema خصوصی تاریخچه، جزئیات ADR-010 را برای پرهیز از DML کلی کسب‌وکار دقیق‌تر می‌کند. پنجاه تست تازهٔ schema، اجرای کامل را به ۲۴۰ تست مستقل از زیرساخت و ۹۴ تست SQL Server بدون failure، error یا skip در ۱۷٫۸۷۹ ثانیه رساندند. هر دو دیتابیس محلی migrate/validate شدند؛ نبود تنظیمات و مهاجرت با runtime شکست می‌خورند. سلامت برنامه فقط با runtime موفق بود. بازتولید و محدودیت دقیق در [Schema.md](Schema.md) آمده است. گام بعد CBS10، نگاشت‌ها، journal افتتاحیه و موجودی committed است. پذیرش رسمی یادگیرنده جدا می‌ماند.
