# نقشهٔ راه مرحله‌ای

وضعیت: برنامهٔ پیشنهادی در ۲۰ اکتبر ۲۰۲۶. [English](../en/Roadmap.md) · [فهرست](../../README.md)

## مراحل و معیار اتمام

اتمام هر مرحله به معنی هماهنگی کد، تست، migration و مستندات هر دو زبان است. هنوز هیچ مرحله‌ای پیاده‌سازی نشده است. برآورد زمان پس از راه‌اندازی مخزن و اولین مسیر کامل انجام می‌شود.

| مرحله | خروجی | شواهد لازم برای عبور | نمونهٔ شاخه |
| --- | --- | --- | --- |
| P0 | قراردادها، تهدیدها، ADR، نسخه‌های ثابت، اسکلت مخزن و CI | قرارداد چهار عملیات، سیاست شناسه، ماتریس خطا، انتخاب دیتابیس، فهرست invariant و query، اجرای wrapper با Java 21 | `docs/balance-service-design` |
| P1 | هستهٔ کامل چالش با دیتابیس پیشنهادی SQL Server و مقداردهی حساب | چهار عملیات، حساب صحیح عددی، انتقال اتمیک، قفل مرتب، هویت ماندگار عملیات، تست واحد و integration روی SQL Server واقعی | `feature/core-balance-service` |
| P2 | صحت SQL و خط مبنای کارایی | تست مستقیم constraint، rollback، پلن واقعی queryهای مهم، گزارش بار ترکیبی و حساب پرترافیک | `test/database-correctness-baseline` |
| P3 | HTTP و کنترل دسترسی | اعتبارسنجی، مالکیت و نقش، جلوگیری از replay بین کاربران، مجوز credit/debit، قرارداد خطا و تست دورزدن | `feature/balance-http-api` |
| P4 | تأیید انتقال با کد یک‌بارمصرف وابسته به تراکنش | intent تغییرناپذیر، انقضا و سقف تلاش، مصرف اتمیک همراه انتقال، تست replay و تأیید هم‌زمان، نبود راز در لاگ | `feature/transfer-confirmation` |
| P5 | ذخیرهٔ پاسخ‌های نهایی در Redis | کنترل fingerprint، fallback به دیتابیس، تست قطع/پاک‌شدن/انقضا، تست دو instance، مقایسهٔ latency و hit rate | `feature/redis-idempotency-cache` |
| P6 | outbox تراکنشی، producer و consumer تاریخچه در Kafka | بازیابی بعد از قطعی، crash بین publish و ثبت نتیجه، consumer مقاوم به تکرار، ثبت offset بعد از commit، retry و dead letter | `feature/transaction-events` |
| P7 | امکان‌سنجی و مهاجرت به Debezium CDC | سازگاری نسخه‌ها، مجوزها، CDC بومی، SQL Server Agent و retention جدول تغییرات، تست snapshot/restart و تنها یک publisher فعال | `feature/outbox-cdc` |
| P8 | سخت‌سازی و تحویل | تست رگرسیون و خطا، پلن‌های نهایی، گزارش throughput، اجرای بازتولیدپذیر، release note دوزبانه و محدودیت‌ها | `docs/release-readiness` |

P1 به PRهای کوچک اسکلت، schema، credit، debit، transfer و تست هم‌زمانی تقسیم می‌شود. P6 نیز outbox، publisher، consumer و تست خرابی را جدا دارد. شاخه‌های جدول صرفاً نمونه‌اند و ایجاد نشده‌اند.

## خط مبنای چالش

قراردادی معادل `credit`، `debit`، `transfer` و `getBalance` حفظ شود. شناسهٔ رشته‌ای می‌تواند داخل برنامه به نوع مشخص تبدیل شود. مبلغ با `long` و واحد کوچک پول، ابتدا یک ارز مشخص، مبلغ مثبت و کنترل overflow مدل شود. موجودی اولیه فقط مسیر bootstrap یا fixture مستند باشد. انتقال موفق باید مقدار دقیقاً یکسان را میان دو حساب موجود و متفاوت جابه‌جا کند.

در نسخهٔ تک‌مستأجر پیشنهادی، transaction ID میان تمام انواع عملیات یکتاست. استفاده از همان شناسه با مبلغ، حساب یا نوع عملیات متفاوت conflict است. fingerprint شامل نوع عملیات، حساب‌ها، مبلغ، ارز و پس از ورود احراز هویت، actor است. کد OTP، زمان retry و correlation ID وارد fingerprint نمی‌شوند. قبل از بازگرداندن پاسخ قبلی، مجوز فعلی کنترل شود. سیاست replay خطای کسب‌وکار و retry خطای موقت در ADR-002 جداست.

تست P1 شامل credit هم‌زمان، debit رقابتی، ترکیب سه عملیات، تکرار هم‌زمان هر عملیات، شناسهٔ یکسان با درخواست متفاوت، انتقال دوطرفه، پیشرفت حساب مستقل هنگام قفل حساب دیگر، حساب ناموجود، مبلغ نامعتبر، انتقال به خود، overflow و rollback است. از barrier یا latch، انتظار محدود و جمع‌آوری خطای worker استفاده شود. تست فشار اثبات ریاضی همهٔ ترتیب‌های اجرای ممکن نیست.

## مرز توسعه‌ها

تست هسته از قرارداد trusted سرویس استفاده می‌کند. پس از ایجاد HTTP، تمام مسیرهای خارجی انتقال باید کنترل دسترسی داشته باشند. در P4 هیچ endpoint دیگری نباید الزام تأیید را دور بزند. credit/debit مجوز عملیاتی دارند و راهی برای تغییر آزاد موجودی توسط مشتری نیستند.

OTP فقط intent مشخص را تأیید می‌کند و جای idempotency، مالکیت یا کنترل موجودی را نمی‌گیرد. ساخت intent در پیشنهاد فعلی پول را رزرو نمی‌کند؛ هنگام تأیید موجودی دوباره بررسی می‌شود و ممکن است ناکافی باشد.

Redis پاسخ نهایی تغییرناپذیر را سریع‌تر برمی‌گرداند؛ جدیدبودن حرکت پول را تعیین نمی‌کند. Kafka واقعیت commitشده را منتشر می‌کند و مجری عملیات هم‌زمان موجودی نیست. تاریخچهٔ consumer با تأخیر به‌روز می‌شود و مرجع endpoint موجودی نیست.

Debezium پس از outbox مبتنی بر polling قرار دارد. راه‌اندازی CDC روی SQL Server نیازمند بررسی عملی است. P7 معیار امکان‌سنجی است؛ اگر سازگاری یا دسترسی کافی نبود، publisher آزموده‌شده باقی می‌ماند و دلیل ثبت می‌شود.

## اولین خروجی اجرایی

پیش از migration اول، ADR-001 تا ADR-003 و جدول بررسی دیتابیس مرور شوند. سپس پروژهٔ Java 21، Spring Boot و Maven با wrapper ساخته شود؛ مسیر ماندگار credit و بلافاصله debit و transfer تکمیل شوند. خط مبنای آزموده‌شدهٔ P1/P2 tag جدا داشته باشد تا توسعه‌های اختیاری وضعیت چالش را مبهم نکنند.
