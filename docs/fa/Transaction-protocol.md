# ترتیب تراکنش و قفل CBS04

[English](../en/Transaction-protocol.md) · [پروتکل هویت](Idempotency-protocol.md) · [دفترکل](Ledger.md) · [نتیجهٔ کسب‌وکار و مرز commit](Operation-outcomes.md)

پیش‌نویس مرور مشترک در ۲۰۲۶-۱۰-۲۳. TransactionTemplate و coordinator با کنترل نبود تراکنش بیرونی امروز پذیرفته شد. ترتیب، isolation، نگاشت قفل و تنظیمات زیر تا مرور و آزمون پیشنهادند. کد مالی، DDL یا شاهد اجرا وجود ندارد.

## یک تلاش

1. بیرون تراکنش، ساختار ثابت درخواست و دسترسی فعلی بررسی، دستور canonical ساخته و replay نتیجهٔ commitشده کنترل شود. سیاست متغیر کسب‌وکار برای نتیجهٔ موجود دوباره ارزیابی نشود.
2. coordinator تراکنش بیرونی را رد کند. callback از نوع REQUIRED در TransactionTemplate اجرا شود؛ بنابراین هر تلاش مالک یک تراکنش فیزیکی است. exception فنی از callback خارج شود؛ exception فنی checked نیز با ترجمه یا مدیریت صریح حتماً rollback ایجاد کند.
3. پیش از قفل حساب، شناسهٔ سراسری عملیات رزرو و flush شود. برخورد موردانتظار هویت باید از callback خارج و rollback شود؛ سپس بازیابی تازه انجام شود. پس از خطای persistence داخل همان تراکنش ادامه ندهیم.
4. مجموعهٔ کامل حساب‌های مشتری و سیستمی مشخص، تکراری‌ها حذف و حساب‌های موجود با ترتیب کلی نزولی یکسان قفل شوند. AccountId از UUID استفاده می‌کند؛ AccountLockOrder.DESCENDING ابتدا نیمهٔ بالایی و سپس پایینی ۶۴ بیتی را unsigned و نزولی مقایسه می‌کند. ترتیب مبدأمحور یا افزودن حساب تازه پس از شروع ترتیب ناسازگار مجاز نیست. lookupهای قفل به‌ترتیب همین comparator و پشت سر هم اجرا شوند؛ UUID.compareTo، ترتیب GUID سرور یا ORDER BY جایگزین تضمین ترتیب اخذ قفل نیستند. SQL واقعی هنوز مرور و تست می‌خواهد.
5. مبنای پیشنهادی READ_COMMITTED همراه خواندن قفل‌دار ایندکس‌شده است که پیش از بازگرداندن موجودی، حفاظت مناسب برای نوشتن بگیرد و تا commit نگه دارد. خواندن عادی و قفل‌گرفتن بعدی کافی نیست. قفل pessimistic در JPA باید به SQL واقعی SQL Server نگاشت و عمر قفل، انتظار، حساب ناموجود، deadlock و lock escalation روی نسخهٔ منتخب تست شود. annotation تضمین قفل فیزیکی صرفاً ردیفی نیست. افتتاحیه، بستن حساب، ترمیم و تمام writerها پروتکل را رعایت کنند.
6. وجود، ارز، نوع، وضعیت و قواعد مربوط زیر پروتکل قفل دوباره بررسی شوند. حساب درخواستی ناموجود رد نهایی با شناسهٔ درخواست بدون FK حساب می‌سازد. پیکربندی ناموجود حساب تأمین داخلی نقص زیرساخت/تنظیمات است، نه رد ساختگی مشتری. انتخاب حساب‌ها و نسخهٔ سیاست متغیر برای این تلاش سازگار باشد.
7. سند کامل در حافظه ساخته شود؛ مبلغ مثبت، حداقل دو سطر و توازن دقیق به‌ازای ارز و همهٔ projectionهای checked بررسی شوند. پیش از عبور تمام کنترل‌ها موجودی تغییر نکند. مشتری غیرمنفی و حساب سیستمی در بازهٔ علامت‌دار مجاز بماند. رد عادی کسب‌وکار مقدار Rejected ذخیره‌شده و بدون نوشتن پولی است.
8. سند موفق، postingها، تمام projectionها و پاسخ موفق سریال‌شده در همان تراکنش ذخیره شوند. خطای flush فنی است و همه را rollback می‌کند. رد فقط عملیات نهایی و پاسخ اصلی را commit می‌کند. رزرو خصوصی PENDING هرگز commit نشود. در بازهٔ قفل مالی Redis، ارسال OTP، Kafka یا تماس شبکهٔ خارجی نداریم.
9. پس از تأیید commit، coordinator نتیجه را برگرداند و به HTTP نگاشت کند. duplicate موردانتظار بازیابی در تراکنش تازه دارد. rollback موقت طبقه‌بندی‌شده retry کل تلاش با همان شناسه/دستور و backoff بیرون تراکنش دارد. commit نامطمئن ابتدا با هویت بازیابی شود؛ خطای اتصال یا یک lookup خالی اثبات عدم commit نیست.

## مثال انتقال

فرض کنیم A برابر 10000000-0000-4000-8000-000000000001، B برابر f0000000-0000-4000-8000-000000000002 و حساب تأمین F برابر 00000000-0000-4000-8000-000000000007 باشد. انتقال A به B ابتدا B و سپس A را قفل می‌کند. جهت مخالف هم B و سپس A را می‌گیرد؛ در اولین حساب مشترک منتظر می‌ماند و عمداً ترتیب مخالف نمی‌سازد. این ترتیب همان الگوی deadlock را کاهش می‌دهد؛ index، قید یکتایی و منابع دیگر همچنان می‌توانند deadlock بسازند. retry محدود کل تراکنش لازم می‌ماند.

credit مشتری B با حساب تأمین F ابتدا B و سپس F را قفل می‌کند. credit هم‌زمان مشتری‌های متفاوت ممکن است روی F منتظر بماند؛ این گلوگاه اندازه‌گیری شود و اتمیک‌بودن تضعیف یا حساب تأمین چندگانهٔ مرور‌نشده اختراع نشود.

## مرز خطا و تنظیمات

رد موردانتظار کسب‌وکار مقدار است، نه exception مولد rollback. خطای غیرمنتظرهٔ FK یا CHECK نقص است و rollback می‌شود؛ فقط برخورد قید یکتای مشخص transaction ID بازیابی duplicate می‌سازد. تمام DataIntegrityViolationExceptionها را replay تلقی نکنیم.

تعداد تلاش، backoff/jitter، انتظار قفل، timeout دستور/تراکنش و deadline کل درخواست تنظیم صریح می‌خواهند؛ مقدار اینجا انتخاب نشده است. انتظار pool/connection و backoff هم از بودجهٔ کل مصرف می‌کنند. timeout پیش از تلاش دیگر پاک‌سازی تراکنش و بازیابی تازهٔ هویت می‌خواهد و اثبات rollback نیست. پایان بودجه پاسخ موقت/نامطمئن با HTTP 503 پیشنهادی و همان شناسه می‌دهد.

## معیار پیش از persistence

نمایش UUID و comparator برنامه پذیرفته و unit-test شده‌اند؛ نسخه و edition سرور، SQL قفل واقعی و تنظیمات اتصال/isolation، چرخهٔ رزرو و سریال‌سازی، ثبات سیاست و حساب‌های درگیر، retry محدود و طبقه‌بندی خطا و مجوز نقش runtime مرور شوند. سقف عددی کسب‌وکار باز است. پس از مرور مفهومی، پیاده‌سازی دامنه در CBS05 شروع می‌شود؛ migration و عملیات ماندگار علاوه بر آن، انتخاب SQL و تست واقعی می‌خواهند.

تست‌ها شامل دو جهت، duplicate مطابق/متعارض، پیشرفت حساب مستقل، رقابت حساب سیستمی، rollback هر مرز نوشتن، retry قربانی، commit نامطمئن و reconciliation باشند. سند نوشتاری این رفتارها را تأیید نمی‌کند.
