# اجرای انتقال اتمیک و شواهد CBS14

[English](../en/Transfer-execution.md) · [برداشت](Debit-execution.md) · [مالکیت تراکنش](Operation-coordinator.md) · [API](API-v1.md)

## دامنه و درخواست

در CBS14، کلاس‌های `TransferHandler`، `TransferAttempt`، `TransferStore`، `JpaTransferStore`، `TransferResponseEncoder` و `JsonTransferResponseEncoder` اضافه شدند. `BalanceController`، handler انتقال را در سازنده می‌گیرد و از مسیر موجود انتقال مستقیم صدا می‌زند. schema نسخهٔ اول، adapter قفل حساب و قرارداد درخواست و پاسخ تغییر نکرده‌اند. هر سه mutation با `balance.execution.enabled=true` و همان سیاست معتبر startup فعال می‌شوند. این سیاست برای credit/debit همچنان تنظیم funding می‌خواهد؛ خود انتقال حساب funding انتخاب یا قفل نمی‌کند و metadata آن را هم ذخیره نمی‌کند.

فرض کنید حساب مبدأ ۱۰۰ ریال و حساب مقصد ۲۰ ریال دارند و هر دو موجودی پشتوانهٔ ledger معتبر دارند:

```http
POST /api/v1/transfers
Content-Type: application/json

{"transactionId":"transfer-example-001","sourceAccountId":"10000000-0000-4000-8000-000000000001","destinationAccountId":"f0000000-0000-4000-8000-000000000002","amountRial":100,"currency":"IRR"}
```

پس از موفقیت، مبدأ صفر و مقصد ۱۲۰ ریال دارند؛ مجموع موجودی مشتریان همان ۱۲۰ می‌ماند. یک journal شامل DEBIT مبدأ و CREDIT مقصد، هرکدام به مبلغ ۱۰۰ ریال است. موجودی funding تغییر نمی‌کند.

## مرز تراکنش و replay

1. ابتدا نیت درخواست canonical می‌شود و نتیجهٔ ماندگار پیش از سیاست فعلی ارز یا سقف بررسی می‌شود. درخواست یکسان، بایت‌های پاسخ اصلی را برمی‌گرداند؛ تغییر مبلغ، مبدأ، مقصد یا نوع عملیات با همان ID تعارض دارد.
2. برای نیت جدید، یک TRANSFER با وضعیت PENDING، هر دو UUID درخواستی، بایت‌ها و digest canonical و نسخهٔ سیاست اجرا رزرو می‌شود. ستون‌های funding مقدار NULL دارند. مبلغ معتبر بالاتر از سقف، رد ماندگار می‌گیرد.
3. `AccountStore.lockAll` مجموعهٔ کامل مبدأ و مقصد را بدون تکرار و با ترتیب `AccountLockOrder.DESCENDING` قفل می‌کند. خواندن‌ها با `UPDLOCK, HOLDLOCK` و به‌صورت ترتیبی‌اند. جهت انتقال و ترتیب GUID در SQL ترتیب قفل را عوض نمی‌کنند.
4. نبودن هرکدام از حساب‌ها، `ACCOUNT_NOT_FOUND` را بدون history یا تغییر موجودی commit می‌کند. حساب موجود باید فعال، از نوع بدهی مشتری و هم‌ارز با درخواست باشد؛ ناسازگاری وضعیت ذخیره‌شده خطای فنی است و مانند مسیرهای قبلی rollback می‌شود.
5. کسری وجه از snapshot قفل‌شدهٔ مبدأ تعیین می‌شود؛ انتقال کل موجودی مجاز است. ظرفیت مقصد با `destinationBalance > maxCustomerBalance - amount` و پیش از جمع بررسی می‌شود. این روش جلوی overflow را می‌گیرد و حتی برای مقصدی با `Long.MAX_VALUE`، رد `BALANCE_LIMIT_EXCEEDED` را نگه می‌دارد. سقف تراکنش مبلغ انتقال را فقط یک بار حساب می‌کند.
6. journal متوازن و هر دو projection پیش از نوشتن مالی محاسبه می‌شوند. history، هر دو موجودی و پاسخ نهایی در یک تراکنش متعلق به coordinator ذخیره می‌شوند. پاسخ موفقیت پس از پایان تراکنش برمی‌گردد.

انتقال به خود، ورودی نامعتبر است و پیش از رزرو با HTTP 400 رد می‌شود. رد کسب‌وکار فقط تصمیم ماندگار دارد و journal/posting ندارد. خطای فنی نوشتن یا قفل، رزرو و همهٔ تغییرات مالی را rollback می‌کند. تعارض constraint نام‌دار transaction ID ابتدا از تراکنش شکست‌خورده خارج می‌شود و سپس نتیجهٔ ماندگار را در تراکنش تازه بازیابی می‌کند. retry خودکار و بازیابی جامع commit نامعلوم، کار CBS15 و مراحل بعدی است؛ پس از 503 یا گم‌شدن پاسخ، caller باید همان ID را نگه دارد.

## بررسی، ۲۰۲۶-۱۰-۲۶

اجرای Java 21 با `./mvnw -o -B -ntp -Psqlserver-it verify`، تعداد **۳۸۵ تست قابل‌حمل و ۱۵۴ تست واقعی SQL Server** را با **صفر failure، error و skip** در **36.105 ثانیه** گذراند. مجموع XMLهای تازهٔ Surefire/Failsafe بررسی شد. نسبت به CBS13، تعداد ۳۴ تست قابل‌حمل و ۲۰ تست دیتابیس انتقال اضافه شده است. اجرای جداگانهٔ انتقال هم هر ۲۰ تست واقعی SQL Server را گذراند. تست‌های قبلی credit، debit، قفل حساب، persistence، schema، constraint و permission در اجرای کامل موفق بودند.

اولین compile متمرکز، تغییر نام اشتباه enum دستهٔ حساب در fixture تست تازه را پیدا کرد؛ پیش از قبولی اصلاح شد. در مرور تست‌ها، literal سمت posting در assertion مستقل SQL هم پیش از اجرای موفق اصلاح شد. Docker Desktop ابتدا خاموش بود؛ پس از startup، SQL Server با خطاهای 17138/17300/17312/28709 روبه‌رو شد و اولین تلاش integration در آماده‌سازی fixture با خطای pre-login شکست خورد. restart همان کانتینر موجود سلامت را برگرداند؛ image، volume، منابع، schema و permission تغییر نکردند. تلاش شکست‌خورده شاهد رفتار انتقال نیست. اجراهای نهایی با identityهای محدود موجود runtime، migrator و initializer انجام شدند و secretها در محیط محلی ignored ماندند.

تست‌های قابل‌حمل، تصمیم‌ها و چرخهٔ تراکنش Spring را می‌سنجند و تضمین دیتابیس نیستند. suite واقعی SQL Server شامل موفقیت HTTP با کل موجودی، مرز دقیق سقف مقصد، حفظ مجموع و reconciliation مستقل، replay و conflict، نبودن هرکدام از حساب‌ها، سقف مقصد، انتقال به خود، replay رد پس از تغییر سیاست یا وجه، بازسازی context/pool، timeout قفل و rollback تزریق‌شده است.

خطاهای rollback پس از journal/posting، نوشتن SQL فقط برای مبدأ، هر دو projection و ذخیرهٔ outcome تزریق می‌شوند. هر حالت باید نبودن operation/journal/posting ماندگار، تغییرنکردن هر دو موجودی و موفقیت retry با همان ID را بررسی کند. حالت نوشتن فقط مبدأ از spy تست در تراکنش HTTP استفاده می‌کند و hook تولیدی ندارد. حالت `Long.MAX_VALUE` فقط snapshot دامنهٔ قفل‌شده را تزریق می‌کند و رد ماندگار واقعی را با موجودی‌های واقعی بدون تغییر می‌سنجد؛ این تست شاهد history واقعی نزدیک BIGINT یا overflow محاسبات SQL نیست.

## معیارهای باز

هر چهار مسیر HTTP اکنون پیاده‌سازی دارند، اما این موضوع به‌تنهایی نسخهٔ هسته یا پذیرش مستقل یادگیری را کامل نمی‌کند. رقابت گستردهٔ duplicate، انتقال معکوس و عملیات ترکیبی، retry/backoff، بازیابی commit نامعلوم، مالکیت احرازشده و سنجش کارایی معیارهای بعدی‌اند. اجرای محلی SQL Server با شبیه‌سازی ARM64 همچنان خارج از پشتیبانی Microsoft است. افتتاحیه همچنان fixture کنترل‌شدهٔ تست است و ادعای آمادگی production نداریم.
