# انتقال معکوس و پیشرفت مستقل در CBS18

[English](../en/Transfer-progress.md) · [identity بین instanceها](Cross-instance-replay.md) · [دستورهای متفاوت](Concurrency-execution.md) · [وضعیت پیاده‌سازی](Implementation-status.md)

## چرا کار مستقل باید جلو برود

یک transfer منتظر حساب مبدأیی است که اتصال دیگری قفل کرده است. درخواست روی حساب‌های موجود و مستقل باید همچنان تمام شود، حتی اگر از همان برنامه برسد. سری‌کردن سراسری درخواست‌ها یا اضافه‌شدن participant مشترک ناخواسته، کار مستقل را به آن انتقال متوقف‌شده وابسته می‌کند.

انتقال‌های معکوس مسئلهٔ دیگری دارند: هر دو درخواست باید مجموعهٔ کامل participantها را با همان ترتیب UUID برنامه قفل کنند. جهت مبدأ/مقصد نباید به دو توالی متفاوت قفل تبدیل شود.

کلاس `SqlServerTransferProgressIT` ده تست واقعی HTTP تا SQL Server اضافه می‌کند. کد تولیدی، schema و تنظیمات runtime تغییر نکرده‌اند.

## دو انتقال معکوس

دو برنامهٔ مستقل، دستورهای A به B و B به A را با transaction IDهای متفاوت می‌گیرند. هر دو حساب در ابتدا ۱۰۰ ریال دارند. barrier رزرو هر دو attempt را با هم آزاد می‌کند؛ خود قفل‌گیری SQL در `AccountStore` می‌ماند.

دو مجموعهٔ پارامتر، مبلغ‌های ۳۰/۲۰ و کل موجودی قابل‌خرج ۱۰۰/۱۰۰ را پوشش می‌دهند. هر دو دستور باید موفق شوند و هرکدام یک operation، یک journal متوازن و دو posting نگه دارند. موجودی نهایی در حالت اول ۹۰/۱۱۰ و در حالت دوم ۱۰۰/۱۰۰ است؛ funding تغییر نمی‌کند.

مشاهده‌گر غیرفعال `AccountLockProbe` بعد از برگشت فراخوانی واقعی قفل حساب، ترتیب کلیدها را کپی می‌کند. نتیجهٔ هر دو جهت باید همان ترتیب نزولی UUID با مقایسهٔ unsigned باشد. این مشاهدهٔ ترتیب participantهای گزارش‌شده توسط adapter است، نه trace مستقل statement/قفل در driver. replay از هر دو برنامه باید بایت‌های پاسخ اصلی، شمارش‌ها و موجودی بازسازی‌شدهٔ مستقل را حفظ کند.

## هشت حالت پیشرفت مستقل

هر حالت با انتقال متوقف‌شدهٔ ۴۰ ریال از A با موجودی ۱۰۰ به D شروع می‌شود. یک اتصال JDBC جدا با identity محدود runtime، با update بدون تغییر projection، قفل واقعی حساب را نگه می‌دارد. تست ورود به adapter واقعی قفل و رزرو PENDING همان نویسنده را در تراکنش باز مشاهده می‌کند؛ سپس در حالی که اتصال خارجی هنوز تراکنش را باز نگه داشته، کار مستقل را می‌فرستد.

| درخواست مستقل | موجودی اولیهٔ حساب‌های مستقل | اثر لازم پیش از آزادشدن قفل |
| --- | --- | --- |
| credit بیست‌وپنج‌ریالی | مشتری ۱۰۰ | مشتری ۱۲۵، funding بیست‌وپنج بیشتر، یک journal تکمیل‌شده و دو posting. |
| debit بیست‌وپنج‌ریالی | مشتری ۱۰۰ | مشتری ۷۵، funding بیست‌وپنج کمتر، یک journal تکمیل‌شده و دو posting. |
| transfer بیست‌وپنج‌ریالی | مبدأ ۱۰۰، مقصد صفر | مبدأ ۷۵، مقصد ۲۵، funding بدون تغییر، یک journal تکمیل‌شده و دو posting. |
| GET موجودی | مشتری ۱۰۰ | HTTP 200 با موجودی مرجع ۱۰۰ ریال؛ projection/history همچنان reconcile می‌شوند. |

هر درخواست یک بار از برنامهٔ نویسندهٔ متوقف‌شده و یک بار از برنامهٔ دوم اجرا می‌شود؛ در مجموع هشت حالت. پاسخ و بررسی مستقل SQL برای history/projection باید زمانی تمام شوند که قفل خارجی هنوز برقرار و future انتقال متوقف‌شده تمام‌نشده است. سپس تست قفل را آزاد می‌کند، موفقیت دقیقاً یک‌بارهٔ انتقال را می‌خواهد و مبدأ ۶۰، مقصد ۴۰ و اثر مستقل بدون تغییر را بررسی می‌کند. replay از برنامهٔ دیگر باید بایت‌های ماندگار انتقال را بدون journal اضافه برگرداند.

مشاهدهٔ PENDING فقط برای instrumentation تست و دیدن رزرو در تراکنش باز از READUNCOMMITTED استفاده می‌کند. خواندن مالی تولیدی تغییر نمی‌کند. reconciliation هنگام برقرار بودن قفل فقط برای حساب‌های مستقل و بعد از آزادشدن آن برای همهٔ participantهاست. این کار ادعای snapshot سراسری سازگار در حین posting دلخواه هم‌زمان ندارد.

## بررسی، ۲۰۲۶-۱۰-۲۹

اجرای کامل Java 21 با `./mvnw -o -B -ntp -Psqlserver-it verify`، تعداد **۴۲۱ تست قابل‌حمل و ۱۸۸ تست واقعی SQL Server** را با **صفر failure، error و skip** گذراند. Maven زمان کل **01:00 min** را گزارش کرد. مجموع XMLهای تازهٔ Surefire/Failsafe بررسی شد.

اجرای متمرکز اولیه، هر ده تست تازهٔ SQL Server را در کنار ۴۲۱ تست قابل‌حمل، در 21.133 ثانیه گذراند. DocTrees در compiler وجود Javadoc سطح کلاس را برای هر ۱۵۶ type در Java، شامل probe مستقل، تأیید کرد؛ تولید Javadoc کل پروژه با دسترسی private و doclint بدون warning/error موفق بود. اسکن syntax tree در همهٔ ۱۵۵ فایل Java زیر src هیچ type تودرتو، local یا anonymous پیدا نکرد. لینک‌های اسناد، whitespace و اسکن مقادیر دقیق credential در logها/reportها هم موفق بودند.

fixture مشترک برنامه اکنون مشاهده‌گر اختیاری و غیرفعال قفل حساب می‌پذیرد. مسیر startup سه‌آرگومانی قبلی حفظ شده و suite کامل CBS17 در regression هست. همهٔ مشاهده‌ها خود adapter واقعی را صدا می‌زنند و snapshot، تصمیم کسب‌وکار یا خطای دیتابیس تزریق نمی‌کنند.

## محدودیت‌ها و کار بعدی

برنامه‌ها سرور و منابع persistence جدا در یک JVM دارند. این‌ها interleavingهای منتخب‌اند؛ ناممکن‌بودن همهٔ deadlockها، benchmark توان عملیاتی یا SLO تأخیر را ثابت نمی‌کنند. بررسی future تمام‌نشده، ترتیب نسبت به آزادشدن قفل را نشان می‌دهد و سقف دقیق زمان سرویس نیست. شبیه‌سازی ARM64 محلی SQL Server خارج از پشتیبانی Microsoft است.

بازیابی گسترده‌تر خطاهای commit/response در CBS19 می‌ماند. پذیرش مستقل یادگیری و معیار هستهٔ CBS20 جدا هستند. CBS17 و بررسی کامل Javadoc برای ۱۵۳ type با `9ea7d1f` روی `test/cross-instance-idempotency-races` commit و push شد؛ این checkpoint شامل CBS18 روی شاخهٔ وابستهٔ `test/transfer-locking-and-independent-progress` است.
